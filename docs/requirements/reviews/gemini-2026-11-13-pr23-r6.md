## 2. Verification of CI Quality Checks & Architecture Scope

A comprehensive adversarial robustness audit was conducted across the structural boundaries of PR #23 at revision 6 head `68a583d88276cd4339c0d08cebf6f0c8367ca76a`:

1. **Compiler-Enforced Build Gate (`xtask/src/build_gate.rs`):**
   - The PR replaces the previous static AST reachability walker with `cargo xtask build-gate`, building the entire workspace (all targets, all features) with the trusted `xtask` as `RUSTC_WRAPPER` appending `-F unsafe_code` to repository crates and `-C linker=<xtask>` as linker guard.
   - However, an unrestricted wildcard directory match in `is_adapter_dir()` permits any crate named `crates/solver-*` to opt out of `-F unsafe_code` without owner approval or code review.
2. **Linker Guard Implementation (`xtask/src/build_gate.rs`):**
   - The linker guard filters library requests using `linked()`. However, `linked()` parses only `-l` and `--library` flags alongside standard `.so`/`.a`/`.dylib` extensions. It omits macOS `-framework <name>` arguments, allowing forbidden Python or Julia frameworks to link undetected on macOS runners.
3. **Workflow Environment and Runner Policy (`xtask/src/workflows.rs`):**
   - Workflow checks enforce top-level permissions, hosted runner labels (`ubuntu-24.04`, `macos-15`), and static environment variable restrictions (`is_toolchain_env`).
   - However, script-level prohibition of `$GITHUB_ENV` and `$GITHUB_PATH` relies on literal substring matching, which is easily bypassed by dynamic parameter expansion in bash.
4. **Trusted Gates Isolation (`.github/workflows/trusted-gates.yml`):**
   - Verified that `trusted-gates.yml` triggers via `pull_request_target`, strictly checks out `refs/remotes/origin/main`, fetches PR commits solely as Git data objects into `refs/remotes/pull/head`, and executes `xtask` compiled from `main`. Untrusted PR code is never checked out, compiled, or executed by trusted gates.
5. **Review and Approval Gates (`xtask/src/review_gates.rs`):**
   - Verified independent review pairing requirements against `xtask/policy/review.toml`, that Gemini cannot supply approval, and that protected path modifications require owner exact-head approval under D-74.
6. **Provenance and Dataset Gate (`xtask/src/repository.rs`):**
   - Verified detection of sample sources, secret scanning, and prohibited paths.
   - However, `part == "raw"` directory path checking is case-sensitive, permitting uppercase directories such as `RAW/` or `Raw/` to escape validation.
7. **Attribution Pattern Coverage (`.githooks/attribution-patterns.regex`):**
   - Verified trailer and footer regex expansions. Several false negatives remain where generic identity tokens (`AI`, `LLM`), vendor-only entities (`Google AI`, `Meta AI`), collaboration prepositions, possessive syntax, and tools (`Roo Code`, `Continue`, `Supermaven`) evade detection.

### ADV23R6-01: Arbitrary Unreviewed Solver Adapter Directories Under `crates/solver-*` Bypass Compiler-Enforced Unsafe Scope

- **Classification:** STRUCTURAL
- **Severity:** CRITICAL
- **Area:** Rust Policy & Build Gate / Unsafe Boundary (ADR 0001, NFR-10)
- **File & Line Citation:** [xtask/src/build_gate.rs:114-117](../../../xtask/src/build_gate.rs#L114-L117), [xtask/src/rust_policy.rs:46-52, 188, 328](../../../xtask/src/rust_policy.rs#L46-L52)
- **Description:**  
  ADR 0001 and requirements specify that unsafe code is strictly prohibited outside individually reviewed solver adapters (`crates/solver-cuopt`, `crates/solver-gurobi`, `crates/solver-highs`, `crates/solver-xpress`).  
  In `xtask/src/rust_policy.rs` and `xtask/src/build_gate.rs`, `is_adapter_dir()` is defined as:
  ```rust
  pub fn is_adapter_dir(dir: &str) -> bool {
      let mut parts = dir.split('/');
      matches!(
          (parts.next(), parts.next(), parts.next()),
          (Some("crates"), Some(name), None) if name.len() > "solver-".len() && name.starts_with("solver-")
      )
  }
  ```
  In root `Cargo.toml`, workspace members are declared via glob:
  ```toml
  [workspace]
  members = [
      "crates/*",
      "xtask",
  ]
  ```
  Because `is_adapter_dir()` matches *any* directory whose name starts with `solver-` under `crates/`, and does not validate against a closed allow-list of reviewed adapters:
  1. An untrusted PR creates a new crate `crates/solver-evil` with `#![allow(unsafe_code)]` and arbitrary unsafe blocks.
  2. Because `Cargo.toml` uses `members = ["crates/*"]`, the root manifest does not need to be modified (avoiding any protected path changes under `repository.toml` or `CODEOWNERS`). `Cargo.lock` is not a protected path.
  3. In `cargo xtask policy`, `roots.entry(...).or_default() |= !package.adapter` marks the package as an adapter (`package.adapter = true`), exempting it from the crate-root `#![forbid(unsafe_code)]` rule.
  4. In `cargo xtask build-gate`, `is_adapter_dir("crates/solver-evil")` evaluates to `true`, so `-F unsafe_code` is NOT appended to rustc.
  
  Both `cargo xtask policy` and `cargo xtask build-gate` pass with exit code 0, completely undermining the workspace unsafe-code boundary.
- **Minimal Test Input:**
  In `crates/solver-evil/Cargo.toml`:
  ```toml
  [package]
  name = "solver-evil"
  version.workspace = true
  edition.workspace = true
  license.workspace = true
  [lints]
  workspace = true
  ```
  In `crates/solver-evil/src/lib.rs`:
  ```rust
  #![allow(unsafe_code)]
  pub fn deref_raw(p: *const i32) -> i32 {
      // SAFETY: test
      unsafe { *p }
  }
  ```
- **Commands Run:**
  ```bash
  cargo xtask policy
  cargo xtask build-gate
  ```
- **Observed Output:**
  ```text
  PASS: unsafe-scope
  PASS: manifests
  PASS: workflows
  PASS: python
  PASS: codeowners

  PASS: build-gate: compiler-enforced unsafe scope and native runtimes
  ```
  Both commands passed with exit code 0.
- **Suggested Fix:**  
  Replace the dynamic prefix check in `is_adapter_dir()` with an explicit allow-list of approved adapters loaded from trusted policy (`gates.toml` or `repository.toml`), e.g.:
  ```rust
  const REVIEWED_ADAPTERS: &[&str] = &[
      "crates/solver-cuopt",
      "crates/solver-gurobi",
      "crates/solver-highs",
      "crates/solver-xpress",
  ];
  ```
  And add `Cargo.lock` to `protected_paths` in `xtask/policy/repository.toml`.

### ADV23R6-02: Linker Guard Omits macOS Framework Arguments (`-framework <name>`), Allowing Prohibited Native Runtime Linking

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** Linker Guard & Build Gate / Native Runtime Ban (NFR-10)
- **File & Line Citation:** [xtask/src/build_gate.rs:176-221, 223-244](../../../xtask/src/build_gate.rs#L176-L221)
- **Description:**  
  Decision NFR-10 forbids linking native Python or Julia runtimes. In `xtask/src/build_gate.rs`, the build gate replaces the system linker with the trusted `xtask` binary (`-C linker=<xtask>`), which invokes `link()` to intercept forbidden library names via `linked()`.  
  In `linked()`:
  ```rust
  while let Some(piece) = iter.next() {
      if piece == "-l" || piece == "--library" {
          if let Some(name) = iter.next() {
              out.push(name.clone());
          }
      } else if let Some(name) = piece
          .strip_prefix("--library=")
          .or_else(|| piece.strip_prefix("-l"))
      {
          out.push(name.to_owned());
      } else if !piece.starts_with('-') {
          let file = piece.rsplit(['/', '\\']).next().unwrap_or(piece);
          let library = file.starts_with("lib")
              || file.ends_with(".so")
              || file.contains(".so.")
              || file.ends_with(".a")
              || file.ends_with(".dylib")
              || file.ends_with(".tbd");
          if library {
              out.push(file.to_owned());
          }
      }
  }
  ```
  On macOS (supported via the `macos-15` runner label in `gates.toml`), native libraries such as Python and Julia are standardly linked as frameworks: `-framework Python` or `-framework Julia` (or via `#[link(name = "Python", kind = "framework")]` or `cargo:rustc-link-arg=-framework` / `cargo:rustc-link-arg=Python`).  
  When rustc passes `["-framework", "Python"]` to the linker:
  1. The piece `"-framework"` starts with `-` and is neither `"-l"` nor `"--library"`, so it is skipped.
  2. The subsequent piece `"Python"` does not start with `-`. However, `file.starts_with("lib")` is false, and it does not end with `.so`, `.a`, `.dylib`, or `.tbd`. `library` evaluates to `false`.
  3. `linked()` returns `[]`, leaving `refused` empty in `link()`.
  
  The linker guard allows the command through to `cc` without reporting any NFR-10 violation.
- **Minimal Test Input:**
  Invoking the linker guard with framework arguments:
  ```bash
  XTASK_BUILD_GATE_LINKER=1 target/debug/xtask -framework Python
  ```
- **Command Run:**
  ```bash
  XTASK_BUILD_GATE_LINKER=1 ./target/debug/xtask -framework Python
  ```
- **Observed Output:**
  ```text
  (Delegates directly to cc; no NFR-10 refusal reported)
  ```
  Contrast with `-lpython3.12`:
  ```text
  error: NFR-10: linking a Python or Julia runtime is forbidden; the linker was asked for python3.12
  ```
- **Suggested Fix:**  
  In `xtask/src/build_gate.rs:linked()`, add support for `-framework` and `-Wl,-framework,` flags:
  ```rust
  if piece == "-framework" {
      if let Some(name) = iter.next() {
          out.push(name.clone());
      }
  }
  ```

### ADV23R6-03: Workflow Environment and Path Hardening Bypassed via Dynamic Command / Parameter Expansion

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** CI Workflow Checks / Environment Hardening (NFR-12, D-73)
- **File & Line Citation:** [xtask/src/workflows.rs:556-564](../../../xtask/src/workflows.rs#L556-L564)
- **Description:**  
  Decision NFR-12 and `xtask/src/workflows.rs` forbid workflow steps from setting compiler flags, wrappers, or writing to `$GITHUB_ENV` or `$GITHUB_PATH`.  
  In `xtask/src/workflows.rs:556-564`, `check_job()` inspects `run:` script contents:
  ```rust
  if script.contains("GITHUB_ENV") || script.contains("GITHUB_PATH") {
      findings.push(Finding::at(
          path,
          None,
          format!(
              "{step_scope}: run: may not write $GITHUB_ENV or $GITHUB_PATH; set env: per step"
          ),
      ));
  }
  ```
  This check uses literal substring containment. In Linux/macOS bash, a script can dynamically target `$GITHUB_ENV` or `$GITHUB_PATH` without ever including the literal strings `"GITHUB_ENV"` or `"GITHUB_PATH"`. Examples include:
  - Dynamic extraction: `$(env | grep ^GITHUB_E | cut -d= -f2)`
  - Parameter expansion / indirect reference: `target=GITHU; target+=B_ENV; echo "RUSTFLAGS=-Aunsafe_code" >> "${!target}"`
  - String concatenation: `eval "echo RUSTFLAGS=-Aunsafe_code >> \$GITHU"B_ENV`
  
  Because `script.contains("GITHUB_ENV")` evaluates to `false`, `cargo xtask policy` gives a clean pass. When the workflow runs on GitHub Actions, the runner processes the file write and exports the toolchain variables or path overrides to all subsequent steps in the job.
- **Minimal Test Input:**
  In `.github/workflows/ci.yml`:
  ```yaml
  - name: step-env-injection
    run: echo "RUSTFLAGS=-Aunsafe_code" >> $(env | grep ^GITHUB_E | cut -d= -f2)
  ```
- **Command Run:**
  ```bash
  cargo xtask policy
  ```
- **Observed Output:**
  ```text
  PASS: unsafe-scope
  PASS: manifests
  PASS: workflows
  PASS: python
  PASS: codeowners
  ```
  The check passed with exit code 0.
- **Suggested Fix:**  
  In `xtask/src/workflows.rs`, inspect scripts with case-insensitive tokenization and pattern matching for environment export patterns (e.g. matching `GITHUB_` prefixes, `printenv`, `env | grep`, indirect parameter syntax `${!`, or `>>`).

### ADV23R6-05: Generic `AI` and `LLM` Tokens Omitted From Trailer Pattern 31 (`Co-Authored-By: AI`, `Co-Authored-By: LLM`)

- **Classification:** ATTRIBUTION-SPELLING
- **Severity:** HIGH
- **Area:** D-52 Attribution Policy / Identity Trailers
- **File & Line Citation:** [.githooks/attribution-patterns.regex:20, 31](../../../.githooks/attribution-patterns.regex#L20-L31)
- **Description:**  
  Pattern 31 matches identity trailers (`Co-Authored-By: ...`):
  ```regex
  ^\s*{{DECOR}}(?:[\w{{DASH}}]*[{{DASH}}]|(?:co[{{DASH}}\s]*)?(?:authored|written|assisted|generated|created|developed|helped|signed[{{DASH}}\s]*off|pair[{{DASH}}\s]*programmed)\s+)(?:by|with)\s*:\s*(?:{{AINAME}}|{{IDNAME}}\s*<[^<>\r\n]+>|[^\r\n]*<?(?:...email...)>?)
  ```
  Notice that while Pattern 37 (footers) explicitly matches `(?:(?:{{AINAME}}|AI|LLM)|...)`, Pattern 31 only matches `{{AINAME}}`.  
  `AINAME` is defined as:
  ```regex
  define AINAME = (?:(?:{{VENDOR}}(?:[\s_-]*ai)?(?:['\x{2019}]s)?[\s_-]+)*{{MODEL}}[\p{L}\p{N}.+]*(?:{{SEP}}+{{WORD}})*{{SEP}}*)
  ```
  Because `AINAME` strictly requires `{{MODEL}}`, trailers crediting generic assistant identities without a specific model name—such as `Co-Authored-By: AI`, `Co-Authored-By: LLM`, `Co-authored-by: AI Assistant`, or `Co-authored-by: LLM Bot`—fail to match `AINAME` and have no vendor email address.  
  Pattern 37 does not match because its verb list `ATTRIBUTE` does not include `co-authored`. Thus, these trailers pass undetected.
- **Minimal Test Inputs:**
  - Input 1: `Co-Authored-By: AI`
  - Input 2: `Co-Authored-By: LLM`
  - Input 3: `Co-authored-by: AI Assistant`
- **Commands Run:**

  ```bash
  cargo xtask attribution --base HEAD --head HEAD --title "Co-Authored-By: LLM"
  cargo xtask attribution --base HEAD --head HEAD --title "Co-authored-by: AI Assistant"
  ```
- **Observed Output:**
  ```text
  scanned 0 commit(s), 0 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  scanned 0 commit(s), 0 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  scanned 0 commit(s), 0 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  ```
  All three inputs passed with exit code 0.
- **Suggested Fix:**  
  In Pattern 31, include `AI` and `LLM` in the name alternatives:
  ```regex

  ```

### ADV23R6-06: Vendor-Only AI Identifiers Without Model Tokens Evade Footers and Trailers (`Google AI`, `Meta AI`, `Apple Intelligence`)

- **Classification:** ATTRIBUTION-SPELLING
- **Severity:** HIGH
- **Area:** D-52 Attribution Policy / Vendor AI Products
- **File & Line Citation:** [.githooks/attribution-patterns.regex:16, 17, 20](../../../.githooks/attribution-patterns.regex#L16-L20)
- **Description:**  
  In `.githooks/attribution-patterns.regex`, `AINAME` requires a `MODEL` token:
  ```regex
  define AINAME = (?:(?:{{VENDOR}}(?:[\s_-]*ai)?(?:['\x{2019}]s)?[\s_-]+)*{{MODEL}}[\p{L}\p{N}.+]*(?:{{SEP}}+{{WORD}})*{{SEP}}*)
  ```

  When an attribution footer or trailer names a major AI provider's branded assistant product that is listed in `VENDOR` but has no separate model token in `MODEL`—such as:

  - `Meta AI`
  - `Apple Intelligence`

  1. `AINAME` fails because no `{{MODEL}}` token exists in `"Google AI"` or `"Meta AI"`.
  2. `(?:AI|LLM)` fails because `"Google AI"` contains the preceding vendor word.
  
  Consequently, footers like `Generated with Google AI`, `Generated with Meta AI`, `Generated with Apple Intelligence`, and trailers like `Co-Authored-By: Google AI` evade all patterns.

  Two significant omissions exist in `ATTRIBUTE` and `BY`:
  1. `pair-programmed` is included in Pattern 31 (for colon-trailers), but is omitted from `ATTRIBUTE` (line 26). When written as a footer sentence (`Pair-programmed with Claude`), it fails to match Pattern 37.

### ADV23R6-08: Possessive Assistant Phrasing (`with Claude's help`, `with Claude's assistance`) Evades Pattern 37

- **Classification:** ATTRIBUTION-SPELLING
- **Severity:** HIGH
- **Area:** D-52 Attribution Policy / Possessive Phrasing
- **File & Line Citation:** [.githooks/attribution-patterns.regex:19, 20, 37](../../../.githooks/attribution-patterns.regex#L19-L37)
- **Description:**  
  Pattern 37 expects the order:
  `{{ATTRIBUTE}}\s+{{BY}}\s*:?\s*{{HELP}}?(?:{{AINAME}}|AI|LLM)`
  where `HELP` is `(?:(?:the\s+|some\s+)?(?:help|assistance|aid|support)\s+(?:of|from)\s+)`.  
  In common English usage, developers frequently place the helper noun after a possessive model name:
  - `Written with Claude's help`
  - `Built with Claude's assistance`
  - `Generated with ChatGPT's help`
  
  This phrasing evades detection for two reasons:
  1. `HELP` only matches helper nouns *before* the model name (`with the help of Claude`).
  2. In `AINAME`, after `{{MODEL}}`, apostrophe `'` is not in `SEP = [\s_{{DASH}}:/,&()]`, so `Claude's` fails to parse as `AINAME`.
- **Minimal Test Inputs:**
  - Input 1: `Written with Claude's help`
  - Input 2: `Built with Claude's assistance`
- **Commands Run:**
  ```bash
  cargo xtask attribution --base HEAD --head HEAD --title "Written with Claude's help"
  cargo xtask attribution --base HEAD --head HEAD --title "Built with Claude's assistance"
  ```
- **Observed Output:**
  ```text
  scanned 0 commit(s), 0 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  scanned 0 commit(s), 0 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  ```
  Both inputs passed with exit code 0.
- **Suggested Fix:**  
  Support possessive phrasing in Pattern 37, matching `(?:{{AINAME}}|AI|LLM)(?:['\x{2019}]s)?(?:\s+(?:help|assistance|aid|support|code))?`.

PR #23 requires remediation of these 10 items prior to milestone M0 closure.
