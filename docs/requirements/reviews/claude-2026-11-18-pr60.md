# PR #60 document review: M1 open-data acquisition plan (2026-11-18)

Scope: [PR #60](https://github.com/Tobechukwu-Njoku/energy-grid-simulator/pull/60),
branch `docs/m1-acquisition-plan`, at the exact head above. The PR changes
`docs/research/m1-acquisition-plan.md` (526 lines, new) and
`docs/requirements/STATUS.md`. I reviewed it under D-54 against AGENTS.md,
`04-requirements.md`, `06-roadmap.md` (M1 row), `03-decisions-log.md` (D-1–D-77),
the D-56 provenance rules, `m1-data-inventory.md`, the merged repository data policy
(`xtask/policy/repository.toml`) and the merged PR #58
(`docs/research/m1-deficit-sources.md`). Line references are to the file at the
reviewed head. PR #60 was not modified.

The URL checks below used HEAD requests, or GET requests limited to the first 1 KiB
where HEAD was refused, plus the public catalogue metadata and the Elexon OpenAPI
document. No dataset payloads were downloaded. A failed check is evidence of an
access problem, not proof that the resource does not exist.

## What holds

  - The register has 43 `### SRC-` entries.
  - With the 11 excluded rows (SRC-06–11, 16a, 16b, 39, 40 and 42), all 54
    inventory rows are accounted for.
  - The classification counts are correct, and every entry keeps the inventory's
    tag. The 23 `open-commercial` entries are SRC-02–05, 13, 15, 17–20, 22, 23,
    29–31, 33, 35, 37a, 37b, 43, 45, 46 and 50. The 20 `research-only` entries are
    SRC-01, 12, 14, 21, 24–28, 32, 34, 36a, 36b, 38a, 38b, 41, 44 and 47–49.
  - "research-only / unverified" is normalised to the exact `research-only` tag.
  - No OSM, ODbL or share-alike source appears. Line 40 extends the exclusion to
    basemaps and upstream derivatives, and the G profile requires geometry
    lineage.
- **No research-only raw data.** Every `research-only` entry says raw commit
  **never**, and the PR adds no data files.
- **Plausible URLs and access methods.** I spot-checked:
  - NESO CKAN `package_show` for SRC-22, SRC-29 and SRC-45: HTTP 200 with JSON.
    The licences are "NESO Open Data Licence". The SRC-45 package lists the
    2023/24 and 2024/25 CSVs named in the plan.
  - Two NESO ETYS documents: `document/383936` (the 2025 Appendix B in the plan)
    and `document/351916` (#58's 2024 Appendix B). Both returned HTTP 200 as XLSX.
  - IANA release 2026f, the ECB `eurofxref-hist.zip`, the NGED and SSEN CKAN
    metadata, `gov.uk/bank-holidays.json`, ElecLink's loss-factor page and the
    MÉRA page: all HTTP 200.
  - The Elexon OpenAPI document (`/swagger/v1/swagger.json`) answers GET with
    HTTP 200 but HEAD with 404, so scripts must not probe it with HEAD. All 12
    SRC-43 routes and the SRC-15, SRC-30 and SRC-50 routes exist with the stated
    query parameters. REMIT filters on `publishDateTimeFrom/To`, as the plan says.
- **Provenance contract.** The C/N/G/T/R/E/K/W profiles cover the FR-19.AC1 fields
  and keep the three clocks separate as D-70 requires. They also preserve the
  existing `licence_status`, `source_url`, `bytes` and `sha256` manifest fields.
- **Roadmap coverage.** The plan covers every roadmap M1 input class:

  P0 keeps heavy work off the coding container and ties it to NFR-12.AC1/AC2
  (line 477). The appendix correctly separates credential-gated rows from
  public rows.
- **Cross-PR consistency with #59.** The real-source probes in PR #59
  (`SRC-22/29/30/33/43/45/46`, `SRC-35`) are all `open-commercial` here. The MÉRA
  end date (2019) and the GB-MID labelling match.

## Findings

1. **[High, blocking] The plan ignores the public sources identified in merged
   PR #58.** The plan is scoped to the 54 inventory rows and is based on `be21158`,
   which predates the merge of #58 (`1734f39`). As a result, it states that several
   inputs remain without a source when #58 already recorded credential-free
   candidates for them. Specifically:
   - **ETYS 2024 Appendix B.** SRC-01 uses only the 2025 edition and says "the
     2025/26 planning case cannot establish a commissioned 2024 fleet" (line 87).
     #58 Candidate 1.1 identifies the **2024** Appendix B (`document/351916`,
     reachable at review time) as the 2023/24 baseline. Add it as the primary
     historical edition, `research-only` (PC-1), and keep the 2025 edition as a
     labelled forward snapshot.
   - **Historical LTDS editions.** #58 Candidate 1.3 recommends the NGED and SSEN
     **November 2024** LTDS editions. SRC-03/05 pin the current releases
     (SSEN May 2026) and call the 2024 editions "historical suitability
     UNVERIFIED". Pin the dated 2024 releases for the holdout.
   - **Irish operating rules.** #58 Candidate 2.1 cites the EirGrid/SONI 2024
     Annual Renewable Constraint and Curtailment Report (publisher PDF reachable at
     review time). It gives SNSP 75%, an inertia floor of 23,000 MW·s, and a
     3 NI + 4 ROI minimum-unit rule enduring from 7 April 2024. The plan has no
     Irish rule source; SRC-24 is observational only. Add it as `research-only`
     R-profile evidence for FR-21.
   - **Embedded PV, Irish embedded capacity and costs.** #58 identifies Sheffield
     Solar PV_Live (3.1), SEAI/ESB microgeneration (3.3) and DESNZ Electricity
     Generation Costs 2023 (6.2, heat rates and VOM; page reachable). The plan
     instead says (line 441) that heat rates, VOM and Irish embedded generation
     "remain M1 work" with no candidate.
   - **Loss methodology.** #58 identifies Ofgem and SEM Committee loss
     methodology and TLAF filings (4.1, 4.3) to complement SRC-32 and SRC-50.
   - **Irish weather and holidays.** For Irish weather observations, #58 names
     Met Éireann hourly station records (7.3, partly CC BY 4.0, no credentials).
     For Irish holidays, it names the WRC public-holidays page (8.1); that page
     returned HTTP 200, whereas SRC-34 Citizens Information returns 403.
   - **RO buy-out notice.** SRC-38b says that a verified 2024/25 notice is
     UNVERIFIED and that a guessed slug returned 404. #58 Candidate 6.3 gives the
     exact Ofgem 2024/25 buy-out notice URL, which was reachable at review time.

   Rebase onto `main`. Then either add these sources as register entries, each with
   its own D-56 tag and raw-commit rule, or add a cross-reference table that maps
   each #58 candidate to "added", "deferred (reason)" or "rejected (reason)". Also
   reference the #58 proposals that change what must be acquired: Q-P-03 needs the
   three-term HVDC loss parameters, and Q-P-06 needs multi-level ERA5 wind.

2. **[High] The raw-commit permission contradicts the merged repository data
   gate.** Every open-commercial entry says raw commit "**yes, conditionally**"
   (lines 37–39 and each entry). The merged policy allows committed data only under
   `open_commercial_data = ["spikes/data/samples/*"]`, with a registered
   open-commercial record, or at exact `data_metadata_files` paths
   (`xtask/policy/repository.toml`, line 64). Any other committed CSV, XLSX, ZIP
   or JSON payload fails `xtask provenance`. Restate the rule: open-commercial raw
   files may be committed only as registered samples under the allow-listed path.
   Anything else stays outside git, or needs an owner policy change first. The
   plan's own recommendation to keep bulk raw data outside git then becomes the
   enforced default, not advice. This PR predates the merge of PR #23, which is why
   it misses the gate.

3. **[Medium] The raw-storage location and host are unspecified, despite the D-65
   constraint.** Line 36 proposes `~/energy-data/raw/` without naming a host.
   SRC-43 alone is 4.16 GiB, before the SRC-22, SRC-24 and SRC-44 archives. P0
   says ingest must not run on the coding container, but bulk acquisition itself
   is unplaced. State that the raw store lives on the D-65 target, or on a declared
   ADR 0004 storage location, with its path recorded in the manifest. Also state
   whether the D-62 Gemini acquisition runs may write there.

4. **[Medium] Decision traceability is thin.** The governing sources (line 27)
   cite only D-56 and D-72. Individual entries cite FR- and NFR- IDs but not the
   decisions that drive the rules applied to them. Add these to the governing list,
   or to the entries they constrain:
   - D-30 (licence recorded per dataset; share-alike ban);
   - D-57 (free historical prices only, for SRC-36b and SRC-44);
   - D-60 and D-71 (all-GB 132 kV; acquire or derive missing parameters, for the
     DNO coverage dispositions);
   - D-65 (no heavy work on the coding container);
   - D-62 (who performs bulk acquisition);
   - D-70 (reconstruction versus as-of), which the text uses but does not cite.

5. **[Low] SRC-36b admission should be stated more strongly.** The EEX disclaimer
   permits only a *personal* non-commercial copy. D-56 relaxes *commercial*
   permission. It does not turn a personal-use grant into a project-use grant. The
   fetch gate (line 294) is right, but say explicitly that SRC-36b cannot be
   admitted, even as `research-only`, unless project research use is confirmed.
   Recommend SRC-37a/37b and #58's DESNZ costs as the default carbon route meanwhile.

6. **[Low] The tzdata pin is not aligned across documents.** SRC-35 pins
   `tzdata2026f`, #58 Candidate 8.3 pins `2024b`, and PR #59's F-TIME says
   "pinned IANA tzdata (`SRC-35`)" without a version. Either release is acceptable
   for 2023–2024 history. Name one canonical release and hash in the plan, and
   state that PR #59's fixture uses it, so that the input identities (FR-4.AC1,
   NFR-1.AC1) agree.

7. **[Low] As-of filters are missing for two Elexon routes.** The current OpenAPI
   exposes `publishDateTimeFrom/To` on `FUELHH/stream` and
   `generation/outturn/interconnectors`, not only on REMIT. The stream table
   (lines 338–351) lists settlement-date filters only for these routes. Record the
   publication-time filters too, because they are the cheapest way to obtain
   publication vintages for FR-3.AC2 and D-70 as-of labelling.

8. **[Low] STATUS conflict and stale base.** GitHub reports `CONFLICTING` against
   `main`. After rebasing, restate the STATUS entry against the current header,
   which records D-1 … D-77, and note in the plan header which `main` commit it was
   checked against.

Findings 1 and 2 must be resolved before merge. The plan is otherwise careful
about rights, exclusions and evidence limits. It flags UNVERIFIED items honestly,
and its URLs and access routes are plausible on spot-check.
