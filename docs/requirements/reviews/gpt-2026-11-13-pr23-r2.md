## Findings requiring correction

### 1. F1 — High: PR-controlled entry points can replace every trusted gate

**Locations:** `.github/actions/trusted-policy/action.yml:25`,
`.github/workflows/ci.yml:99`, `.github/workflows/review-gates.yml:36`,
`xtask/src/workflows.rs:428`; **original findings:** R1, ADV23-02.

The base SHA is validated before use, and the normal action path really does
create a base worktree. However, the loader is a local action from the PR
checkout. The workflow steps deciding whether to invoke it and the checker
are also PR-controlled. The gate-graph check validates job names, job-level
conditions and dependencies; it does not establish what those jobs execute.

**Reproduced:** with the unchanged trusted `Policy`, supply each required job
in `ci.yml` and `review-gates.yml` with `steps: [{run: echo success}]`, retaining
the required names, hosted runners, read permissions, and aggregator's
`if: always()` and complete `needs`. Both `check_workflow` calls return **[]**.
A replacement composite loader whose sole command checks out `HEAD` also
returns **[]** from `check_action`. Requiring the same status names cannot
distinguish these replacement jobs from the intended checks. Replacing the
policy-approval and independent-review bodies removes those safeguards too.

There is also an unrestricted absence-based bootstrap fallback: when the base
lacks `xtask/Cargo.toml`, the action executes the PR's own seed. That is the
path for this PR because the compared main has no xtask. A warning is useful
disclosure, but is not independent policy evidence or an exact-SHA seed
authorization. Missing policy in any later base also re-enables the fallback.

**Regression assessment:** `r1_gate_graph_is_enforced` genuinely rejects
removed/conditional jobs and incomplete `needs`; `r1_head_cannot_weaken_trusted_policy`
genuinely keeps attribution configuration separate. Neither executes the actual
loader/workflow chain or tests a surviving job whose body is replaced.

**Suggested change:** establish a protected base/main entry point or required
workflow outside PR control, and verify the loader and gate execution as well
as the graph. Make the initial seed a separately attested exact-SHA exception;
fail closed on unexpected missing policy afterward. Until that is deployed,
retain the explicit coordinator check and do not describe PR-emitted status
names as proof that base policy ran. Add negative tests for replaced bodies,
head-directed loader output, softened steps and unexpected bootstrap fallback.

### 2. F2 — High: policy approval is impossible for this repository's shared identity

**Locations:** `xtask/src/review_gates.rs:246`,
`xtask/policy/repository.toml:5`, `.github/workflows/review-gates.yml:45`.

`evaluate_approval` requires the policy owner's latest non-comment review to
be `APPROVED` on the exact head. Both the configured policy owner and PR #23's
author are `Tobechukwu-Njoku`, confirmed by the read-only PR API. GitHub does
not permit an author to approve their own PR. The current gate therefore
cannot turn green through the documented owner-approval procedure.

This directly contradicts ADR 0001's explicit instruction to use required
status evidence rather than GitHub approval counts because the shared owner
identity cannot approve itself. The observed GitHub policy-approval job fails
asking for precisely this unavailable approval. No approval submission was
attempted, since the task forbids modifying PR #23.

**Regression assessment:** `r1_protected_changes_need_owner_approval` uses an
invented `APPROVED` review tuple without a PR author. It tests the pure
comparison correctly, but assumes a review GitHub cannot produce here.

**Suggested change:** implement exact-head policy-change attestation compatible
with ADR 0001 and the shared identity, read from trusted evidence, with the
old/new-policy disposition and independent review recorded. Test author=owner,
stale/missing attestations and rejection of PR-authored self-waivers. Do not
require an additional account or change owner decisions implicitly.

### 3. F3 — High: attribution after code on the same line still passes

**Locations:** `xtask/src/attribution.rs:222`, `xtask/src/attribution.rs:311`;
**original findings:** R2, ADV23-01.

Comment-prefix stripping works only at the beginning of a candidate. It does
not extract a trailing comment after code. The quoted-string candidate logic
does not help an unquoted source comment.

**Reproduced end to end:** use the submitted runtime-built `footer()` fixture
and commit `pub const N: u8 = 0; // {footer}` as the only changed source line
in a scratch repository. The unchanged `scan_range` reports **one added line,
zero findings**. The same footer at the beginning of `// {footer}` is rejected
by the submitted range test. This is valid, ordinary Rust source syntax.

**Regression assessment:** `r2_adv23_01_comment_prefixes_are_detected` exercises
leading comment forms and some quoted literals; `r2_source_comment_is_rejected`
checks a leading comment on its own line. Neither covers trailing comments.

**Suggested change:** extract comment/header payloads beyond column zero using
appropriate source syntax, retaining original locations and avoiding matches
on unrelated technical prose. Add end-to-end trailing Rust line/block comments
and corresponding relevant script/markup cases, each as the sole violating input.

### 4. F4 — High: macro-parameter lint opt-outs defeat the unsafe boundary

**Locations:** `xtask/src/rust_policy.rs:38`, `xtask/src/rust_policy.rs:107`,
`Cargo.toml:48`; **original finding:** R5.

Parsing unexpanded token streams cannot establish the effective lint level.
A macro definition contains `allow($lint)` without naming `unsafe_code`, while
its invocation names `unsafe_code` without an `allow` group. Both pass the scan.

**Reproduced:** put this in the disposable `crates/engine/src/lib.rs`, with crate
and function documentation and a valid SAFETY comment for the pointer read:

```rust
macro_rules! lowered {
    ($lint:ident) => {
        #[allow($lint)]
        pub fn value() -> i32 {
            let n = 1;
            let p = &n as *const i32;
            // SAFETY: p refers to n, which is alive and aligned.
            unsafe { *p }
        }
    };
}
lowered!(unsafe_code);
```

The unchanged built xtask, with the pristine policy directory, passes **every
policy category** against that checkout. `cargo clippy -p egs-engine --locked
-- -D warnings` also passes. A standalone `rustc --emit=metadata -Dunsafe_code`
probe passes as well. This is an effective opt-out in a non-adapter crate.

**Regression assessment:** missing workspace lint, multiline attributes, nested
`cfg_attr`, raw identifiers and a macro containing a *literal* lint opt-out
are all now tested and rejected. The macro fixture in
`r5_adv23_05_cfg_attr_is_rejected` does not substitute the lint identifier.

**Suggested change:** enforce a compiler-level `forbid` boundary for non-adapter
targets, or another equally effective reviewed mechanism that survives macro
expansion; keep only the reviewed solver exception. Test this substitution with
a real unsafe operation through the actual policy/build path.

### 5. F5 — High: env expression interpolation restores shell injection

**Locations:** `xtask/policy/gates.toml:8`, `xtask/src/workflows.rs:391`;
**original finding:** ADV23-16.

The run-expression allow-list accepts all `env.*` expressions. Environment
variables can themselves contain PR-controlled values. Interpolating them
with the Actions expression syntax still inserts raw text into the script
before shell parsing; passing through `env` only helps if the script reads
the shell environment variable instead.

**Reproduced:** `check_workflow` returns **[]** for a workflow with allowed
triggers/permissions/runner and this job fragment:

```yaml
env:
  TITLE: ${{ github.event.pull_request.title }}
steps:
  - run: echo "${{ env.TITLE }}"
```

A title containing shell command-substitution syntax becomes executable script
text. `echo "$TITLE"` is the appropriate environment-variable form. The current
workflows do not use this unsafe fragment; the defect is a promised policy
check that allows a new workflow to introduce it.

**Regression assessment:** `adv23_16_untrusted_expressions_in_run_are_rejected`
tests each listed untrusted context only when directly embedded in `run`.
The accepted `GOOD` fixture explicitly treats `${{ env.X }}` as safe.

**Suggested change:** remove blanket `env.*` script interpolation, or prove a
specific value is trusted before allowing it. Require shell-variable expansion
for event-derived data. Add this indirect case and a safe `$TITLE` control.

### 6. F6 — High: review evidence accepts incompatible roles and changed tree modes

**Locations:** `xtask/src/review_gates.rs:110`, `xtask/src/review_gates.rs:131`,
`xtask/src/review_gates.rs:196`; **original finding:** ADV23-10.

Two independent acceptance defects remain in the new review gate:

- **Roles and triage:** `parse_header` discards the role and `evaluate` checks
  only unequal provider strings. An approving report for code generation /
  Anthropic with reviewer adversarial / Gemini passes, despite the team rules
  forbidding Gemini from supplying independent review. A second adversarial
  file need only contain a PR SHA; unresolved high findings and absent triage
  do not prevent success. The coordinator note explicitly leaves triage manual,
  so this check is not the full NFR-3.AC3/ADR 0001 gate by itself.
- **Currentness:** `unchanged` compares only blob object IDs for final PR-changed
  paths. It ignores tree entry modes. In a scratch repository, approve the
  commit adding a non-executable `run.sh`, then commit only
  `git update-index --chmod=+x run.sh`. With the earlier approval and an
  adversarial report in a separate evidence revision, `independent_review`
  returns **[]** for the later head. This is a changed reviewed tree, not an
  evidence-only successor. No production file contents or fake SHA were needed.

**Regression assessment:** `adv23_10_review_gate_requires_evidence` correctly
rejects no reports, same provider, must-fix verdict, unrelated commits and a
supplied `unchanged_since=false`. It never exercises the real Git currentness
calculation, file modes, incompatible roles or triage dispositions.

**Suggested change:** check the trusted artifact/role/provider matrix and
recorded triage, and compare the full reviewed tree entries (including modes)
and allowed intervening evidence-only changes. If triage remains manual at
M0, require a separate exact-head coordinator attestation before representing
review as complete. Add real Git mode-change and wrong-role negative tests.

### 7. F7 — Medium: native-runtime scanning misses Cargo-selected build scripts

**Locations:** `xtask/src/rust_policy.rs:98`, `xtask/src/rust_policy.rs:152`;
**original finding:** ADV23-12.

Build-script scanning is enabled only for a path literally named `build.rs`.
Cargo permits `[package] build = "native.rs"`. The manifest validator accepts
that field, but a direct `println!("cargo:rustc-link-lib=python3.12")` in that
selected script is treated as an ordinary Rust literal and not checked.

**Reproduced:** `scan_rust("crates/engine/build.rs", source)` rejects that
script; changing only the path to `crates/engine/native.rs` returns **[]**.
Separately, `#[cfg_attr(all(), link(name = "julia"))]` on an unsafe extern block
in a solver adapter returns **[]**, because only an outer `link` attribute is
inspected. These are static policy probes; no Python/Julia library was loaded.

**Regression assessment:** `adv23_12_native_runtime_links_are_rejected` tests
the default build-script filename and a direct `#[link]` attribute only.

**Suggested change:** derive actual build-script targets from parsed package
metadata/manifests and inspect conditional link attributes too. Keep native
runtime/deployment inventory review for constructs a source scanner cannot
prove. Add custom-path and conditional-link tests.

### 8. F8 — Medium: CODEOWNERS coverage ignores more-specific overrides

**Location:** `xtask/src/repository.rs:503`; **related original finding:** R1.

The validator compares protected directory-pattern strings with identical
CODEOWNERS patterns or `*`, rather than checking the effective last matching
rule for protected files. For protected `/xtask/`, this returns **[]**:

```text
/xtask/ @Owner
/xtask/src/lib.rs @someone
```

The second rule transfers that file away from the policy owner. The submitted
CODEOWNERS is currently correct; the validator fails to keep it correct when
a more-specific rule is added. A separate lexical probe also returned **[]**
when the owner handle appeared after `#`; parsing should follow GitHub's
CODEOWNERS validity rules rather than counting arbitrary whitespace tokens.

**Regression assessment:** `r1_codeowners_cover_protected_paths` tests missing
coverage and repeated *identical* directory patterns, not narrower overrides.

**Suggested change:** validate effective ownership for every protected tracked
path with CODEOWNERS matching/precedence and reject invalid rules. Test exact
file, wildcard and directory overrides, including rules clearing ownership.

### 9. F9 — Medium: the provenance gate permits an unregistered dataset sample

**Locations:** `xtask/src/repository.rs:434`, `xtask/src/repository.rs:452`,
`xtask/policy/repository.toml:33`; **original finding:** ADV23-04.

The directory allow-list and manifest validation are independent. A matching
CSV path is accepted without any corresponding dataset/provenance entry.
The requirement that some manifest exists does not bind that manifest to the
committed data. D-56 requires every dataset to be tagged.

**Reproduced end to end:** in a scratch repository, commit an unrelated
`data/manifest.toml` containing a single open-commercial dataset and
`spikes/data/samples/unregistered.csv` containing synthetic two-column data.
The manifest does not name that file; there is no sources.tsv entry.
`repository::provenance`, using the pristine trusted policy, returns **[]**.

**Regression assessment:** `adv23_04_manifest_tags_are_required` correctly tests
tags, share-alike licence text and research-only filenames.
`adv23_04_data_files_and_secrets` tests path and secret rules, but explicitly
accepts an allowed sample without checking its provenance association.

**Suggested change:** require every allowed data file to resolve to an explicit
open-commercial provenance record, and validate conflicting/research-only
classifications. Keep path restrictions as an additional check. Add full-gate
tests for an unregistered sample, a valid registered sample, and a sample
registered as research-only.

attribution, docs, licence, policy and provenance jobs; independent-review and
policy-approval failed, and merge-gates had a failed run after macOS was
cancelled, with a newer macOS run queued. Those are observations, not a request
to rerun or alter PR #23. The review result rests on the source and reproduced
false negatives, not on transient CI scheduling.

Correct F1–F9, retain the passing original regressions, add the missing boundary
cases and request a fresh review on the final SHA. The independently reviewed
bootstrap seed, compatible policy-change attestation and coordinator adversarial
triage remain necessary before any merge-ready disposition.
