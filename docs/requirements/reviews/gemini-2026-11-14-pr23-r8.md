A build script requesting `cargo:rustc-link-lib=pypy3-c` or adding `cargo:rustc-link-search=/opt/pypy/lib` fails to be reported as an illegal Python runtime by `analyse()` or `names_runtime()`.
3. **CI Workflow Checks, Environment Hardening & Script Interpreter Policy (NFR-12, D-73):**
   - Verified that workflow scripts reject non-shell interpreters (`python`, `pypy`, `julia`, `node`, `ruby`, `perl`, etc.) and script extensions.
   - Verified that file commands (`$GITHUB_ENV`, `$GITHUB_PATH`) are restricted and dynamic shell redirection is caught.
   - However, in `xtask/src/workflows.rs:544-554`, `check_env()` strictly checks `is_toolchain_env()`, which only matches `CARGO*`, `RUSTC*`, `RUSTDOC*`, `RUSTUP_*`, and `*RUSTFLAGS*`. It fails to validate or restrict critical dynamic linker variables such as `LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES`, and `DYLD_LIBRARY_PATH`, permitting arbitrary dynamic library injection into workflow steps.
4. **Trusted Gates Isolation & Gate-Name Spoofing (`.github/workflows/trusted-gates.yml`, `xtask/src/review_gates.rs`, D-74):**
   - Verified that `trusted-gates.yml` runs from `main` via `pull_request_target`, checks out `refs/remotes/origin/main`, fetches the PR head only as Git data, and executes `xtask` compiled from `main`.
   - However, in `spoofed_gate_names()`, the check compares workflow job IDs and names against `trusted_jobs`, which is populated exclusively from workflows declaring `trusted = true` (`trusted-gates.yml`). The required PR status check and aggregator gate `merge-gates` defined in `ci.yml` is entirely omitted from `trusted_jobs`. Any PR workflow can define a job named `merge-gates` to spoof the required check run without detection.
5. **Provenance and Dataset Gate (`xtask/src/repository.rs`, D-56):**

   - However, in energy grid simulation and transmission system operations, European grid models (ENTSO-E CGMES / IEC 61970-552) and power flow network profiles standardly use `.rdf` (Resource Description Framework) and proprietary case archives `.pfd` / `.dz` (PowerFactory). 6. **Attribution Pattern Coverage (`.githooks/attribution-patterns.regex`, D-52):**

### ADV23R8-01: Spoofed Gate Name Detection Omits Required Aggregator Gate `merge-gates`, Permitting PR Workflows to Spoof CI Merge Checks

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** CI Review Gates / Spoofed Check Detection (F1, ADV23R-08, D-74)
- **File & Line Citation:** [xtask/src/review_gates.rs:604-658](../../../xtask/src/review_gates.rs#L604-L658), [xtask/src/workflows.rs:130-139](../../../xtask/src/workflows.rs#L130-L139), [xtask/policy/gates.toml:49-61](../../../xtask/policy/gates.toml#L49-L61)
- **Description:**  
  Decision D-74 and finding F1 prohibit pull-request workflows from defining jobs whose status checks spoof required gate checks.  
  In `.github/workflows/ci.yml`, the required status check protecting the `main` branch is the aggregator job `merge-gates`.  
  In `xtask/src/main.rs:210` and `xtask/src/workflows.rs:130-139`, the trusted gate list passed to `spoofed_gate_names()` is populated via `Policy::trusted_gates()`:
  ```rust
  pub fn trusted_gates(&self) -> (Vec<String>, Vec<String>) {
      let trusted: Vec<&Graph> = self.graphs.iter().filter(|graph| graph.trusted).collect();
      (
          trusted.iter().map(|graph| graph.file.clone()).collect(),
          trusted
              .iter()
              .flat_map(|graph| graph.jobs.iter().cloned())
              .collect(),
      )
  }
  ```
  In `xtask/policy/gates.toml`, only `trusted-gates.yml` sets `trusted = true`:
  ```toml
  [[workflow]]
  file = ".github/workflows/ci.yml"
  jobs = [
      "rust-linux", "rust-macos", "licences", "attribution", "docs", "policy", "provenance",
  ]
  aggregator = "merge-gates"

  [[workflow]]
  file = ".github/workflows/trusted-gates.yml"
  jobs = ["independent-review", "policy-approval"]
  trusted = true
  ```
  Consequently:
  1. `trusted_jobs` contains only `["independent-review", "policy-approval"]`.
  2. `merge-gates` (as well as all individual required gate jobs of `ci.yml`) is completely omitted from `trusted_jobs`.
  3. If a PR introduces an additional workflow (e.g. `.github/workflows/pr-bypass.yml`) defining a job `merge-gates` with a trivial pass, `spoofed_gate_names()` inspects the jobs against `trusted_jobs`.
  4. Because `merge-gates` is not in `trusted_jobs`, 0 findings are reported.
  5. Furthermore, `workflows::check()` does not restrict PRs from adding additional workflow files as long as the required workflows in `policy.graphs` are present.
  
  An untrusted PR workflow can create a check run named `merge-gates`, satisfying branch protection without running the actual merge gates.
- **Minimal Test Input:**
  In `.github/workflows/spoof.yml`:
  ```yaml
  name: spoof
  on: [pull_request]
  permissions:
    contents: read
  jobs:
    merge-gates:
      runs-on: ubuntu-24.04
      steps:
        - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1
          with:
            persist-credentials: false
        - run: echo "bypass"
  ```
- **Command Run:**
  Evaluating `spoofed_gate_names(&workflows, &trusted_files, &trusted_jobs)` where `trusted_jobs` is loaded via `Policy::trusted_gates()`.
- **Observed Output:**
  ```text
  findings: [] (0 findings reported; job `merge-gates` accepted without error)
  ```
- **Suggested Fix:**  
  In `Policy::trusted_gates()` or `gates.toml`, include all required gate jobs and aggregator jobs from `policy.graphs` (including `ci.yml`'s `merge-gates` and gate jobs) in the list of protected/spoof-prohibited check names.

### ADV23R8-02: Workflow Environment Validation in `check_env` Ignores Critical Dynamic Linker Variables (`LD_PRELOAD`, `LD_LIBRARY_PATH`)

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** CI Workflow Hardening / Environment Injection (ADV23R5-01, NFR-12)
- **File & Line Citation:** [xtask/src/workflows.rs:530-554](../../../xtask/src/workflows.rs#L530-L554), [xtask/policy/gates.toml:12-15](../../../xtask/policy/gates.toml#L12-L15)
- **Description:**  
  Decision ADV23R5-01 mandates that pull-request workflows may not inject arbitrary environment variables that alter execution, compiler behavior, or linker operations.  
  In `xtask/policy/gates.toml`, `allowed_env` restricts permitted workflow variables:
  ```toml
  allowed_env = ["CARGO_TERM_COLOR", "CARGO_INCREMENTAL", "CARGO_DENY_VERSION"]
  ```
  However, in `xtask/src/workflows.rs:544-554`, `check_env()` gates variables using `is_toolchain_env()`:
  ```rust
  pub fn is_toolchain_env(name: &str) -> bool {
      let upper = name.to_ascii_uppercase();
      upper == "CARGO"
          || upper.starts_with("CARGO_")
          || upper.starts_with("RUSTC")
          || upper.starts_with("RUSTDOC")
          || upper.starts_with("RUSTUP_")
          || upper.contains("RUSTFLAGS")
  }

  fn check_env(path: &str, name: &str, _value: &Yaml, policy: &Policy, findings: &mut Vec<Finding>) {
      if is_toolchain_env(name) && !policy.env.iter().any(|allowed| allowed == name) {
          findings.push(Finding::at(
              path,
              None,
              format!(
                  "`{name}` may not be set in workflows unless allowed_env in the trusted policy lists it (compiler flags, wrappers and lint levels stay out of CI)"
              ),
          ));
      }
  }
  ```
  Notice that `check_env()` only verifies variables for which `is_toolchain_env()` evaluates to `true`.  
  If a variable is NOT in `is_toolchain_env()`—such as the standard dynamic linker injection variables `LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES`, `DYLD_LIBRARY_PATH`, or script path variables `PYTHONHOME` / `PYTHONPATH`—`check_env()` silently ignores it.  
  A PR workflow can specify:
  ```yaml
  env:
    LD_PRELOAD: "/path/to/malicious.so"
    LD_LIBRARY_PATH: "/path/to/libs"
  ```
  at workflow level, job level, or step level, and `cargo xtask policy` reports a clean pass. Furthermore, neither `rust_policy::is_sanitised()` nor `build_gate::DRIVER_ENV` removes `LD_PRELOAD` or `LD_LIBRARY_PATH` prior to spawning compiler/linker processes.
- **Minimal Test Input:**
  In `.github/workflows/ci.yml`:
  ```yaml
  jobs:
    policy:
      runs-on: ubuntu-24.04
      env:
        LD_PRELOAD: "/tmp/injected.so"
  ```
- **Command Run:**
  ```bash
  cargo xtask policy
  ```
- **Observed Output:**
  ```text
  PASS: unsafe-scope
  PASS: manifests
  PASS: workflows
  PASS: python
  PASS: codeowners
  ```
  Clean pass with exit code 0.  
  Contrast with setting `RUSTFLAGS`:
  ```text
  FAIL: workflows
    .github/workflows/ci.yml: `RUSTFLAGS` may not be set in workflows unless allowed_env in the trusted policy lists it
  ```
- **Suggested Fix:**  
  Expand `check_env` to disallow setting any dynamic linker variables (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_*`) or non-allowlisted environment variables in workflow `env:` mappings.

### ADV23R8-03: Build Gate Runtime Enforcement in `names_runtime` Omits PyPy (`pypy`, `pypy3`)

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** Compiler Build Gate / Native Runtime Linking Ban (ADV23R7-03, NFR-10, D-73)
- **File & Line Citation:** [xtask/src/build_gate.rs:104-110, 1461-1475](../../../xtask/src/build_gate.rs#L104-L110)
- **Description:**  
  Decision D-73 and requirement NFR-10 forbid linking or embedding Python or Julia runtimes.  
  In round 7, ADV23R7-03 identified that Python runtime enforcement must include PyPy (`pypy`, `pypy3`). While `xtask/src/workflows.rs` was updated to check PyPy in workflow scripts, `names_runtime()` in `xtask/src/build_gate.rs` was not updated:
  ```rust
  #[must_use]
  pub fn names_runtime(text: &str) -> bool {
      let lower = text.to_lowercase();
      lower.contains("python") || lower.contains("julia")
  }
  ```
  `names_runtime()` is used in two critical paths in `build_gate.rs`:
  1. Inspecting Cargo build script execution messages in `analyse()`:
     ```rust
     Some("build-script-executed") => {
         for library in message["linked_libs"].as_array().into_iter().flatten() {
             let library = library.as_str().unwrap_or_default();
             if names_runtime(library) {
                 findings.push(Finding::general(format!(
                     "build script of `{package}` asks Cargo to link `{library}`: linking a Python or Julia runtime is forbidden (NFR-10)"
                 )));
             }
         }
         for search in message["linked_paths"].as_array().into_iter().flatten() {
             let search = search.as_str().unwrap_or_default();
             if names_runtime(search) {
                 findings.push(Finding::general(format!(
                     "build script of `{package}` adds search directory `{search}`: linking a Python or Julia runtime is forbidden (NFR-10)"
                 )));
             }
         }
     }
     ```
  2. Inspecting requested linker arguments in `LinkPolicy::check()`:
     ```rust
     let runtimes: BTreeSet<&String> = scan
         .named
         .iter()
         .filter(|name| names_runtime(name))
         .collect();
     ```
  PyPy's standard C-API shared library is named `libpypy3-c.so` (or `libpypy-c.so`). Because neither `"pypy3-c"` nor `"/opt/pypy/lib"` contains `"python"` or `"julia"`, `names_runtime()` returns `false`.  
  A build script requesting `println!("cargo:rustc-link-lib=pypy3-c");` or adding `println!("cargo:rustc-link-search=/opt/pypy/lib");` passes `analyse()` without any runtime linking finding.
- **Minimal Test Input:**
  In a package build script (`build.rs`):
  ```rust
  fn main() {
      println!("cargo:rustc-link-lib=pypy3-c");
      println!("cargo:rustc-link-search=/opt/pypy3/lib");
  }
  ```
- **Command Run:**
  Evaluating `analyse()` over Cargo's `build-script-executed` message:
  ```json
  {"reason":"build-script-executed","package_id":"egs-solver-highs","linked_libs":["dylib=pypy3-c"],"linked_paths":["/opt/pypy3/lib"],"env":[]}
  ```
- **Observed Output:**
  ```text
  findings: [] (0 findings; linking PyPy runtime accepted without error)
  ```
  Contrast with `python3.12`:
  ```text
  build script of `egs-solver-highs` asks Cargo to link `dylib=python3.12`: linking a Python or Julia runtime is forbidden (NFR-10)
  ```
- **Suggested Fix:**  
  Update `names_runtime()` in `xtask/src/build_gate.rs` to detect `pypy` and `graalpy`:
  ```rust
  pub fn names_runtime(text: &str) -> bool {
      let lower = text.to_lowercase();
      lower.contains("python") || lower.contains("julia") || lower.contains("pypy") || lower.contains("graalpy")
  }
  ```

### ADV23R8-04: Provenance Gate (D-56) Omits Standard Power Grid Network Model and CIM Exchange Extensions (`.rdf`, `.pfd`, `.dz`)

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** Provenance & Dataset Gate (D-56)
- **File & Line Citation:** [xtask/policy/repository.toml:35-51](../../../xtask/policy/repository.toml#L35-L51), [xtask/src/repository.rs:654-710](../../../xtask/src/repository.rs#L654-L710)
- **Description:**  
  Decision D-56 prohibits committing datasets outside allowlisted sample paths (`spikes/data/samples/*`) or metadata records.  
  In energy grid simulation and transmission operations, the European Network of Transmission System Operators for Electricity (ENTSO-E) mandates the Common Grid Model Exchange Standard (CGMES, IEC 61970-452 / IEC 61970-552). CGMES serializes full network topology, equipment, power flow parameters, and operational limits into Resource Description Framework (`.rdf`) files. Furthermore, commercial simulation tools widely used in European grid planning (e.g. DIgSILENT PowerFactory) exchange grid project cases in `.pfd` (PowerFactory database/project archive) and `.dz` (compressed case file) formats.  
  In `xtask/policy/repository.toml`, `data_extensions` enumerates recognized dataset extensions, including PSS/E (`.raw`, `.rawx`, `.sav`, `.dyr`) and IEEE Common Data Format (`.cdf`), but omits `.rdf`, `.pfd`, and `.dz`:
  ```toml
  data_extensions = [
      ".csv", ".tsv", ".parquet", ".feather", ".arrow", ".xlsx", ".xls", ".ods", ".zip",
      ".gz", ".bz2", ".xz", ".7z", ".tar", ".nc", ".cdf", ".grib", ".grib2", ".grb", ".h5",
      ...
  ]
  ```
  Furthermore, because CGMES `.rdf` files are XML-based text representations, they do not start with any magic byte sequence in `DATA_SIGNATURES`.  
  If a developer commits an unapproved transmission grid model as `spikes/europe_grid_model.rdf` or `spikes/case.pfd`:
  1. Neither `.rdf` nor `.pfd` matches `data_extensions`.
  2. `data_signature()` fails to match any binary header.
  3. `cargo xtask provenance` outputs a clean pass (`PASS: provenance/secrets/data (D-56)` with exit code 0).
  
  In contrast, committing the identical network dataset in `.raw` (PSS/E), `.cdf` (IEEE), or `.epc` format is rejected with exit code 1.
- **Minimal Test Input:**
  Tracked file `spikes/europe_grid_model.rdf` or `spikes/network_case.pfd`.
- **Command Run:**
  ```bash
  cargo xtask provenance
  ```
- **Observed Output:**
  ```text
  PASS: provenance/secrets/data (D-56)
  ```
  Exit code 0.  
  Contrast with `spikes/europe_grid_model.raw`:
  ```text
  FAIL: provenance/secrets/data (D-56)
    spikes/europe_grid_model.raw: data file outside the allow-listed open-commercial sample paths (D-56)
  ```
- **Suggested Fix:**  
  Add `.rdf`, `.pfd`, and `.dz` to `data_extensions` in `xtask/policy/repository.toml`.

### ADV23R8-08: Attribution Footers with Preposition `under` and Noun `supervision` Evade Pattern 49

- **Classification:** ATTRIBUTION-SPELLING
- **Severity:** HIGH
- **Area:** D-52 Attribution Policy / Preposition and Noun Coverage
- **File & Line Citation:** [.githooks/attribution-patterns.regex:39-40, 49](../../../.githooks/attribution-patterns.regex#L39-L49)
- **Description:**  
  In `.githooks/attribution-patterns.regex`, Pattern 49 joins verbs to names using `BY` and optional `HELP`:
  ```regex
  define BY = (?:with|by|via|using|through|from|thanks\s+to|courtesy\s+of|alongside|(?:together|jointly)\s+with|in\s+(?:collaboration|partnership|cooperation|conjunction|tandem)\s+with)
  ```

  Notice two omissions in these definitions:
  1. `BY` omits the common English preposition `under` (e.g. `Written under the guidance of Claude`).

  - `Written under the supervision of Claude`
  - `Written with supervision from Claude`
  
  `BY` fails to match `under`, and `HELP` fails to match `supervision`. As a result, the footers evade Pattern 49 entirely.

- **Suggested Fix:**  
  - Add `under` to `BY` in `.githooks/attribution-patterns.regex:39`.
  - Add `supervision` to `HELP` in `.githooks/attribution-patterns.regex:40`.

## 5. Conclusion & Recommendations

The revision 8 enhancements on PR #23 head `bcd4b2c7aa933662ad952f3656b1a1f408057fc3` successfully resolve all 8 vulnerabilities identified in round 7 (ADV23R7-01 through ADV23R7-08), including case-insensitive job ID matching in `spoofed_gate_names`, expansion of `data_extensions` and content sniffing for compressed data archives, interpreter family matching in `invokes_interpreter`, and pattern additions for prompting footers and generic coding assistants.

However, this round 8 adversarial robustness audit confirms 8 remaining false negatives (4 STRUCTURAL and 4 ATTRIBUTION-SPELLING):
- **4 STRUCTURAL gaps:** spoofed gate name detection omitting the required aggregator `merge-gates` from protected check names, workflow environment validation in `check_env` ignoring dynamic linker injection variables (`LD_PRELOAD`, `LD_LIBRARY_PATH`), build gate runtime detection in `names_runtime` omitting PyPy (`pypy3-c`), and provenance gate omission of standard power grid network model and CIM exchange extensions (`.rdf`, `.pfd`, `.dz`).
- **4 ATTRIBUTION-SPELLING gaps:** omission of `OpenHands` / `OpenDevin`, `Bolt` / `Bolt.new`, and `Replit` from tool dictionaries; omission of vendor email domains for Tabnine, Phind, OpenHands, Replit, and StackBlitz; omission of verbs `reviewed` and `fixed` from footer `ATTRIBUTE`; and omission of preposition `under` and noun `supervision` from footer patterns.

PR #23 requires remediation of these 8 items prior to milestone M0 closure.
