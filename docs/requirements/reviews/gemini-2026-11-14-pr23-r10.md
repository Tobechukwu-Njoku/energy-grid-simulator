### ADV23R10-01: Provenance Gate (D-56) Omits Standard Optimization Solution, Basis, and MIP-Start Dataset Formats (`.sol`, `.mst`, `.bas`, `.ilp`)

- **Classification:** CORE
- **Severity:** HIGH
- **Area:** Provenance & Dataset Gate (D-56)
- **File & Line Citation:** [xtask/policy/repository.toml:35-63](../../../xtask/policy/repository.toml#L35-L63), [xtask/src/repository.rs:686-713](../../../xtask/src/repository.rs#L686-L713)
- **Description:**  
  Decision D-56 prohibits committing datasets outside allow-listed open-commercial sample paths (`spikes/data/samples/*`).  
  The repository develops mathematical optimization models and power system dispatch engines (`egs-solver-highs`, `egs-solver-gurobi`, `egs-solver-xpress`, `egs-solver-cuopt`, `egs-optimisation`).  
  In mathematical programming, power grid dispatch simulation, and operations research, solver solutions and intermediate solver artifacts are standardly exchanged as:
  - `.sol`: Solution files containing primal dispatch schedules, generator setpoints, nodal marginal prices, branch power flows, and dual multipliers (supported by HiGHS, Gurobi, CPLEX, Xpress, CBC).
  - `.mst`: Mixed Integer Programming (MIP) start files containing complete integer solution vectors used for warm-starting unit commitment runs.
  - `.bas`: Simplex basis files containing optimal basis statuses for warm-starting linear programming solves.
  - `.ilp`: Irreducible Inconsistent Subsystems / infeasibility files containing problem conflict models.  
  
  In `xtask/policy/repository.toml`, `data_extensions` enumerates model formats (`.mps`, `.qps`, `.lp`, `.gms`), but omits `.sol`, `.mst`, `.bas`, and `.ilp`.  
  Furthermore, because `.sol`, `.mst`, and `.bas` files are ASCII text files consisting of variable names and floating-point values, they carry no binary magic bytes recognized by `DATA_SIGNATURES`. In addition, `solver_model()` in `xtask/src/repository.rs` only inspects input problem formulations (`MPS`, `LP`, `GAMS`), not solution or basis formats.  
  
  When an unapproved dispatch solution or unit commitment warm-start dataset is committed as `spikes/dispatch.sol` or `spikes/unit_commitment.mst`:
  1. Neither `.sol` nor `.mst` matches `data_extensions`.
  2. Content sniffing does not recognize them as data.
  3. `cargo xtask provenance` outputs `PASS: provenance/secrets/data (D-56)` with exit code 0.
- **Minimal Test Input:**
  Tracked file `spikes/dispatch.sol` or `spikes/unit_commitment.mst`:
  ```text
  # Solution for model unit_commitment
  # Objective value = 1.2345e+05
  generator_1 100.0
  generator_2 250.0
  bus_voltage_1 1.02
  ```
- **Command Run:**
  ```bash
  git add -f spikes/dispatch.sol spikes/unit_commitment.mst
  cargo xtask provenance
  ```
- **Observed Output:**
  ```text
  PASS: provenance/secrets/data (D-56)
  ```
  Clean pass with exit code 0.
- **Suggested Fix:**  
  Add `.sol`, `.mst`, `.bas`, and `.ilp` to `data_extensions` in `xtask/policy/repository.toml`.

### ADV23R10-02: Python Policy (D-20, D-73) Fails to Restrict Julia Script Files (`.jl`) Outside Approved Spike / Validator Paths

- **Classification:** CORE
- **Severity:** HIGH
- **Area:** Scripting Language Scope (D-20, D-73, NFR-10)
- **File & Line Citation:** [xtask/src/repository.rs:37-74](../../../xtask/src/repository.rs#L37-L74), [xtask/policy/repository.toml:28-30](../../../xtask/policy/repository.toml#L28-L30)
- **Description:**  
  Decision D-20 and D-73 establish: "Rust is the primary language wherever code is needed — not Python with Rust bindings. Rust SDK/CLI is primary; a Python SDK is optional/later. Python/Julia allowed only for offline validation against reference tools and the TS frontend... D-73: Rust for product code, tooling, CI and tests. Python allowed only in spikes/ and offline reference validators."  
  In `xtask/src/repository.rs`, `check_python()` enforces language boundaries across repository paths:
  ```rust
  let python_name = [".py", ".pyw", ".pyi", ".ipynb"]
      .iter()
      .any(|ext| lower.ends_with(ext));
  let python_shebang = !name.contains('.')
      && heads(path).is_some_and(|first| first.starts_with("#!") && first.contains("python"));
  ```
  Notice that `check_python()` inspects only Python extensions and Python shebangs. It completely omits Julia scripts (`.jl`) and Julia shebangs (`#!/usr/bin/env julia`).  
  If a developer commits Julia scripts outside `spikes/` and reference validators (for example, in `crates/grid/validator.jl` or `crates/scenario/run.jl`):
  1. Neither `.jl` nor Julia shebangs trigger `check_python()`.
  2. `cargo xtask policy` reports `PASS: python` with exit code 0.
- **Minimal Test Input:**
  Tracked file `crates/validator.jl`:
  ```julia
  println("Julia script")
  ```
- **Command Run:**
  ```bash
  git add -f crates/validator.jl
  cargo xtask policy
  ```
- **Observed Output:**
  ```text
  PASS: unsafe-scope
  PASS: manifests
  PASS: workflows
  PASS: python
  PASS: codeowners
  ```
  Clean pass with exit code 0.
- **Suggested Fix:**  
  In `xtask/src/repository.rs`, expand `check_python()` (or rename to script language policy) to inspect `.jl` extensions and Julia shebangs (`contains("julia")`), ensuring Julia is restricted to `spikes/` and approved reference validators.

### ADV23R10-03: Prepositional Attribution Footers Starting with `With <help/assistance/guidance> from/of <Model>` Evade Pattern 52 Due to Missing Leading Verb Requirement

- **Classification:** PERIPHERAL
- **Severity:** HIGH
- **Area:** D-52 Attribution Policy / Prepositional Sentence Footers
- **File & Line Citation:** [.githooks/attribution-patterns.regex:41-52](../../../.githooks/attribution-patterns.regex#L41-L52)
- **Description:**  
  Decision D-52 prohibits whole-line AI attribution trailers and footers in commits, PR titles, and PR bodies.  
  In `.githooks/attribution-patterns.regex`, Pattern 52 matches attribution sentence footers:
  ```regex
  ^\s*{{DECOR}}(?:\*{1,2})?{{ATTRIBUTE}}\s+{{BY}}\s*:?\s*{{HELP}}?(?:{{NAME}}|\[{{NAME}}\]\(https?://[^\s)]+\))[.!]?(?:\*{1,2})?\s*$
  ```
  Pattern 52 strictly requires an `{{ATTRIBUTE}}` verb (`Written`, `Generated`, `Assisted`, etc.) at the start of the pattern before `{{BY}}` (`with`, `by`, `from`).  
  In software engineering PR descriptions and commit messages, developers frequently write attribution footers phrased as standalone prepositional credit clauses:
  - `With help from Claude`
  - `With assistance from Claude`
  - `With guidance from Claude`
  - `With input from Claude`
  - `With suggestions from Claude`
  - `With the assistance of Claude`
  
  Because these footers start directly with `With` rather than an `{{ATTRIBUTE}}` verb:
  1. Pattern 52 fails to match due to the missing leading `{{ATTRIBUTE}}`.
  2. Patterns 46 and 50 fail to match because they enforce git trailer syntax with a mandatory `:` separator (`Key: Value`).
  3. `cargo xtask attribution` reports `PASS: attribution policy (D-52)` with exit code 0.
- **Minimal Test Inputs:**
  - Input 1: `With help from Claude`
  - Input 2: `With assistance from Claude`
  - Input 3: `With guidance from Claude`
  - Input 4: `With input from Claude`
- **Commands Run:**
  ```bash
  cargo xtask attribution --base HEAD --head HEAD --title "With help from Claude"
  cargo xtask attribution --base HEAD --head HEAD --title "With assistance from Claude"
  cargo xtask attribution --base HEAD --head HEAD --title "With guidance from Claude"
  cargo xtask attribution --base HEAD --head HEAD --title "With input from Claude"
  ```
- **Observed Output:**
  ```text
  scanned 0 commit(s), 0 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  ```
  All 4 inputs passed with exit code 0.
- **Suggested Fix:**  
  In `.githooks/attribution-patterns.regex`, make `{{ATTRIBUTE}}\s+` optional in Pattern 52 when `{{BY}}` is followed by `{{HELP}}`, or add a pattern for `^\s*{{DECOR}}(?:\*{1,2})?{{BY}}\s+{{HELP}}(?:{{NAME}}|\[{{NAME}}\]\(https?://[^\s)]+\))[.!]?(?:\*{1,2})?\s*$`.

### ADV23R10-04: Standalone Autonomous Coding Assistants `Blackbox` and `Sweep` Evade `MODEL` and `VENDOR` When Cited Without ` AI` Suffix

- **Classification:** PERIPHERAL
- **Severity:** HIGH
- **Area:** D-52 Attribution Policy / Tool Dictionaries
- **File & Line Citation:** [.githooks/attribution-patterns.regex:23-24](../../../.githooks/attribution-patterns.regex#L23-L24)
- **Description:**  
  In `.githooks/attribution-patterns.regex`, commit `cf55dc3` added JetBrains, Blackbox, and Sweep to `MODEL`:
  ```regex
  define MODEL = (?:...|blackbox[\s_-]*ai(?![\p{L}\p{N}])|sweep[\s_-]*ai(?![\p{L}\p{N}])|...)
  ```
  Notice that `MODEL` strictly requires the suffix `[\s_-]*ai` for `blackbox` and `sweep`.  
  Unlike models and agents such as `claude`, `chatgpt`, `copilot`, `cursor`, `devin`, `aider`, `windsurf`, `codeium`, `supermaven`, and `replit` (which match the standalone name without requiring `ai`), `Blackbox` and `Sweep` without `ai` do not match `MODEL`.  
  Furthermore, while `blackbox` and `sweep` are in `VENDOR`, `AINAME` (line 27) requires `{{MODEL}}`, and `GENERIC` (line 31) requires `{{VENDOR}}` to be followed by `ai`, `agent`, `assistant`, `model`, etc.  
  When an author credits these tools by their product name:
  - `Generated by Blackbox`
  - `Co-Authored-By: Blackbox`
  - `Generated by Sweep`
  - `Co-Authored-By: Sweep`
  
  The inputs fail to match both `MODEL` and `GENERIC`, and pass undetected with exit code 0.
- **Minimal Test Inputs:**
  - Input 1: `Generated by Blackbox`
  - Input 2: `Co-Authored-By: Blackbox`
  - Input 3: `Generated by Sweep`
  - Input 4: `Co-Authored-By: Sweep`
- **Commands Run:**
  ```bash
  cargo xtask attribution --base HEAD --head HEAD --title "Generated by Blackbox"
  cargo xtask attribution --base HEAD --head HEAD --title "Co-Authored-By: Blackbox"
  cargo xtask attribution --base HEAD --head HEAD --title "Generated by Sweep"
  cargo xtask attribution --base HEAD --head HEAD --title "Co-Authored-By: Sweep"
  ```
- **Observed Output:**
  ```text
  scanned 0 commit(s), 0 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  ```
  All 4 inputs passed with exit code 0.
- **Suggested Fix:**  
  In `MODEL` in `.githooks/attribution-patterns.regex:24`, allow `ai` to be optional:
  `blackbox(?:[\s_-]*ai)?(?![\p{L}\p{N}])|sweep(?:[\s_-]*ai)?(?![\p{L}\p{N}])`.
