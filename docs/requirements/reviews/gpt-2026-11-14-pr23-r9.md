## Remaining findings

### 1. R9-01 — High — STRUCTURAL: a partial bot edit launders inherited authored credit

**Locations:** `xtask/src/attribution.rs:840–865` (`unverified`), `:899`
(whole-block exemption); ADR 0001 revision-9 provenance bullet and risk 12.
**Authority:** D-52 and D-61 in the [decisions log](../03-decisions-log.md).

The predicate establishes that a bot edit first contained a particular *whole
block*. It does not establish that the bot introduced each credit-bearing line.
Changing one unrelated bullet makes the whole block a new string, so unchanged
owner-authored credit becomes exempt. Checking `Bot` and the correct login does
not resolve this distinction.

**Concrete reproduction:** construct the following body versions, oldest first.
Use the real configured start/end markers, `H = "## Summary " + "by CodeRabbit"`,
and `C = footer("Generated", "with", "Claude")`:

```text
v0 User/owner:       Implement checks.
v1 Bot/coderabbitai: Implement checks. + blank line + START + H
                    + blank line + "* Add checks." + END
v2 User/owner:       v1 with line C inserted before "* Add checks."
v3 Bot/coderabbitai: v2 with "* Add tests." inserted before END
```

All components within a version are newline-separated. Encode these as the
GraphQL response shape accepted by `--body-history`: `data.repository.pullRequest`
with `author`, `body`, and `userContentEdits.nodes`; each node has ascending
`editedAt`, null `deletedAt`, full post-edit text in `diff`, and `editor` with
`__typename` and `login`. Supply nodes newest first. Use `v3` as the body file:

```bash
xtask attribution --base e64acc5cfb7343485e660436cfd9fb8da1a0e5dd \
  --head e64acc5cfb7343485e660436cfd9fb8da1a0e5dd \
  --body-file launder-body.txt --body-history launder-history.json
```

**Observed:** exit 0, attribution PASS, although C entered in the owner edit
and survived unchanged. **Control:** stop the same history/body at v2; exit 1,
including a finding on C. Appending an owner version restoring exact v3 also
passes. The already-submitted control where a bot changes only text *outside*
the unchanged user block still rejects; it misses this within-block variation.

This is a synthetic history replay demonstrating the verifier's decision, not
a claim that the reviewer induced CodeRabbit to preserve this line in a real
edit. Exploitation requires a genuine bot edit retaining the injected line;
the replay does not prove such an edit can be induced in the current bot.
Nevertheless, the claimed provenance guarantee assumes that every bot edit
regenerates or vouches for every byte inside the block. GitHub's history API
provides no such guarantee, and no compromised account or API defect is needed
for this history to be authentic.

**Suggested change and regression:** track provenance of the credit-bearing
content through block edits, retaining unverified status for authored lines a
bot merely preserves. Reject v3 above while accepting a clean bot introduction,
unmodified historical restoration, and owner edits outside a genuine block.
Alternatively, explicitly propose trusting the bot's whole-block adoption as
a policy limitation for owner consideration; the current ADR claims stronger
authorship evidence. Expand risk 12 to distinguish bot-originated text from
inherited or attacker-influenced text.

### 3. R9-03 — Medium — STRUCTURAL: ordinary namespace-valid RDF/XML escapes content detection

**Location:** `xtask/src/repository.rs:721–742` (`is_cim_rdf`).
**Authority:** D-56 and the revision-9 network-model content guarantee in
[ADR 0001](../../architecture/adr/0001-repo-layout-and-ci-gates.md).

The new sniffer requires one of four initial byte prefixes, including the
literal `<rdf:`. XML declarations are optional and namespace prefixes are
arbitrary; RDF/XML can use the RDF namespace as its default. The subsequent
namespace check is never reached for that ordinary document layout.

**Concrete reproduction:** add and stage `spikes/network-notes.txt` with this
synthetic RDF graph, without an XML declaration:

```xml
<RDF xmlns="http://www.w3.org/1999/02/22-rdf-syntax-ns#"
     xmlns:cim="http://iec.ch/TC57/2013/CIM-schema-cim16#">
  <cim:BaseVoltage>
    <cim:IdentifiedObject.name>400kV</cim:IdentifiedObject.name>
    <cim:BaseVoltage.nominalVoltage>400</cim:BaseVoltage.nominalVoltage>
  </cim:BaseVoltage>
</RDF>
```

Run `provenance` against that clone with unchanged revision-9 policy.
**Observed:** exit 0, provenance PASS. **Control:** prepend only
`<?xml version="1.0"?>`; exit 1, data file with CIM/RDF XML content outside
allowed sample paths. The namespace and graph are unchanged. An arbitrary
prefix such as `<r:RDF xmlns:r="…">` has the same initial-prefix problem.

**Suggested change and regression:** recognise XML root elements independent
of the optional declaration or chosen namespace prefix, retaining the bounded
namespace/content test. Test default and arbitrary prefixes without a
declaration through the complete provenance command, alongside the existing
Markdown/source/SVG controls. This is a parser/structure gap for an already
recognised format, rather than a request to identify every possible dataset.

## D-61 design and ADR limitation assessment

Restoring a historical, genuinely bot-originated block unchanged is reasonable
under D-61. Requiring the latest body editor to be the bot would incorrectly
reject harmless edits to surrounding authored prose. Exact block matching
also means an owner-only edit cannot introduce *new* credit by changing that
block or concatenating selected parts of different old blocks. Credit outside
the block, in titles, commits and added source lines remains scanned. This
historical restoration rule itself does not require a new owner decision.

However, “a bot edit first contained this whole string” is weaker than “the bot
wrote all of this content.” R9-01 demonstrates the difference. Once a tainted
block qualifies, historical matching preserves that mistaken exemption even
when an owner restores it later. The unacceptable part is the provenance
qualification, rather than allowing historical restoration after sound
qualification. Risk 12 correctly identifies GitHub/actor trust and the marker
boundary, but omits this ordinary inherited-content path. Trusting summaries
also cannot establish their factual accuracy or resistance to adversarial
instructions; D-61 permits the integration, not an inference that bot output
proves code authorship.

The revision-9 risk-11 clarification is accurate: standard library roots,
compiler/sysroot paths and the guard are trusted by location; hosted sudo and
same-user build scripts make them unsuitable as an isolation boundary. That
is the existing risk-5 job-tampering limit. Read-only credentials, separate
trusted jobs, protected workflows and exact-head review are appropriate M0
controls. The closed adapter list, compiler forbid, library allowlist and
feature/target/doctest checks remain useful within that boundary.

The documented host-configuration and multi-feature limits, static-link/search
path caveats, finite attribution vocabulary, and lexical workflow lint are
reasonable M0 bounds. Data signatures likewise cannot identify the meaning or
licence of every arbitrary file. Those limits do not justify missing a standard
XML serialisation of the explicitly supported RDF format or omitting actual
gate display names from the claimed reservation rule. M1's D-65 isolation
evidence remains a separate activation requirement under NFR-12.
