## Remaining findings

### 1. R14-01 — High — CORE: deleting historical provenance records hides restricted intermediate datasets

**Locations:** `xtask/src/repository.rs:1235`, `:1312`, `:1431`, `:1451`;
`xtask/tests/policy.rs:1008`; ADR 0001 revision-14 History paragraph.
**Authority:** D-56, NFR-12. **Disposition:** must fix before bootstrap attestation.

`HistoryScan` receives only records parsed from the final checkout. Historical
manifest/source-table blobs are scanned for secrets and format signatures, but
are never parsed for their provenance declarations. Deleting a research-only
record along with its dataset therefore removes the restriction from the range
scan. The submitted research-data test leaves the declaration in the final tree,
which does not cover this case.

**Concrete test:** start from a passing repository with an ordinary open-commercial
manifest and save `BASE`. In one commit add a second `manifest.toml` declaring
`review-prices.csv` as `research-only`, together with the synthetic two-row file
`spikes/data/samples/review-prices.csv`. In the next commit remove both added files.
Do not alter the trusted policy. Run:

```bash
"$XTASK" --repo "$SCRATCH" --policy "$TRUSTED" all
"$XTASK" --repo "$SCRATCH" --policy "$TRUSTED" provenance --base "$BASE" --head HEAD
```

**Observed:** the live intermediate checkout rejects as research-only, but both
commands above pass at the final head. This was replayed in a full disposable
clone of the candidate. A minimal-repository control that retains the restricted
record at head rejects the same historical dataset.

This also exceeds the explicitly accepted history file-type limitation. A separate
minimal probe commits a recognized `PAR1`-framed synthetic fixture under
`spikes/data/samples/safe.parquet` while the manifest marks it research-only. The
next commit deletes that sample and changes its declaration to open-commercial.
The range scan passes even though it recognizes the historical Parquet signature;
it applies the later permission to the earlier restricted version. That live
intermediate checkout rejects. Synthetic fixture bytes establish detection scope,
not real Parquet data validity; no restricted dataset was used.

**Suggested change/test:** validate historical provenance records and apply the
restrictions present when a dataset version was committed, including applicable
base-tree declarations. A conservative union of restricted declarations can also
fail closed, with genuinely cleared exceptions reviewed separately. Add deleted
manifest/source-table and later-reclassification tests, including recognized
formats in permitted sample paths. Keep the approved extension/binary history
limitation separate. Correct the ADR's “research-only records” claim after fixing
this behavior; documenting the bypass alone does not meet D-56.

### 2. R14-02 — High — CORE: a YAML block scalar hides kubeconfig client private keys

**Locations:** `xtask/policy/secret-rules.toml:181`, `:184`;
`xtask/src/secrets.rs:600`. **Authority:** D-56, NFR-12.
**Disposition:** must fix before bootstrap attestation.

The client-key-data rule requires base64 bytes on the same line as the colon.
Valid YAML can put the same field value in a literal block scalar. The new
kubeconfig-user rule does not include that key, and the generic assignment rules
do not parse the scalar, so this widely used credential type remains committable.

**Concrete test:** generate an unregistered RSA private key with
`openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048`, base64-encode the PEM,
and place the resulting string at the indented value below in a complete
kubeconfig stored as `docs/review-kube.yaml`:

```yaml
apiVersion: v1
kind: Config
users:
- name: admin
  user:
    client-key-data: |
      BASE64_OF_THE_GENERATED_PEM
```

Track that file and run the trusted `all` command above. **Observed:** exit **0**.
The actual fixture uses the complete generated base64 string, not the placeholder
shown here. Parsing with the repository's `yaml-rust2` dependency recovers the
scalar; base64 decoding yields the original PEM byte for byte, and
`openssl pkey -check -noout` reports a valid key. Removing the `|` and placing that
same value after the colon rejects with `local-kubeconfig-client-key`.

**Suggested change/test:** recognize supported YAML scalar forms for credential
fields, or conservatively reject a client-key-data declaration that cannot be
safely classified. Cover literal/folded and quoted scalars, CRLF and JSON/YAML
serializations with a generated-key round-trip control. Do not rely on optional
generic base64 decoding: this is a named credential field whose serialization is
valid, not an arbitrary encoded secret hidden in prose.

### 3. R14-03 — High — CORE: the netrc/pgpass rules omit supported credential-record syntax

**Locations:** `xtask/policy/secret-rules.toml:201`, `:207`.
**Authority:** D-56, NFR-12. **Disposition:** must fix before bootstrap attestation.

The pgpass rule requires a whitespace-free password and the netrc rule requires a
login in either accepted ordering. Those requirements are stricter than the
actual credential formats. At a permitted text filename, neither path rules nor
the generic assignment rule rescues these omissions.

**Concrete pgpass test:** concatenate the five fields
`postgres.prod.internal`, `5432`, `energy_grid`, `grid_user`, and
`my database password` with ASCII colons; append LF. Track this single record as
`notes.txt` in a minimal repository with a valid manifest. **Observed:** trusted
`provenance` exits **0**. Replacing only the password with
`myDatabasePassword123!` rejects with `local-pgpass-credentials`.

Independently exercised libpq 17.11 using an equivalent localhost record, a
mode-0600 temporary password file and `PQconnectStart`/`PQpass`: libpq returns the
complete password including both internal spaces. No database or server was
started. The whitespace-bearing value is a usable database password, not an
invalid synthetic record.

**Concrete netrc test:** build a record from `machine energy-api.example.com`
plus one ASCII space plus `password SecretPassword123!`, then LF; track it as
`notes.txt`. The standard-library netrc parser accepts it and returns the supplied
password with an empty login/account. Trusted `provenance` exits **0**. The
original record including `login service-user` rejects. Missing login is supported
record syntax; the file does not need an assignment operator to hold a password.

**Suggested change/test:** handle the formats' token/escaping rules and optional
fields, or conservatively detect their record structures without demanding these
extra restrictions. Add password-internal-whitespace, quoted netrc tokens,
optional-login and escaped pgpass-field cases with real parser controls. Preserve
ordinary prose and host/port examples that contain no credential record.

### 5. R14-05 — Low — PERIPHERAL: ADR overstates local-rule uniformity and omits decoder limits

**Locations:** ADR 0001 revision-14 Credential formats paragraph;
`xtask/policy/secret-rules.toml:147`–`:169`; revision-13 evaluator description.
**Authority:** accurate M0 enforcement documentation.
**Disposition:** bounded documentation follow-up; no separate bootstrap blocker.

“No local rule has a length cap or placeholder heuristic” is too broad: inherited
local SendGrid/Groq/xAI/Azure rules retain letters-only/digits-only allowlists.
The newly added credential-format rules avoid those heuristics, which is the
narrower accurate statement. The ADR should also explicitly state that the port
omits optional base64/hex secret decoding and recursive archive inspection, and
that upstream entropy/stopword/same-line allowlists remain heuristic. For example,
the submitted same-line mount-marker AWS control intentionally passes; fixing the
following-line location defect does not remove legitimate upstream exclusions.
The exact inherited rule definitions and that passing control are concrete
evidence for this wording correction. Historical provenance behavior in R14-01
is a CORE repair, not something this documentation follow-up accepts.

## Enforcement, limitations and one-time bootstrap assessment

1. **Trusted checks and owner approval.** Current-main policy loading,
   fail-closed bootstrap loading, reserved check names, exact aggregator steps,
   protected paths and exact-head owner approval remain a reasonable M0 design.
   Relevant workflow/approval negative tests pass. No new bypass of what main's
   checks execute, owner approval or review currentness was found in this revision.
   Trusted pull-request-target jobs inspect PR Git objects as data and do not
   execute PR code. Shared-account role evidence is attestation, not provider
   identity proof. Branch protection and D-74 account activation remain operational
   prerequisites. The authorized use of the configured owner account for this
   report does not prove that an owner-authored policy PR can satisfy D-74's
   separate approver gate.

2. **Unsafe and native runtimes.** Compiler-forbid/wrapper, feature, doctest and
   linker regressions pass, as does the complete local build gate. ADR residual
   risks 5, 7, 8, 9 and 11 continue to describe same-user build-script/proc-macro
   tampering, trusted library roots, static linking and host/feature coverage.
   Those bounded, reviewed limits are acceptable for M0; this is not a sandbox
   against arbitrary malicious build-time code. M1 runner-isolation evidence must
   still precede heavy B1 execution. No new unsafe or Python/Julia-linking bypass
   was established in the reviewed changes.

3. **Secrets and data.** Whole-block, per-view exemptions close the original
   PuTTY substitution; trimming consumed line endings closes R13-02; vendored
   rules remain pinned and fail closed on unsupported schema/regexes. The history
   enumerator reaches add/delete, replacement and side-branch commits. These are
   useful controls, but they cannot establish licence truth or exhaustively
   classify arbitrary source-embedded data. The reproduced widely used credential
   and declared research-only history gaps above are CORE, not rare-provider
   dictionary omissions.

4. **History-scan scope.** Excluding content objects already reachable from the
   chosen base makes this an incremental PR/push scan, not D-58's whole-history,
   all-branches publication audit. Skipping duplicate checkout versions is
   reasonable. The owner-accepted historical file-type allowlist and
   binary/undecodable-class exclusions can be an M0 baseline limitation; they
   knowingly leave unknown historical file types to review and the later
   publication audit. They do not authorize ignoring historical licence records
   or applying a later open-commercial label to an earlier restricted version.
   The addendum's claimed research-only history coverage is consequently
   inaccurate until R14-01 is repaired. Current-checkout declarations alone are
   insufficient even when the historical format is recognized.

**Verdict: must-fix list R14-01, R14-02, R14-03.** This exact head is unsuitable as
the one-time checks bootstrap on main. Repair the historical-provenance and
credential-format counterexamples, obtain an exact-head independent re-review and
current adversarial review/triage, then perform the manual first-B0 attestation
checklist. R14-04 and R14-05 can follow separately; rare upstream formats and
additional attribution spellings need not independently prevent an M0 seed.
PR #23, bootstrap attestation, owner decisions and repository settings were not
modified.
