## Findings requiring correction

### 1. R3-01 — High: a tool-qualified lint satisfies the required Rust forbid

**Locations:** `xtask/src/rust_policy.rs:212` (`forbids_unsafe`),
`xtask/src/rust_policy.rs:85` (`names_unsafe`). **Related finding:** F4.

The checker searches all tokens in a `forbid(...)` for the identifier
`unsafe_code`. It does not require that the lint itself be the unqualified Rust
lint. Consequently `#![forbid(clippy::unsafe_code)]` is accepted as the boundary,
although it does not forbid Rust's `unsafe_code` lint.

**Reproduction:** replace only the disposable engine crate's root with its normal
crate documentation followed by this source. The function documentation and SAFETY
comment keep the normal workspace clippy configuration satisfied:

```rust
#![allow(unknown_lints)]
#![forbid(clippy::unsafe_code)]

macro_rules! lowered {
    ($lint:ident) => {
        /// Value.
        #[allow($lint)]
        pub fn value() -> i32 {
            let n = 1;
            let p = &n as *const i32;
            // SAFETY: p refers to n, which is alive and aligned.
            unsafe { *p }
        }
    };
}
lowered!(unsafe_code);
```

The unchanged built `target/debug/xtask policy` reports **PASS in all five
categories**. `cargo clippy -p egs-engine --locked -- -D warnings` exits **0**.
A separate `rustc --edition=2024 --crate-type=lib --emit=metadata -Dunsafe_code
-Dwarnings` probe also exits **0**. Replacing the qualified lint with the real
`#![forbid(unsafe_code)]` fails with E0453 and an unsafe-block diagnostic.

**Regression assessment:** `f4_macro_parameter_opt_out_is_rejected` genuinely
reproduces the old macro bypass, proves `deny` accepts it, and proves the real
`forbid` rejects it. It never supplies an ineffective qualified lint to the
checker, so the claimed compiler boundary can still be removed.

**Suggested change:** parse lint arguments structurally and require a direct,
unqualified `unsafe_code` lint in an unconditional inner `forbid` attribute.
Add this input as a checker rejection and retain the compiler positive/negative
controls. Do not treat arbitrary occurrences of a lint identifier as enforcement.

### 2. R3-02 — High: Cargo-selected targets without `.rs` escape source checks

**Location:** `xtask/src/rust_policy.rs:348`. **Related findings:** F4 and F7.

`package_targets` now identifies custom target/build-script paths, but the scan
loop still skips every tracked filename not ending in `.rs`. Cargo does not
require that extension for an explicit target or a build script.

**Reproduction:** in a scratch package use this valid manifest fragment:

```toml
[package]
name = "engine"
version = "0.0.0"
build = "native"

[lib]
path = "engine"
```

Track `crates/engine/engine` containing the macro and unsafe operation from
R3-01, with neither of its crate-level attributes. Track
`crates/engine/native` containing:

```rust
fn main() { println!("cargo:rustc-link-lib=python3.12"); }
```

`rust_policy::check_sources` returns **[]**: neither the missing forbid nor
the direct Python runtime link is reported. `cargo metadata --no-deps
--format-version=1` confirms those exact files as the library and `custom-build`
targets. The library source compiles successfully with `rustc -Dunsafe_code
-Dwarnings` because its macro lowers `deny`. No Python library was loaded or linked.

**Regression assessment:** `f4_all_crate_roots_are_found` uses `.rs` for every
explicit target; `f7_custom_build_script_and_conditional_link_are_rejected` uses
`native.rs`. Both exercise real discovery, but their inputs all survive the
extension filter. Their original round-2 inputs are corrected; the general
Cargo-selected-target guarantee is not.

**Suggested change:** scan the union of tracked Rust files and every selected
target/build-script path, regardless of suffix; require those target files to
exist and be tracked. Apply the root forbid and build-script rules to that union.
Add extensionless and alternative-extension targets as real Cargo fixtures.

### 3. R3-03 — High: the review-directory exemption permits unreviewed code changes

**Location:** `xtask/src/review_gates.rs:477` (`still_current`).
**Related finding:** F6/currentness.

Every changed path under `docs/requirements/reviews/` is exempt from currentness,
including executable source. The rule does not establish that a change is evidence
only. This can keep both approval and triage current after production behavior changes.

**Reproduction with real Git and Cargo:** create a PR commit R with an engine
library and a tracked payload:

```rust
// crates/engine/src/lib.rs
#![forbid(unsafe_code)]
include!("../../../docs/requirements/reviews/payload.rs");
```

```rust
// docs/requirements/reviews/payload.rs, at R
pub fn price() -> u8 { 1 }
```

Put an approving Anthropic/OpenAI code-review report, a valid Google adversarial
report and complete OpenAI triage for R on the separate main branch. Commit H on
the PR branch changing **only** `payload.rs`, replacing the return value with
`99`. The evidence remains unchanged and still names R.

`still_current(main, R, H)` returns **true** and the full
`independent_review(ctx, main, H)` returns **[]**. `cargo check --offline` on H
exits **0**, confirming the changed payload is compiled production source.
There is no forged SHA, changed report or file-mode trick. The source can also be
included from a file named `.md`, so an extension-only exception is insufficient.

**Regression assessment:** `f6_mode_change_invalidates_review` correctly rejects
the original chmod-only input and accepts a harmless note plus a main merge.
It never checks that a supposedly evidence-only file can affect compiled code.

**Suggested change:** remove the blanket directory exemption. Require exact-head
review/triage or narrowly verified evidence-only successors with an enforced rule
excluding executable inputs/references. A minimal safe M0 approach is strict
currentness for all PR tree changes; reports already land separately on main.
Add this full-Git reproduction and preserve legitimate main-evidence merge controls.

### 4. R3-04 — Medium: CODEOWNERS matching omits the `?` wildcard

**Locations:** `xtask/src/repository.rs:844` and `xtask/src/util.rs:233`.
**Related finding:** F8.

GitHub CODEOWNERS uses gitignore-style `?` wildcard matching. The shared matcher
implements `*`/`**`, but treats `?` literally. A later valid override can therefore
take a protected file away from the owner while the check reports coverage.

**Reproduction:** with protected `/xtask/`, tracked `xtask/src/lib.rs` and owner
`Owner`, pass these rules to `check_codeowners_paths`:

```text
/xtask/ @Owner
/xtask/sr?/lib.rs @someone
```

The checker returns **[]**. Independently putting `/xtask/sr?/lib.rs` in a scratch
`.gitignore` and running `git check-ignore --no-index xtask/src/lib.rs` returns
the path with exit **0**, confirming the wildcard matches under the underlying
pattern rules. GitHub's last-match rule makes `@someone` the effective owner.

**Regression assessment:** the narrower literal override, wildcard `*.rs`, inline
comment and invalid-line inputs from F8 are now rejected. The new matching tests
exercise `*` and `**`, but never `?`.

**Suggested change:** use a mature gitignore-compatible matcher with CODEOWNERS'
documented syntax exceptions, or implement and test the complete supported syntax.
If unsupported syntax cannot be interpreted faithfully, fail closed on that rule.
Add this question-mark override and a nonmatching control.

## Trusted execution, attestation and owner flow

The **submitted** `trusted-gates.yml` has the appropriate execution boundary.
Its `pull_request_target` jobs check out the base context with persisted credentials
disabled, fetch current main and the PR ref, verify the numeric PR number and full
head SHA, compare the fetched head with the event, and then check out **main**.
They build only main's locked xtask. The PR head is never checked out or passed to
Cargo; the checker reads it through `rev-list`, `merge-base`, `diff --name-only
--no-ext-diff`, `ls-tree` and raw `git show SHA:path` calls. These paths do not invoke
PR build scripts, local actions, textconv or external diff drivers.

Both jobs have read-only permissions. Only the approval step receives `GH_TOKEN`,
from `github.token`, to read reviews. No custom secret, write token, cache or PR
artifact is used. Event number/SHA expressions enter shell variables through `env`,
not script interpolation; title/body/branch strings are not interpolated into these
scripts. The approval API path uses separately validated repository/number fields.
No PR-code execution or shell injection was found in this exact workflow/checker
chain. Static workflow policy is defense in depth, not a proof for arbitrary future
shell commands; protected-path owner review remains essential.

The loader now reads `docs/process/ci-bootstrap.toml` from **fetched main**, checks
an exact full `seed_sha`, and uses the PR seed only on that match when main lacks
xtask. Tests exercise the actual shell script with a real bare origin and verify
the resulting worktree's SHA. They do not merely inspect warning text. A later head
does not inherit the authorization. Do not update the attestation to a corrected
head until that head has fresh review and adversarial triage.

However, the loader and ordinary CI jobs are themselves PR-defined until merged.
The new trusted workflow is not on current main, so there is no trusted-gates run
for this seed yet. This initial exception genuinely relies on the coordinator's
manual exact-head inspection. Attestation is authorization to execute the reviewed
seed; it cannot compensate for R3-01–R3-04 in that seed's own checker.

Read-only GitHub inspection confirmed PR #23 remains authored by
`Tobechukwu-Njoku`. D-74 makes future exact-head owner approval workable **once a
separate machine account actually opens the PR**. The placeholder `egs-bot` is only
used in diagnostics; it neither provisions an account nor changes an existing PR's
author. Attesting this head does not make self-approval possible. To use the D-74
approval procedure for this change, publish the reviewed head from the machine
account, obtain the owner's review on that exact head, and preserve the separate
bootstrap coordinator check while trusted-gates is absent from main. The seed can
remain the same SHA when only PR ownership changes.

The documented re-run approach is reasonable for an unchanged head: after an owner
approval or reports/triage land on main, re-run the trusted run. It fetches current
main and queries current reviews, instead of relying on its old evidence snapshot.
A new PR head must use its new event/run and fresh exact-head owner approval.
This review did not submit an approval, re-run CI or mutate repository settings.

The observed policy-job failures in Actions run `43478139289` explicitly report
missing main policy and no matching bootstrap attestation, as intended. Its Linux
and macOS test jobs were cancelled during nextest; those cancellations are not
additional demonstrated code defects. Local verification supplies the baseline
above, but the coordinator still needs completed applicable CI before merging.

**Bootstrap decision:** do **not** attest `b2173e28f8f232366ffe6a27d5e787fd2adfc39c`
as a merge-ready trusted policy seed. Its trusted execution mechanism is materially
