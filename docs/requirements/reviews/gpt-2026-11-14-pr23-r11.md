## Remaining defects

### 1. R11-01 — High — CORE: ordinary UTF-16/32 text hides recognized secret signatures

**Locations at reviewed head:** `xtask/src/repository.rs:1317` reads every tracked
file, `:1326` decodes it only with `String::from_utf8_lossy`, and `:1340` passes
that undecoded/NUL-interleaved text to `scan_secrets` (`:661`).
**Authority:** D-56, NFR-12, ADR 0001's secrets gate.
**Disposition:** must fix before bootstrap attestation.

The data sniffer understands UTF-16/32 for XML, but the secret scanner does not
decode those same ordinary text encodings. A known token signature written as a
UTF-16 text file contains NULs between its ASCII characters. Lossy UTF-8 conversion
leaves those NULs in place, so neither the prefix nor tail regex logic matches.
The generic `.txt` path is not a data extension and has no archive/model signature.
No trusted policy, workflow, exemption or provenance record has to change.

**Concrete test:** in a disposable checkout of the reviewed head, use a throwaway
directory outside the checkout for `SCRATCH`, the compiled binary for `XTASK`,
and an unchanged checkout of the reviewed head for `TRUSTED`:

```bash
printf 'service_token=ghp_%036d\n' 0 > "$SCRATCH/plain.txt"
iconv -f UTF-8 -t UTF-16 "$SCRATCH/plain.txt" > docs/connection-notes.txt
git add -f docs/connection-notes.txt
"$XTASK" --repo "$PWD" --policy "$TRUSTED" provenance
"$XTASK" --repo "$PWD" --policy "$TRUSTED" all
```

**Observed:** both commands exit **0**. The BOM-bearing UTF-16 file is 112 bytes;
its first bytes are `ff fe 73 00 65 00 72 00 76 00`. The full `all` command passes
unsafe scope, manifests, workflows, Python, CODEOWNERS, provenance and every docs
category. Independently committed the synthetic file in the disposable clone and
repeated provenance: still exit **0**. The same text encoded as UTF-16LE, UTF-16BE,
UTF-32LE and UTF-32BE without a BOM also gives provenance exit **0**.

**Control:** copy `plain.txt` directly onto the same tracked path, changing only
the encoding. Provenance exits **1** with
`docs/connection-notes.txt:1: possible GitHub token committed`.
The sample is a synthetic, non-working signature, not a live credential. The
encoding defect applies equally to a real token satisfying that existing rule;
it is not a request to recognize a new provider or decrypt arbitrary blobs.

**Suggested change and regression:** scan properly decoded UTF-16/32 text as well
as the existing byte/UTF-8 view, or explicitly fail closed on unsupported encoded
text. Do not merely reuse the XML sniffer's 64 KiB head for secrets: preserve
whole-file coverage and exact-line exemption semantics. Add the exact CLI
UTF-8/UTF-16 control pair, both endiannesses and BOM variants, UTF-32, a recognized
signature after 64 KiB, and non-secret text controls. A temporary documented
rejection of these text encodings is sufficient; no Unicode language detector or
general decoder framework is required. An ADR caveat alone does not resolve this
CORE false negative.

## Overall enforcement and M0 limitation assessment

1. **Trusted execution and approval are substantially sound within their stated
   boundary.** Current-main policy supplies the checker, protected policy/action/
   workflow paths require exact-head owner approval, reserved IDs and published
   names prevent ordinary check-name substitution, and aggregator steps are
   compared with trusted main. Trusted review/approval jobs read PR Git objects
   without executing its code. Independent-review evidence comes from main,
   compares PR-owned blobs and modes, and requires adversarial triage. The full
   regression suite passes; this review found no new counterexample in those
   execution/approval controls. A self-reported role header is trusted evidence
   only because its report lands through main's review process, not cryptographic
   proof of a reviewer identity.
2. **Compilation and native-link enforcement are useful, not a sandbox.** Root
   and compiler forbids, manifest checks, compiled generated code, default/no-
   default/all/single-feature builds, production and test targets, doctests,
   trusted adapter identities and resolved native-library allowlists form a
   materially useful M0 boundary. ADR risks 5, 7–11 accurately retain same-user
   build-script/proc-macro tampering, hosted-runner sudo/location trust, static
   bundling, unsupported targets and uncovered feature combinations. Build-time
   code can tamper with its own job; read-only tokens do not prevent that. These
   are acceptable explicitly reviewed M0 limitations for the first-party stub
   workspace, with separate trusted jobs and no privileged target runners, not
   a claim that malicious PR build code is safely isolated.
3. **Content policy is layered and necessarily bounded.** Provenance records,
   sample allowlists, signatures, model extensions and secret patterns catch many
   accidental violations. They cannot establish the truth of a declared licence,
   exhaust every data format or identify all arbitrarily disguised credentials.
   The 64 KiB XML/model sniff bound and known-source-extension/shebang scope are
   accurately described in revision 11. XML allowlisting remains empty; DTDs do
   not trigger network/entity resolution. Renaming a solver solution is not
   promised to have content detection. The ordinary encoded-text R11-01 is an
   actionable missing boundary, not one of ADR 0001's documented runner/feature
   risks; the secrets gate cannot yet be described as reliably enforcing its
   existing recognized patterns across committed text.
4. **The revised D-61 size limitation is correctly closed for the original
   input.** Large unknown diffs no longer manufacture bot authorship, while
   known historical bot text can be restored. GitHub history/actor trust and the
   exact-marker boundary remain explicit risk 12. Bot summaries are not proof
   of code authorship. Finite attribution dictionaries and the deliberate
   R11-02 trade-off remain PERIPHERAL, rather than new structural blockers.
5. **Bootstrap and deployment remain explicit owner/coordinator operations.**
   Main has no trusted checker yet, so this PR cannot bootstrap its own
   independence merely by going green. Before eventual acceptance, land current
   review/triage evidence, attest only a reviewed exact seed SHA on main, rerun
   checks, and verify required checks, their trusted workflow origin, repository
   merge-message settings and the final merge payload. The D-74 machine account
   must be established for subsequent policy PRs: an owner-authored policy PR
   cannot satisfy its own approval gate. The requested temporary configured-
   account allowance for this report does not remove that deployment condition.
