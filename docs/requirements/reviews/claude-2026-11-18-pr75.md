## Findings

1. **[P1] With more than one merge base, a docs-only classification can merge
   non-review changes.** `independent_review` runs `git merge-base main head`, which
   returns one merge base, and classifies the diff from that commit
   (`review_gates.rs:650-653`). When main contains merge commits (it does: `3cf6a3f`
   merged PR #23 with a merge commit), a branch can be built with two merge bases, B1
   and B2. Its tree equals B1 plus a report. The diff from B1 then shows only the
   report, and the D-77 path accepts it. GitHub's merge, however, uses the virtual base
   `merge(B1, B2)`, so merging reverts everything the B2 side introduced.

   The `changed.is_empty()` early return (`review_gates.rs:654-656`) has the same
   cause. If the head tree equals B1 exactly, it passes with no evidence at all.

   Before this PR, `changed_paths(main, head)` would have shown the reverted paths, so
   this weakness is introduced by the GPT finding 1 fix. `policy_approval` already
   measured changes from a single merge base on main (`review_gates.rs:890-893` at
   head), so for protected paths both human gates miss the revert. The change set is
   limited to reverting previously merged work, but that includes earlier gate
   hardening.

   Reproduction, using the gate's own Git commands in a scratch repository:

   ```sh
   git init -q -b main r && cd r && git config user.email t@t && git config user.name t
   mkdir -p docs/requirements/reviews src
   echo safe > src/gate.rs; echo base > README.md; git add -A; git commit -qm base
   git checkout -qb feature; echo hardened > src/gate.rs; git commit -qam harden; P2=$(git rev-parse HEAD)
   git checkout -q main; echo m > m.txt; git add m.txt; git commit -qm work; P1=$(git rev-parse HEAD)
   git merge -q --no-ff feature -m merge; MAIN=$(git rev-parse HEAD)
   git checkout -qb evil $P1; git merge -q -s ours $P2 -m "merge (ours)"
   echo report > docs/requirements/reviews/r.md; git add -A; git commit -qm report
   git merge-base --all $MAIN evil                 # two bases: P1 and P2
   git diff --name-only $(git merge-base $MAIN evil) evil   # docs/requirements/reviews/r.md only
   git checkout -qb result $MAIN; git merge -q --no-edit evil; cat src/gate.rs   # "safe": hardening reverted
   ```

   Fix: classify the change the merge actually makes. Diff `main` against
   `git merge-tree --write-tree main head`, and fail closed on conflicts. A smaller fix
   is to run `git merge-base --all` and fall through to the ordinary gate unless there
   is exactly one merge base. Apply the same fix to the empty-diff early return and to
   `policy_approval`. Add a regression test with this criss-cross shape. The test must
   expect a non-empty result both for a report-plus-revert head and for a revert-only
   head.

2. **[P2] PR #75 can never pass `policy-approval` as opened.** The PR author is the
   policy owner (`Tobechukwu-Njoku`), and the PR changes protected paths
   (`xtask/policy/review.toml`, `xtask/src/review_gates.rs`, `xtask/tests/gates.rs`).
   On the head, `policy-approval` fails with "protected policy paths changed in a pull
   request opened by the policy owner". GitHub does not let authors approve their own
   PRs, so under D-74 this PR cannot merge through the gates. The change must be
   re-opened from the agent account (`automated-machines`) for the owner to approve the
   exact head.

3. **[P2] The policy widening and the rewritten D-77 text are not sourced from the
   owner.**
   - `b39bfcf` adds `google` to the `code generation` author vendors of the
     OpenAI-reviewer pairing (`xtask/policy/review.toml:17`). Team rule 2 (D-51) says
     Gemini output is checked by GPT, but no decision entry covers this change to the
     trusted matrix. GPT's own report said it "needs an explicitly authorized
     alignment".
   - `3829126` rewrites the D-77 row, which first appeared in `c938d79`, to add
     merge-base semantics, exact-SHA, verdict, triage and symlink/gitlink rules. The
     row is still attributed "2026-11-17 | Owner".

   AGENTS.md rule 1 requires decision text to come from owner answers. Either:
   - get the owner to confirm the expanded D-77 wording and the matrix change (via
     `record-decision`, as a D-77 amendment or a new D-entry), or
   - restore the owner's original D-77 wording and move the implementation detail to
     the requirements or the gate's documentation.

   The owner's exact-head approval under finding 2 would cover the `review.toml` change
   as a policy edit, but not the wording of the decisions log. A stray blank line was
   also appended to the end of the decisions log.

4. **[P3] Repeated header fields are resolved silently.** `parse_header` keeps the
   last valid `Reviewed head` and ignores later invalid ones. It also keeps the last
   `Verdict` (`review_gates.rs:96-120`). A report with a valid `Reviewed head` line
   followed by `- Reviewed head: garbage` therefore passes direct validation. D-77
   promises validated full-SHA references. Reject a report that repeats `Reviewed head`
   or `Verdict` within the parsed header, or that has any unparsable `Reviewed head`
   line, and add a test for it.

## Other observations (no change requested)

- New review documents may have mode `100755`. Git treats them as regular files, as
  the tests do, and changing the mode of existing evidence is still rejected. Reject
  the executable bit if "regular" in D-77 should mean `100644` only.
- STATUS-only PRs pass with no report, and STATUS content is unrestricted. This
  matches D-77's allowed set; narrowing it would need an owner decision. GPT's report
  records this too.
- By design, a merged review-evidence PR becomes trusted evidence for other PRs with
  no independent check of its own; header roles are self-declared. That is the trade-off
  D-77 accepts. Finding 1 matters because it lets a non-review change ride on that
  trust.
- The stricter verdict parser fails closed for unbolded verdicts with trailing words
  (`approve with nits` is no longer approving). No report on main is affected.
