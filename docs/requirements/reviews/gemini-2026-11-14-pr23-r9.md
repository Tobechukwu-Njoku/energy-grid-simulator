## 2. Verification of CI Quality Checks & Architecture Scope

A comprehensive robustness re-check of PR #23 was conducted at head `e64acc5cfb7343485e660436cfd9fb8da1a0e5dd`:

1. **Compiler-Enforced Build Gate (`cargo xtask build-gate`) & Unsafe Boundary (ADR 0001, NFR-10):**
   - Executed full `cargo xtask build-gate` across the workspace across default features, all features, single features, production targets, test targets, and doctests.
   - Verified that all non-adapter crates receive command-line `-F unsafe_code` with lint caps scrubbed.
   - Verified that the linker guard resolves libraries and frameworks through search roots and checks requested libraries against `link_libraries` in `gates.toml`.
   - Verified that `scrub_loader_env()` removes dynamic loader variables before invoking compiler and linker processes.
   - Gate passed cleanly with `PASS: build-gate: compiler-enforced unsafe scope and native runtimes`.
2. **CI Workflow Graph, Aggregator Gate & Spoofed Gate Detection (ADR 0001, NFR-12, D-74):**
   - Verified that `Policy::protected_gates()` aggregates job IDs and aggregator IDs from `policy.graphs` and `required_checks`.
   - However, `protected_gates()` records only the raw YAML job IDs (`rust-linux`, `licences`, `attribution`, `docs`, `policy`, `provenance`). It omits the published check-run display names declared via `name:` in `.github/workflows/ci.yml`. An untrusted workflow can declare a job with `name: "rust (fmt, clippy, nextest incl. xtask and hook tests) linux"`, spoofing the check run without detection (ADV23R9-01).
   - Furthermore, in `check_graph()`, aggregator validation only checks job ID lookup `jobs.iter().find(|(name, _)| name == aggregator)`. It does not require the aggregator job's published `name:` property to match `merge-gates`. In addition, `check_graph` verifies `needs` and `if: always()`, but never inspects whether the aggregator job steps actually evaluate the status of the prerequisite jobs, allowing a PR to replace aggregator steps with `run: echo "bypassed"` to force a green merge check when gates fail (ADV23R9-02).
3. **Workflow Environment Hardening & Dynamic Execution Variables (NFR-12):**
   - Verified that `is_loader_env()` catches `LD_*` and `DYLD_*` variables.
   - However, `check_env()` strictly gates variables where `is_loader_env()` or `is_toolchain_env()` returns true. It fails to restrict shell execution variables such as `BASH_ENV` and `ENV`, which execute arbitrary scripts before every workflow step, as well as language runtime path variables (`PYTHONPATH`, `NODE_OPTIONS`, `PERL5LIB`) (ADV23R9-03).
4. **CodeRabbit PR-Body Exemption Provenance (D-61, R8-01):**
   - PR #23 revision 9 introduced GraphQL edit history verification (`fetch_body_history`, `unverified`).
   - However, `parse_body_history()` parses `userContentEdits` from GitHub GraphQL. GitHub's `userContentEdits` records only edits to user content, omitting the initial PR creation text.
   - In `unverified()`, `before_without = index == 0 || ...` assumes that an edit at `index == 0` had no prior version. If an author writes a bot block in the initial PR creation, and CodeRabbit makes the first edit to the PR body, the bot edit is placed at `index == 0`, causing `unverified()` to falsely conclude that CodeRabbit introduced the block and exempting user-authored attribution text (ADV23R9-04).
5. **Provenance and Dataset Gate (D-56):**
   - Verified that `data_extensions` covers standard archive formats and power grid CIM/CGMES formats (`.rdf`, `.pfd`, `.dz`).
   - However, `data_extensions` omits standard mathematical optimization and solver model dataset formats (`.mps`, `.lp`, `.qps`) used by the workspace solver adapters (`egs-solver-highs`, `egs-solver-gurobi`, `egs-solver-xpress`). Committing unapproved `.mps` or `.lp` problem instances outside sample paths passes `cargo xtask provenance` with exit code 0 (ADV23R9-05).
6. **Attribution Pattern Coverage (D-52):**
   - Verified pattern coverage for trailers and footers. Four false-negative gaps remain: omission of major coding assistants `JetBrains AI` (`jetbrains`), `Blackbox AI` (`blackbox`), and `Sweep AI` (`sweep`) from `VENDOR` and `MODEL` (ADV23R9-06); omission of vendor email domains `jetbrains.com`, `blackbox.ai`, `sweep.dev` (ADV23R9-07); omission of attribution verbs `optimized`, `optimised`, `polished`, `completed` from `ATTRIBUTE` (ADV23R9-08); and omission of assistance nouns `recommendations`, `coaching`, `prompts`, `instructions` from `HELP` (ADV23R9-09).

### ADV23R9-01: Published Check-Run Display Names (`name:` Property) Omitted from Protected Gate Check Detection

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** CI Review Gates / Spoofed Check Detection (F1, ADV23R8-01, D-74)
- **File & Line Citation:** [xtask/src/workflows.rs:152-179](../../../xtask/src/workflows.rs#L152-L179), [xtask/src/review_gates.rs:644-658](../../../xtask/src/review_gates.rs#L644-L658), [xtask/policy/gates.toml:46-65](../../../xtask/policy/gates.toml#L46-L65)
- **Description:**  
  Decision D-74 and finding F1 prohibit pull-request workflows from defining jobs whose status checks spoof required gate checks.  
  In `.github/workflows/ci.yml`, gate jobs define user-facing `name:` attributes:
  - `name: rust (fmt, clippy, nextest incl. xtask and hook tests) linux`
  - `name: licences and advisories (cargo-deny, trusted deny.toml)`
  - `name: attribution policy (D-52)`
  - `name: provenance, secrets and raw data (D-56)`
  In GitHub Actions, when a job specifies `name:`, GitHub names the check run after `name:`, not the job ID.  
  In `xtask/src/workflows.rs:152-179`, `Policy::protected_gates()` collects protected gate names exclusively from `graph.jobs`, `graph.aggregator`, and `required_checks`. These entries are the raw job IDs (`rust-linux`, `licences`, `attribution`, `docs`, `policy`, `provenance`).  
  The actual published check run display names are completely omitted from `protected_gates()`.  
  If a pull request introduces an additional workflow (e.g. `.github/workflows/spoof.yml`) defining:
  ```yaml
  jobs:
    bypass:
      name: "rust (fmt, clippy, nextest incl. xtask and hook tests) linux"
      runs-on: ubuntu-24.04
      steps:
        - run: echo "bypass"
  ```
  `spoofed_gate_names()` compares the job ID (`bypass`) and name against `gates`. Because the display name is not in `gates`, 0 findings are reported, allowing an untrusted PR workflow to publish check runs with the exact names of the required gate checks.
- **Minimal Test Input:**
  In `.github/workflows/spoof.yml`:
  ```yaml
  name: spoof
  on: [pull_request]
  permissions:
    contents: read
  jobs:
    bypass:
      name: "rust (fmt, clippy, nextest incl. xtask and hook tests) linux"
      runs-on: ubuntu-24.04
      steps:
        - run: echo "bypass"
  ```
- **Command Run:**
  ```bash
  git add .github/workflows/spoof.yml
  cargo xtask policy
  ```
- **Observed Output:**
  ```text
  PASS: unsafe-scope
  PASS: manifests
  PASS: workflows
  PASS: python
  PASS: codeowners
  ```
  Clean pass with exit code 0; 0 findings reported.
- **Suggested Fix:**  
  In `Policy::protected_gates()`, parse the owning workflow files to collect the published `name:` attribute for each gate job and aggregator, protecting both the job ID and its display name from reuse.

### ADV23R9-02: Aggregator Validation in `check_graph` Fails to Enforce Aggregator Published Name and Allows Trivial Passing Implementations

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** CI Workflow Hardening / Aggregator Gate Integrity (F1, D-74)
- **File & Line Citation:** [xtask/src/workflows.rs:881-910](../../../xtask/src/workflows.rs#L881-L910)
- **Description:**  
  Decision D-74 and requirement NFR-12 require the required branch-protection check `merge-gates` to aggregate and verify the results of all individual gate checks.  
  In `xtask/src/workflows.rs:881-910`, `check_graph()` performs aggregator validation:
  1. It locates the aggregator job by ID: `let Some((_, job)) = jobs.iter().find(|(name, _)| name == aggregator)`. It never validates that the aggregator's published `name:` property matches `merge-gates`. If `ci.yml` sets `name: random-name` on `merge-gates`, `check_graph` passes cleanly and `spoofed_gate_names` does not report it because the job ID is `merge-gates`. However, GitHub publishes the check run under `random-name`, omitting the required check `merge-gates` from branch protection.
  2. `check_graph` verifies that the job contains `needs: [...]` covering all required jobs and sets `if: always()`. However, it never inspects the job's steps to verify that it actually evaluates the results of its dependencies.  
  A PR modifying `.github/workflows/ci.yml` can replace the aggregator's verification step with:
  ```yaml
  jobs:
    merge-gates:
      if: always()
      needs: [rust-linux, rust-macos, licences, attribution, docs, policy, provenance]
      runs-on: ubuntu-24.04
      steps:
        - run: echo "bypassed"
  ```
  `cargo xtask policy` reports a clean pass (`PASS: workflows` with exit code 0). When executed in GitHub Actions, even if all 7 prerequisite gate checks fail, `merge-gates` executes and exits with 0 (PASS), satisfying GitHub branch protection.
- **Minimal Test Input:**
  In `.github/workflows/ci.yml`:
  ```yaml
  merge-gates:
    if: always()
    needs: [rust-linux, rust-macos, licences, attribution, docs, policy, provenance]
    runs-on: ubuntu-24.04
    steps:
      - run: echo "bypassed"
  ```
- **Command Run:**
  ```bash
  cargo xtask policy
  ```
- **Observed Output:**
  ```text
  PASS: unsafe-scope
  PASS: manifests
  PASS: workflows
  PASS: python
  PASS: codeowners
  ```
  Clean pass with exit code 0.
- **Suggested Fix:**  
  In `check_graph()`, require the aggregator job to have a literal `name:` matching the aggregator check name, and verify that its steps inspect dependency results (e.g. validating `needs.*.result == 'success'`).

### ADV23R9-03: Workflow Environment Validation in `check_env` Ignores Shell Startup Variable `BASH_ENV` and Runtime Injections

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** CI Workflow Hardening / Environment Injection (ADV23R5-01, ADV23R8-02, NFR-12)
- **File & Line Citation:** [xtask/src/workflows.rs:588-628](../../../xtask/src/workflows.rs#L588-L628)
- **Description:**  
  Decision ADV23R5-01 and NFR-12 mandate that pull-request workflows may not inject environment variables that alter execution or execute unauthorized code.  
  In `xtask/src/workflows.rs:608-628`, `check_env()` gates variables using `is_loader_env()` and `is_toolchain_env()`:
  ```rust
  pub fn is_loader_env(name: &str) -> bool {
      let upper = name.to_ascii_uppercase();
      upper.starts_with("LD_") || upper.starts_with("DYLD_")
  }
  ```
  Variables that do not match `is_loader_env()` or `is_toolchain_env()` are silently ignored.  
  When GitHub Actions executes `run:` steps on Linux runners, it launches `bash --noprofile --norc -e -o pipefail {0}`. According to the GNU Bash reference manual, when bash starts non-interactively, it inspects the environment variable `BASH_ENV`, expands its value, and executes commands from that file before executing any script.  
  If a workflow defines:
  ```yaml
  env:
    BASH_ENV: /tmp/injected.sh
  ```
  at workflow level, job level, or step level, the script at `/tmp/injected.sh` is executed before every single step script in the job. Furthermore, language runtime path variables (`PYTHONPATH`, `NODE_OPTIONS`, `PERL5LIB`, `RUBYLIB`) and POSIX shell variable `ENV` similarly bypass `check_env()`.
- **Minimal Test Input:**
  In `.github/workflows/ci.yml`:
  ```yaml
  jobs:
    policy:
      runs-on: ubuntu-24.04
      env:
        BASH_ENV: /tmp/injected.sh
  ```
- **Command Run:**
  ```bash
  cargo xtask policy
  ```
- **Observed Output:**
  ```text
  PASS: unsafe-scope
  PASS: manifests
  PASS: workflows
  PASS: python
  PASS: codeowners
  ```
  Clean pass with exit code 0.
- **Suggested Fix:**  
  Expand `check_env()` to forbid `BASH_ENV`, `ENV`, `SHELLOPTS`, `BASHOPTS`, `PYTHONPATH`, `NODE_OPTIONS`, and other execution-altering environment variables unless allow-listed in the trusted policy.

### ADV23R9-04: CodeRabbit PR-Body Exemption (D-61) Incorrectly Treats Bot Edit at `index == 0` as Introducer, Exempting Blocks Authored in Initial PR Creation

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** PR Review Attribution / Bot Block Exemption Provenance (D-61, R8-01)
- **File & Line Citation:** [xtask/src/attribution.rs:711-734, 853-874](../../../xtask/src/attribution.rs#L711-L734)
- **Description:**  
  Decision D-61 specifies that only summary blocks introduced by a bot edit from the listed bot account (`coderabbitai`) are exempt from attribution policy scanning. Blocks authored or changed by anyone else must be scanned and rejected.  
  In `xtask/src/attribution.rs`, `fetch_body_history()` queries GitHub GraphQL for `userContentEdits`.  
  In GitHub's GraphQL API, `userContentEdits` records only edits made to an existing PR description; it does not record the original PR creation.  
  In `parse_body_history()`, lines 717-733 sort the edits chronologically and return a `Vec<BodyVersion>`.  
  In `unverified()` (lines 853-866):
  ```rust
  let introduced = versions.iter().enumerate().any(|(index, version)| {
      let by_bot = version
          .editor
          .as_ref()
          .is_some_and(|editor| editor.bot && editor.login.eq_ignore_ascii_case(wanted));
      let before_without = index == 0
          || versions[index - 1]
              .text
              .as_deref()
              .is_some_and(|text| !contains(text));
      by_bot && version.text.as_deref().is_some_and(contains) && before_without
  });
  ```
  Notice that `before_without` evaluates to `true` whenever `index == 0`.  
  If a human author creates a PR whose initial description contains a spoofed or tampered CodeRabbit block (e.g. containing `Co-Authored-By: Claude` or AI credit), and the CodeRabbit bot performs the first edit on the PR description (e.g. adding a review status or updating the body), the bot's edit is the first edit in `userContentEdits`, placing it at `index == 0` in `versions`.  
  Because `index == 0`, `before_without` evaluates to `true`, and `unverified()` concludes that the bot introduced the block, exempting the user-authored block from scanning.
- **Minimal Test Input:**
  PR edit history where a human user creates the PR with the block in the initial body, and CodeRabbit makes the first edit to the PR body. Replaying this sequence with `versions = [BodyVersion { editor: coderabbitai (bot: true), text: "<bot_block with AI credit>" }]`.
- **Command Run:**
  Evaluating `bot_block_lines(body, &rules, Some(&history))` where `history` contains the bot edit at `index == 0`.
- **Observed Output:**
  ```text
  exempt: {1..10} (block lines marked exempt; 0 findings reported)
  ```
- **Suggested Fix:**  
  In `parse_body_history()`, include the PR author and initial creation text as the base version before `userContentEdits`, so that an edit by the bot is only considered to have introduced a block if the version prior to the bot's edit did not contain it.

### ADV23R9-05: Provenance Gate (D-56) Omits Standard Optimization and Solver Model Formats (`.mps`, `.lp`, `.qps`)

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** Provenance & Dataset Gate (D-56)
- **File & Line Citation:** [xtask/policy/repository.toml:35-58](../../../xtask/policy/repository.toml#L35-L58), [xtask/src/repository.rs:650-713](../../../xtask/src/repository.rs#L650-L713)
- **Description:**  
  Decision D-56 prohibits committing datasets outside allow-listed open-commercial sample paths (`spikes/data/samples/*`).  
  The repository develops mathematical optimization models and power system dispatch engines (`egs-solver-highs`, `egs-solver-gurobi`, `egs-solver-xpress`, `egs-solver-cuopt`, `egs-optimisation`). In mathematical programming and operations research, optimization problem instances are standardly exchanged in Mathematical Programming System format (`.mps`), Linear Programming format (`.lp`), and Quadratic Programming format (`.qps`).

  If a developer commits an unapproved transmission dispatch optimization model as `spikes/unit_commitment.mps` or `spikes/europe_opf.lp`:
  1. Neither `.mps` nor `.lp` matches `data_extensions`.
  2. `data_signature()` fails to match any binary signature.
  3. `cargo xtask provenance` reports a clean pass (`PASS: provenance/secrets/data (D-56)` with exit code 0).
- **Minimal Test Input:**
  Tracked file `spikes/unit_commitment.mps` or `spikes/europe_opf.lp`.
- **Command Run:**
  ```bash
  git add -f spikes/unit_commitment.mps spikes/europe_opf.lp
  cargo xtask provenance
  ```
- **Observed Output:**
  ```text
  PASS: provenance/secrets/data (D-56)
  ```
  Clean pass with exit code 0.
- **Suggested Fix:**  
  Add `.mps`, `.lp`, and `.qps` to `data_extensions` in `xtask/policy/repository.toml`.
