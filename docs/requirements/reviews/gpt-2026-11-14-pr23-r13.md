## Remaining findings

### 1. R13-01 — High — CORE: exempt PuTTY header permits arbitrary private key bodies

**Locations:** `xtask/policy/repository.toml:92`, `xtask/src/repository.rs:1238`,
`xtask/src/secrets.rs:586`. **Authority:** D-56, NFR-12, ADR 0001 secrets gate.
**Disposition:** must fix before bootstrap attestation.

The new exemption with line blob `4008fdecffda6aa6bf309962c5d3bd1a6726a782`
allows an indented PuTTY v3 header in the round-12 Gemini report. The local rule
matches only that header, and the exemption authenticates only that first line.
Changing the body below it to real private key material leaves the finding
exempt. This report path is outside protected policy paths; no owner-approved
policy change is needed.

**Concrete test:** in a disposable clone of the reviewed head, generate a throwaway
Ed25519 key with `ssh-keygen -q -t ed25519 -N '' -C review-ephemeral -f <key>`,
then convert it with `puttygen <key> -O private -o <key.ppk>`. Replace the entire
synthetic seven-line key block under ADV23R12-01 in
`docs/requirements/reviews/gemini-2026-11-14-pr23-r12.md` with that PPK, retaining
the existing two-space indentation on every code-block line. Its first line
remains exactly exempt; the public/private blocks and MAC now belong to the key.
Removing the Markdown indentation recovers the original valid PPK.
`puttygen <key.ppk> -L` round-trips to the OpenSSH public key (`cmp` succeeds).

Run the unchanged trusted binary/policy against the modified clone:

```bash
"$XTASK" --repo "$SCRATCH" --policy "$TRUSTED" all
```

**Observed:** exit **0**; policy, provenance/secrets/data and all documentation
checks pass. Control: the same PPK with an unindented header at the same report
path exits **1**, `local-putty-private-key`. This is exemption scope, not an
unsupported credential format or encrypted payload.

**Suggested change/test:** bind multiline secret exemptions to the complete
reviewed synthetic block or immutable reviewed file, and evaluate each finding
before merging views. A header-only exemption must not authorize an arbitrary
body. Add a regression replacing the body/MAC while preserving the approved
header, retaining the existing report and non-exempt-path controls.

### 2. R13-02 — High — CORE: a following line can allowlist an otherwise detected AWS secret

**Locations:** `xtask/src/secrets.rs:572`–`:582`;
`xtask/policy/gitleaks.toml:2112` (generic API-key line allowlist).
**Authority:** D-56, NFR-12, ADR 0001 secrets gate.
**Disposition:** must fix before bootstrap attestation.

When a rule consumes the terminating LF, `whole.end()` is after that LF.
The computed `end_line` therefore includes the following line in `regexTarget =
"line"`. A marker on that unrelated line suppresses a recognized secret on the
preceding line. This is an evaluator defect, not a missing gitleaks format.

**Concrete test:** generate a synthetic 40-character AWS-secret-shaped value
at runtime, in an otherwise unchanged clone:

```python
from pathlib import Path
import random, string
value = ''.join(random.Random(1302).choices(
    string.ascii_letters + string.digits + '+/', k=40))
Path('docs/credentials.txt').write_text(
    'aws_secret_access_key=' + value + '\n# --mount=type=secret,\n')
```

Track it with `git add -f docs/credentials.txt`, then run the trusted CLI command
above. **Observed:** `all` exits **0**, including provenance and documentation.
Independent minimal-repository controls:

| Input | `provenance` result |
|---|---|
| Unquoted assignment alone, ending in LF | **1**, `generic-api-key`, line 1 |
| Same assignment + immediately following `# --mount=type=secret,` | **0** |
| Same assignment + immediately following `import { harmless } from "module"` | **0** |
| Blank line between assignment and mount marker | **1**, `generic-api-key` |
| Quoted assignment followed by either marker | **1**, `generic-api-key` |

The pinned upstream `detect/detect.go` explicitly trims terminal newlines before
computing the match location, with a comment about excluding an incorrectly
following line. The port omits that behavior. AWS secret-access-key assignments
are a widely used credential type, so this is CORE even though the detecting
rule is named `generic-api-key`.

**Suggested change/test:** compute line/match allowlist targets with upstream's
newline/location semantics, excluding non-matching following lines. Add CLI and
evaluator cases for both markers, LF/CRLF, quoted/unquoted assignments, actual
same-line exclusions and decoded views.

### 3. R13-03 — High — CORE: secrets added and removed within the PR escape current-head gates

**Locations:** `xtask/src/repository.rs:1180`–`:1203` (tracked checkout only),
`.github/workflows/ci.yml` provenance step; `xtask/src/attribution.rs` range scan.
**Authority:** D-56, NFR-12, ADR 0001 secrets/data gate.
**Disposition:** must fix before bootstrap attestation; pre-existing scope gap.

Provenance scans only the final checkout. Attribution reads range commit messages
and final added lines for attribution, not intervening secret/data blobs. Adding
a secret in one PR commit and deleting it in the next restores green current-head
checks while retaining the secret in Git. No policy change or encoding is needed.

**Concrete test:** start from a passing repository, record `BASE`, and make two
ordinary local commits with harmless subjects. The first adds `notes.txt` holding
`service_token=` + `ghp_` + 36 zeroes + LF; the second deletes it. Use a synthetic
token, never a live credential. At the second commit:

```bash
"$XTASK" --repo "$SCRATCH" --policy "$TRUSTED" provenance
"$XTASK" --repo "$SCRATCH" --policy "$TRUSTED" attribution --base "$BASE" --head HEAD
git -C "$SCRATCH" cat-file -e "$INTRODUCING_COMMIT:notes.txt"
```

**Observed:** both gates exit **0**; attribution reports two commits and zero
added lines, and `cat-file -e` confirms the historical blob remains. The final
tracked tree is identical to the passing base. The same token rejects when
present in the current checkout (R12-01 controls above). This independent replay
used a minimal repository; the unchanged final tree establishes why builds and
other snapshot gates cannot detect the intervening blob.

The configured repository allows rebase merges, which can retain those commits
on main despite linear-history protection. A failed run on the first commit does
not block the succeeding head's checks. Squash-only merging would reduce main's
exposure but would not scan the published PR commits.

**Suggested change/test:** scan every newly introduced PR commit/blob against
trusted secret policy and applicable provenance/data policy, with a validated
range from current main. Deduplicate blob scans; do not rely on final-tree diffs,
prior check failures or commit-message scanning. Add add-then-delete and
add-then-replace regressions for credentials and declared research-only raw files,
including intermediate merge commits, plus clean-history/approved-fixture controls.

## Enforcement, ADR limitations and bootstrap assessment

1. **Trusted execution and approvals:** current-main policy loading, exact-head
   owner approval, protected workflow/policy paths, reserved check names and exact
   aggregator remain a sound M0 design within the stated identity boundary.
   Trusted `pull_request_target` jobs read PR objects as data and do not execute
   PR code. Existing negative tests pass; no new workflow/approval bypass was
   found. Shared-account evidence is attested cooperation, not cryptographic
   provider proof. D-74 account and branch-protection activation remain operational
   prerequisites, not tests this report labels green. Owner-author approval
   restrictions remain explicit.

2. **Unsafe/runtime checks:** root `forbid`, wrappers, feature/profile coverage
   and linker/search-root guards pass regressions and a full local build gate.
   ADR risks 5, 7, 8, 9 and 11 accurately retain same-user build-script/proc-macro
   tampering, static-library/location trust, target and higher-order feature limits.
   Those are acceptable reviewed M0 limitations; NFR-12 target-runner isolation
   evidence is due before M1 heavy jobs. Arbitrary build code is not sandboxed.

3. **Data/secrets:** type allowlists, signatures, strict text classification,
   manifest tags and sample provenance improve enforcement, but cannot establish
   licensing truth or classify every dataset hidden in source/Markdown/images.
   Disclosed heuristic limits are acceptable at M0 with review. Scanning the union
   of views fixes R12-01; pinning and fail-closed schema checks are valuable. They
   do not establish safe multiline exemptions (R13-01), evaluator equivalence
   (R13-02) or historical coverage (R13-03).

4. **Documentation accuracy:** the revision-13 ADR accurately describes views,
   pinning, global-path-allowlist exclusion, local formats and capitalization.
   Also disclose omitted optional base64/hex decoding (already in the PR body),
   ordinary upstream entropy/allowlist false negatives, and actual commit-range
   coverage once R13-03 is fixed. Those documentation additions are PERIPHERAL
   follow-ups. Documenting these three reproduced CORE bypasses without fixing
   them would not make the seed acceptable.

**Verdict: must-fix list R13-01, R13-02, R13-03.** Do not attest this head as the
one-time checks bootstrap on main. Resolve them and obtain an exact-head
independent re-review plus current adversarial review/triage before the manual
first-B0 checklist and seed attestation. R13-04 and bounded documentation/dictionary
work may follow separately. PR #23, bootstrap attestation, repository protection
and owner decisions were not modified.
