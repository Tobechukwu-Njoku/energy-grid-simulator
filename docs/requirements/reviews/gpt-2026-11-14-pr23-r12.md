## Remaining findings

### 1. R12-01 — High — CORE: encoding selection hides a raw token that revision 11 detects

**Locations at reviewed head:** `xtask/src/repository.rs:802` (`detect_encoding`),
`:852` (`decode_text`), `:1490` (select decoded text), `:1510` (only that view
reaches `scan_secrets`). **Authority:** NFR-12, ADR 0001 secrets gate.
**Disposition:** must fix before bootstrap attestation.

The new scanner replaces the raw-byte/UTF-8 view rather than scanning it as well.
A two-byte prefix `41 00` selects UTF-16LE for the entire file. An ordinary raw
ASCII token after that prefix becomes unrelated, valid Unicode code points when
paired as UTF-16. Strict decoding succeeds, the decoded text has no forbidden
controls, and the `.txt` type is allowed. Neither the data gate nor the sole
decoded secret scan reports anything. No policy, exemption, approval, workflow or
provenance manifest changes are necessary.

**Concrete test:** use a disposable clone of the exact head, `XTASK` pointing to
its compiled revision-12 checker, and `TRUSTED` to an unchanged revision-12 tree:

```bash
printf 'A\000service_token=ghp_%036d\n ' 0 > docs/connection-notes.txt
git add -f docs/connection-notes.txt
"$XTASK" --repo "$PWD" --policy "$TRUSTED" provenance
"$XTASK" --repo "$PWD" --policy "$TRUSTED" all
git -c core.hooksPath=/dev/null commit -m 'docs: synthetic notes'
"$XTASK" --repo "$PWD" --policy "$TRUSTED" provenance
```

**Observed:** all three checks exit **0**. The 58-byte file starts
`41 00 73 65 72 76 69 63`; the complete ASCII signature is present in raw bytes,
not encrypted, compressed, reconstructed or split. The rebuilt revision-11
checker, with its own unchanged policy, rejects this exact committed file with
exit **1**, `docs/connection-notes.txt:1: possible GitHub token committed`.
Removing the two-byte prefix and trailing padding gives the ordinary revision-12
positive control, which also exits **1**. This is a new loss of existing detection,
not a request to recognize another provider or to decrypt arbitrary blobs.

**Suggested change and regression:** scan the whole raw byte-preserving/UTF-8
view **and** the whole decoded view, rejecting the union of recognized secret
findings; alternatively fail closed on ambiguity without weakening ordinary
UTF-16/32 detection. Preserve the exact-file/exact-line exemption semantics for
each scanned view, without broad exemptions. Add this precise CLI fixture,
encoding-prefix/endian variants, the previous UTF-16/32 positives and harmless
controls. A passing submitted suite or an ADR caveat does not close this CORE
false negative.

## Enforcement and ADR limitation assessment

1. **Trusted check execution and approval:** the current-main loader, exact-head
   owner approval for protected paths, main-resident evidence and role/vendor
   checks remain substantially sound within their documented boundary. The
   trusted `pull_request_target` workflow reads PR objects as data, never executes
   the PR tree, and is separate from unprivileged PR build jobs. Reserved job IDs
   and published names and exact aggregator steps remain protected. Applicable
   adversarial tests passed; no new bypass of these boundaries was found.

2. **Unsafe/native-runtime enforcement:** the compiler/build/linker approach and
   mandatory root `forbid` remain a reasonable M0 baseline, not a claim of a
   malicious-build-script sandbox. The tested production/all-target/doc and
   feature configurations pass. ADR risks 5, 7, 8, 9 and 11 accurately retain
   same-user build-script tampering, static-library/search-root trust and the
   higher-order feature-combination/target limits. These require review, future
   target-system isolation and applicable reference evidence, not a claim that
   every possible execution path has been proved safe.

3. **File allowlists and D-73 composition:** new unlisted data formats now fail
   closed without enumerating every solver extension. `.py` being a tracked
   type does **not** authorize Python product code: independently tested
   `crates/tool.py` fails `all` at `python`, while `spikes/tool.py` passes.
   `provenance` is not a replacement for `policy`; the mandatory gate graph runs
   both. Exact image signatures are type checks, not full validation or proof
   that an image contains no hidden dataset. The ADR accurately states the
   five-consecutive-row table rule and that Markdown/source tables are not
   sniffed. File names, signatures and sample provenance remain a bounded
   heuristic, not universal data classification or licence verification.

4. **Decoder guarantee needs correction in code:** the revision-12 description
   accurately describes the chosen decoding path and its BOM-less heuristic,
   but that choice does not ensure that existing secret signatures remain
   visible. R12-01 defeats the claimed secrets baseline with a raw recognized
   token; this is **not acceptable** as an M0 limitation. Ordinary UTF-16/32
   positives are fixed, but their successful regression tests do not establish
   preservation of the raw scan. After fixing the code, document the combined
   scanning/ambiguity behavior accurately.

5. **Attribution and D-61:** the original watermark cases are fixed, R12-02 is
   narrow and peripheral, and heuristic language coverage cannot establish
   universal prose recognition. CodeRabbit remains enabled and its exemption
   remains provenance-scoped; no integration was removed or disabled. Existing
   GitHub-history/actor trust and unknown-origin handling remain relevant.

6. **Deployment is still a coordinator control:** on 2026-11-14 the repository
   API reports main protected, but legacy required-status-check contexts/checks
   are empty with enforcement `off`, and the active branch-rules endpoint
   returns no rules. Do not equate that flag with required gates being deployed.
   PR #23 has no approving owner review on this head. Run `43582116057` has
   passing Linux/macOS jobs but five failing policy-loader jobs and a failing
   aggregator; their logs explicitly say main `4cd9623` lacks xtask and this head
   is not an attested seed. This is the expected bootstrap fail-closed behavior,
   not evidence of deployment or authority to merge. A manual exact-SHA bootstrap
   procedure, followed by required trusted checks/code-owner protection and
   re-running gates after approval, remains necessary. Keep the D-74 machine
   account transition separate from this owner-authorized report publication.
