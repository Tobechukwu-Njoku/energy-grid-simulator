### 1. R6-01 — High — STRUCTURAL: a real crate named `___` bypasses the wrapper

**Location:** `xtask/src/build_gate.rs:89`–`:95` (`rewrite`).
**Reviewer test:** `reviewer_r6_probe_crate_name_skips_guard`.

Create `crates/solver-highs` with this addition to its inherited package manifest:

```toml
[lib]
name = "___"
```

Its library source is `#![allow(unsafe_code)]`. Its build.rs is:

```rust
#![forbid(unsafe_code)]
fn main() {
    let out = std::path::PathBuf::from(std::env::var_os("OUT_DIR").unwrap());
    let library = out.join("libpython3.12.a");
    assert!(std::process::Command::new("ar")
        .arg("crs").arg(&library).status().unwrap().success());
    println!("cargo:rustc-link-arg={}", library.display());
}
```

Cargo accepts that library name. The build gate and static graph check both
return no findings. Every real rustc invocation with `--crate-name ___` is
misclassified as a target-info probe and returned unchanged: no linker guard
and no command-line unsafe forbid are added. Cargo's JSON exposes no linked_libs
or linked_paths for a link-arg, so the second channel does not catch the archive.
The actual library test executable links successfully with the Python-named input.

**Control:** remove only `[lib] name = "___"`. The same build.rs, archive and
workspace now produce an NFR-10 linker-guard finding. This is normal build-script
output, not wrapper replacement or job tampering. The static root-forbid check
still protects non-adapter source; the demonstrated false negative is native linking.

**Suggested change:** identify probes by their actual invocation structure or
apply enforcement to them too. A legal crate name must never exempt a compilation.
Add this real Cargo fixture and its ordinary-name rejection control.

### 2. R6-02 — High — STRUCTURAL: response-file quoting hides the actual library name

**Location:** `xtask/src/build_gate.rs:176`–`:220` (`linked`).
**Reviewer test:** `reviewer_r6_linker_response_file_hides_library`.

Add an engine `src/main.rs` with root forbid and an empty main. Its build.rs is:

```rust
#![forbid(unsafe_code)]
fn main() {
    let out = std::path::PathBuf::from(std::env::var_os("OUT_DIR").unwrap());
    let library = out.join("libpython3.12.a");
    assert!(std::process::Command::new("ar")
        .arg("crs").arg(&library).status().unwrap().success());
    let rsp = out.join("native.rsp");
    std::fs::write(&rsp,
        format!("\"{}\"/libpyth\"on\"3.12.a\n", out.display())).unwrap();
    println!("cargo:rustc-link-arg=@{}", rsp.display());
}
```

The guard does run. It splits the response text on whitespace and trims quote
characters at token ends, preserving the embedded quotes in `libpyth"on"3.12.a`.
That spelling contains neither prohibited runtime name. The real C driver parses
the response syntax and concatenates adjacent quoted/unquoted fragments into the
existing `libpython3.12.a` path. Both compilation and linking succeed; the build
gate and static graph check return no findings. No link-search instruction is
emitted, so directory inspection does not catch it.

**Control:** the direct `/tmp/libpython3.12.a` argument to this same linker guard
is refused with NFR-10 before cc runs. Ordinary fully quoted Python library
paths are also detected by the existing parser; embedded quoting is the difference.

**Suggested change:** parse the supported C-driver response grammar correctly,
including quoting and escaping, or reject response files outside a deliberately
restricted supported syntax. Also handle or reject nested and linker-forwarded
response files; the current one-pass expansion cannot justify its broad coverage
claim. Only the embedded-quote case is claimed here as locally reproduced end to
end; this machine's Zig driver rejects the separately tried forwarded/nested forms.

### 3. R6-03 — High — STRUCTURAL: all-features compilation omits default-feature link code

**Location:** `xtask/src/build_gate.rs:336`–`:345` (`check`).
**Reviewer test:** `reviewer_r6_feature_disabled_runtime`.

Give `crates/solver-highs` this feature and source:

```toml
[features]
pure = []
```

```rust
#![allow(unsafe_code)]
#[cfg(not(feature = "pure"))]
#[link(name = "python3.12")]
unsafe extern "C" {}
```

The build gate and static graph check return no findings: `--all-features`
disables this link request. `cargo metadata --all-features` does not enumerate
the Rust items active in other feature configurations. The same omission applies
to build-script link output conditional on a disabled feature.

**Control:** run the same wrapped Cargo build with only `--all-features` removed.
The default-feature library test reaches the guard and is refused with NFR-10.
That diagnostic occurs before the real linker, so it needs no installed Python.
The ordinary Linux/macOS jobs do not use the guard; an installed runtime may let
their default-feature builds succeed. Thus those jobs are not enforcement controls.

**Suggested change:** at least enforce the default build as well as all features,
and explicitly define the supported feature configurations requiring guarded
builds, including relevant no-default/subset configurations. Reject unsupported
configurations or document and review that bounded coverage. All features is not
the union of all compiled code. The ADR's target-cfg limitation omits this host-side
feature limitation and must be corrected.

## Design, reporting and M0 acceptability

Using Cargo metadata and compiler expansion is a substantial correctness
improvement. Metadata covers the actual resolved local packages, targets and
patches without duplicating Cargo's glob language. The static check rejects
untracked/out-of-repository targets and non-crates.io remote dependencies.
For ordinary compiled repository units, the wrapper strips lint caps and enforces
the unsafe boundary after macro expansion. Registry dependencies retain their
existing unsafe permissions, consistently with a boundary on project crates.
Adapter build scripts receive the compiler forbid even though the static graph
check exempts adapter targets generally. The wrapper actually exempts every
non-build-script adapter target, not just the library/test targets named in the
addendum; all still belong to the adapter package.

Observed failures are reported reliably: compiler errors become findings;
linker NFR-10 text survives the JSON diagnostic; a failed Cargo process without
a parsed compiler finding produces a fallback finding; `main` exits nonzero for
findings. The policy step and merge-gates aggregation propagate that failure.
The four false negatives above arise before that reporting decision: the relevant
check is bypassed or never observes the prohibited code/input, so the green result
overstates coverage. The tested library-only `test = false` input was still checked
under `--all-targets`; no defect is claimed for that hypothesis.

The ADR's same-user build-script/proc-macro tampering limitation is accurate.
For M0's unprivileged, secret-free hosted job, this is an acceptable bounded
cooperative-review baseline, not an isolation boundary against malicious build
code. Neither new linker counterexample tampers with that job or wrapper.
The separation from `pull_request_target` trusted review/approval jobs is correct.

Host-target-only compiler coverage is also a reasonable M0 scope if stated
precisely: root forbid protects ordinary non-adapter target-specific Rust code
when later compiled, but native-runtime linking on other targets is unproven.
Doctests and feature-dependent compilation require the corrections above.
The static-archive bundling limitation is real: no final-link argument exists to
inspect after rustc bundles the native archive into an rlib. The current search-
directory heuristic is not a complete native dependency inventory and can also
reject an unused runtime library merely present in a search directory. At this
skeleton M0, with no implemented native solver integration, that expressly bounded
limitation can be carried as a reviewed follow-up before native integrations;
it must not be described as proof that arbitrary native archives contain no
Python/Julia code. NFR-8 already requires separate native-library inventory.

The known bootstrap requirements remain: coordinator exact-SHA attestation on
main, current independent/adversarial review and triage, exact-head owner approval
where applicable, the separate machine account, and required-check activation.
This report supplies no attestation or repository-setting change. Because the
four counterexamples above remain, **do not use this head as the one-time seed**.
