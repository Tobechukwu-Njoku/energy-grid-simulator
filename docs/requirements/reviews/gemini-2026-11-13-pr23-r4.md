### ADV23R4-01: Hex and Unicode Character Escapes in `#[link(name = "...")]` Attributes Evade Native Runtime Ban (NFR-10)

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** Rust Policy / Native Runtimes (NFR-10)
- **File & Line Citation:** [xtask/src/rust_policy.rs:70-88, 112-117](xtask/src/rust_policy.rs#L70-L88)
- **Description:**  
  Decision NFR-10 forbids linking native Python or Julia runtimes.
  In `xtask/src/rust_policy.rs`, `links_runtime()` and `names_runtime()` inspect link attributes:
  ```rust
  if ident.unraw() == "link"
      && let Some(TokenTree::Group(group)) = trees.get(index + 1)
      && group.delimiter() == Delimiter::Parenthesis
      && names_runtime(&group.stream().to_string())
  {
      return true;
  }
  ```
  `names_runtime()` converts the token stream string to lower case and checks:
  ```rust
  ["python", "julia", "libpython", "libjulia"]
      .iter()
      .any(|name| lower.contains(name))
  ```
  This check operates on the raw token stream text rather than decoding the string literal. In Rust, string literals support standard ASCII hex escapes (`\x70` for `'p'`, `\x6a` for `'j'`) and Unicode escapes (`\u{74}` for `'t'`).
  When an attribute is written as `#[link(name = "\x70ython3.12")]`, the token stream text contains literal `\x70ython3.12`, which does not contain the substring `"python"`. Rustc decodes the escape at compile time and links against `libpython3.12`, completely evading the policy check.
- **Minimal Test Input:**
  ```rust
  #[link(name = "\x70ython3.12")]
  unsafe extern "C" {}
  ```
- **Command Run:**
  ```bash
  cargo xtask policy
  ```
- **Observed Output:**
  ```text
  PASS: unsafe-scope and native-runtimes
  PASS: manifests
  PASS: workflows
  PASS: python
  PASS: codeowners
  ```
  The check passed with exit code 0.
- **Suggested Fix:**  
  Parse the contents of `link(...)` attributes using `syn::Meta` or decode string literals (`syn::LitStr::value()`) so character escapes are resolved prior to substring evaluation.

### ADV23R4-02: Build Script Submodules and Helper Files Emitting Cargo Instructions Bypass Native Runtime Detection (NFR-10)

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** Rust Policy / Build Script Scanning (NFR-10)
- **File & Line Citation:** [xtask/src/rust_policy.rs:162-170, 380-395](xtask/src/rust_policy.rs#L162-L170)
- **Description:**  
  In `xtask/src/rust_policy.rs`, `check_sources()` identifies build scripts via `package_targets()`:
  ```rust
  findings.extend(scan_rust_as(path, &source, build_scripts.contains(path)));
  ```
  `build_scripts` contains only the primary build script entry point (e.g. `crates/engine/build.rs`).
  Build scripts in Rust commonly factor helper routines, code generators, and link helpers into submodules (e.g. `mod build_helper;` located in `build_helper.rs` or `src/build_helper.rs`).
  When `check_sources()` iterates through the remaining `.rs` files in the crate, `build_scripts.contains(path)` evaluates to `false`. In `Scan`, string literals and macro arguments are inspected for runtime library names only when `self.build_script` is true:
  ```rust
  fn visit_lit_str(&mut self, literal: &'ast syn::LitStr) {
      if self.build_script && names_runtime(&literal.value()) {
          self.flag(literal.span().start().line, "build script names a Python or Julia library (NFR-10)");
      }
  }
  ```
  Because `self.build_script` is `false` for the helper module, `println!("cargo:rustc-link-lib=python3.12")` is ignored. When Cargo compiles and executes `build.rs`, the helper outputs the instruction to Cargo stdout, linking against `python3.12` without detection.
- **Minimal Test Input:**
  A helper file `crates/engine/src/build_helper.rs` invoked from `build.rs`:
  ```rust
  pub fn link() {
      println!("cargo:rustc-link-lib=python3.12");
  }
  ```
- **Command Run:**
  ```bash
  cargo xtask policy
  ```
- **Observed Output:**
  ```text
  PASS: unsafe-scope and native-runtimes
  PASS: manifests
  PASS: workflows
  PASS: python
  PASS: codeowners
  ```
  The check passed with exit code 0.
- **Suggested Fix:**  
  When scanning a crate with a build script, either traverse modules reachable from `build.rs` with `build_script = true`, or inspect any string literal matching `cargo:rustc-link-lib=` across all non-adapter Rust files.

### ADV23R4-03: Action Workflow Check Only Inspects `.github/actions/`, Allowing Uninspected Composite Actions Outside That Directory

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** CI Workflow Hardening / Action Pinning & Security (NFR-12, D-73)
- **File & Line Citation:** [xtask/src/workflows.rs:169-172, 643-651](xtask/src/workflows.rs#L169-L172)
- **Description:**  
  `xtask/src/workflows.rs:643-651` checks local actions as follows:
  ```rust
  for path in tracked(&ctx.repo)? {
      if path.starts_with(".github/actions/")
          && (path.ends_with("action.yml") || path.ends_with("action.yaml"))
      {
          let text = std::fs::read_to_string(ctx.repo.join(&path))
              .map_err(|error| format!("{path}: {error}"))?;
          findings.extend(check_action(&path, &text, &policy));
      }
  }
  ```
  Meanwhile, `pinned()` in `workflows.rs:169-172` exempts any local action path starting with `./`:
  ```rust
  fn pinned(action: &str) -> bool {
      if action.starts_with("./") {
          return true;
      }
      ...
  ```
  If a pull request defines a local action at `actions/helper/action.yml` or `tools/ci/action.yml` (outside `.github/actions/`) and references it in a workflow via `uses: ./actions/helper`:
  1. `pinned()` evaluates to `true` because the string starts with `./`.
  2. `check()` ignores `actions/helper/action.yml` because it does not start with `.github/actions/`.
  3. `check_action()` is never invoked, allowing the action to configure prohibited shells (such as `python`), execute unpinned remote actions, access secrets, or bypass CI policies.
- **Minimal Test Input:**
  Tracked file `actions/helper/action.yml`:
  ```yaml
  name: helper
  runs:
    using: composite
    steps:
      - shell: python
        run: |
          import os
          print("Running python")
  ```
- **Command Run:**
  ```bash
  cargo xtask policy
  ```
- **Observed Output:**
  ```text
  PASS: unsafe-scope and native-runtimes
  PASS: manifests
  PASS: workflows
  PASS: python
  PASS: codeowners
  ```
  The check passed with exit code 0.
- **Suggested Fix:**  
  In `xtask/src/workflows.rs`, inspect all tracked `action.yml` / `action.yaml` files anywhere in the repository, and enforce that local action references in workflows must start with `./.github/actions/`.

### ADV23R4-04: Inline Comment and Markup Delimiters Without Preceding Whitespace Evade Payload Segmentation in Attribution Scanner (D-52)

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** D-52 Attribution Policy / Markup & Delimiter Stripping
- **File & Line Citation:** [xtask/src/attribution.rs:344-374](xtask/src/attribution.rs#L344-L374)
- **Description:**  
  `delimiter_forms()` was added in revision 4 to strip non-alphanumeric comment delimiters generically:
  ```rust
  for (index, character) in line.char_indices() {
      if previous_space && index > 0 && is_delimiter(character) {
          starts.push(index);
      }
      previous_space = character.is_whitespace();
  }
  ```
  Notice that `starts.push(index)` requires `previous_space` to be `true`.
  When a comment delimiter directly follows code without preceding whitespace—for instance in PowerShell `$x = 1<# Generated with Claude Code #>` or ARM assembly `mov r0, r1@Generated with Claude Code`—`previous_space` is `false`.
  Because `<#` and `@` are not in `TRAILING_MARKERS`, `trailing_payloads()` does not slice the line.
  Consequently, `candidates()` never evaluates the trimmed payload `Generated with Claude Code`, and the unstripped line fails to match Pattern 4 due to the preceding `$x = 1<#` tokens.
- **Minimal Test Input:**
  ```text
  $x = 1<# Generated with Claude Code #>
  ```
- **Command Run:**
  ```bash
  cargo xtask attribution --base HEAD~1 --head HEAD --title '$x = 1<# Generated with Claude Code #>'
  ```
- **Observed Output:**
  ```text
  scanned 1 commit(s), 9 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  ```
  The check passed with exit code 0.
- **Suggested Fix:**  
  In `delimiter_forms()`, record delimiter transition boundaries when transitioning from an alphanumeric character to a delimiter, or include `<#`, `#>`, and `@` in `TRAILING_MARKERS`.
