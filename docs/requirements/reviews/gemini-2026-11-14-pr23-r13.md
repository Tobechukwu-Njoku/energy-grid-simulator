## 3. Detailed Findings (ADV23R13-01 .. ADV23R13-08)

### ADV23R13-01: Database Connection URIs with Embedded Credentials Omitted from Secret Scanning (D-56)

- **Classification:** CORE
- **Severity:** HIGH
- **Area:** Secrets Detection (D-56, ADR 0001)
- **File & Line Citation:** [xtask/src/secrets.rs:483-594](../../../xtask/src/secrets.rs#L483-L594), [xtask/policy/secret-rules.toml:35-166](../../../xtask/policy/secret-rules.toml#L35-L166), [xtask/policy/gitleaks.toml:637-660](../../../xtask/policy/gitleaks.toml#L637-L660)
- **Description:**  
  Decision D-56 and ADR 0001 require that credentials and secrets must not be committed to the repository.  
  Standard database and message broker connection URIs commonly follow the RFC 3986 format `scheme://username:password@hostname:port/database` (for example, `postgres://`, `mysql://`, `mongodb://`, `redis://`, `amqp://`).  
  When committed in source code, configuration files, or documentation (e.g., `const DB_URL: &str = "postgres://user:secret@host/db";`), these strings bypass secret detection completely:
  1. The vendored Gitleaks ruleset does not include rules for RFC 3986 connection URIs with embedded userinfo.
  2. The fallback rule `generic-api-key` ([gitleaks.toml:637](../../../xtask/policy/gitleaks.toml#L637)) requires specific variable keywords (`access|auth|api|credential|creds|key|passwd|password|secret|token`), which standard URL variable identifiers (`DB_URL`, `DATABASE_URL`, `POSTGRES_URL`, `REDIS_URL`, `DATABASE_CONNECTION`) do not contain.
  3. No local rule in `secret-rules.toml` checks for connection URIs with embedded passwords.
- **Minimal Test Inputs:**
  Tracked file `crates/db.rs` containing a database connection URI: scheme `postgres://`, username `grid_admin`, password `aB8$kL2#mN9*pQ4!zY1`, host `postgres.prod.internal:5432`, database `energy_grid`.
- **Commands Run:**
  ```bash
  printf 'const DB_URL: &str = "postgres://grid_admin:aB8$kL2#mN9*pQ4!zY1@postgres.prod.internal:5432/energy_grid";\n' > crates/db.rs
  git add -f crates/db.rs
  cargo xtask provenance
  ```
- **Observed Output:**
  ```text
  PASS: provenance/secrets/data (D-56)
  ```
  Clean pass with exit code 0.
- **Suggested Fix:**  
  Add a local rule in `xtask/policy/secret-rules.toml` targeting standard connection string URI schemes with embedded passwords: `(?i)(?:postgres(?:ql)?|mysql|mariadb|mongodb(?:\+srv)?|redis|amqps?|mssql)://[^\s:@/\\]+:[^\s@/\\]{8,}@[^\s/]+`.

### ADV23R13-02: Kubernetes Cluster Authentication Configs and Client Key Data (`client-key-data:`) Evade Secret Scanning (D-56)

- **Classification:** CORE
- **Severity:** HIGH
- **Area:** Secrets Detection (D-56, ADR 0001)
- **File & Line Citation:** [xtask/policy/gitleaks.toml:2443-2455](../../../xtask/policy/gitleaks.toml#L2443-L2455), [xtask/policy/secret-rules.toml:35-166](../../../xtask/policy/secret-rules.toml#L35-L166)
- **Description:**  
  Kubernetes cluster access configurations (`kubeconfig`, standard YAML format) store cluster credentials using the `client-key-data:` attribute, which contains the base64-encoded private key of the cluster administrator or service client.  
  In `xtask/policy/gitleaks.toml`, the rule `kubernetes-secret-yaml` ([line 2444](../../../xtask/policy/gitleaks.toml#L2444)) strictly checks for `kind: Secret`. In contrast, kubeconfig files define `kind: Config`.  
  Furthermore, because an encoded client private key is typically 1,000+ base64 characters, it exceeds the 150-character limit of `generic-api-key` (`[\w.=-]{10,150}`).  
  Consequently, a kubeconfig file or YAML deployment config containing cluster client private keys in permitted extensions (e.g., `crates/kube.yaml`) passes secret scanning undetected.
- **Minimal Test Inputs:**
  Tracked file `crates/kube.yaml` containing a standard `kind: Config` kubeconfig document with `client-key-data:` containing base64-encoded private key material.
- **Commands Run:**
  ```bash
  cat << 'EOF' > crates/kube.yaml
  apiVersion: v1
  kind: Config
  clusters:
  - cluster:
      server: https://10.0.0.1:6443
    name: energy-cluster
  contexts:
  - context:
      cluster: energy-cluster
      user: cluster-admin
    name: default
  current-context: default
  users:
  - name: cluster-admin
    user:
      client-key-data: LS0tLS1CRUdJTiBSU0EgUFJJVkFURSBLRVktLS0tLQpNSUlFcEFJQkFBS0NBUUVBMEsyYl...
  EOF
  git add -f crates/kube.yaml
  cargo xtask provenance
  ```
- **Observed Output:**
  ```text
  PASS: provenance/secrets/data (D-56)
  ```
  Clean pass with exit code 0.
- **Suggested Fix:**  
  Add a local rule in `xtask/policy/secret-rules.toml` targeting `client-key-data:\s*["']?[A-Za-z0-9+/]{40,}` in YAML/text files.

### ADV23R13-03: Machine Login and Database Authentication Credential Lines (`.netrc` / `.pgpass`) in Permitted Files Evade Secret Scanning (D-56)

- **Classification:** CORE
- **Severity:** HIGH
- **Area:** Secrets Detection & Credential Files (D-56, ADR 0001)
- **File & Line Citation:** [xtask/src/repository.rs:423-433](../../../xtask/src/repository.rs#L423-L433), [xtask/src/secrets.rs:483-594](../../../xtask/src/secrets.rs#L483-L594)
- **Description:**  
  In `xtask/src/repository.rs:423-433`, `KEY_FILES` flags files whose exact filename is `.netrc` or `.pgpass`.  
  However, neither `gitleaks.toml` nor `secret-rules.toml` scans the content syntax of these credential formats:
  - `.netrc` lines: `machine <host> login <user> password <secret>`
  - `.pgpass` lines: `hostname:port:database:username:password`  
  Because `.netrc` uses space delimiters rather than assignment operators (`=`, `:`), `generic-api-key` does not match. Similarly, colon-delimited `.pgpass` lines do not contain the keyword before an assignment operator.  
  When `.netrc` or `.pgpass` credential records are stored in permitted text files (such as `crates/auth.txt`, `crates/netrc.txt`, or documentation), they completely evade secret scanning.
- **Minimal Test Inputs:**
  - Tracked file `crates/netrc.txt` containing: `machine energy-api.example.com login service-user password SecretPassword123!`
  - Tracked file `crates/pgpass.txt` containing: `postgres.prod.internal:5432:energy_grid:grid_user:P@ssw0rd987654321!`
- **Commands Run:**
  ```bash
  printf 'machine energy-api.example.com login service-user password SecretPassword123!\n' > crates/netrc.txt
  git add -f crates/netrc.txt
  cargo xtask provenance
  ```
  ```bash
  printf 'postgres.prod.internal:5432:energy_grid:grid_user:P@ssw0rd987654321!\n' > crates/pgpass.txt
  git add -f crates/pgpass.txt
  cargo xtask provenance
  ```
- **Observed Output:**
  ```text
  PASS: provenance/secrets/data (D-56)
  ```
  Both commands passed cleanly with exit code 0.
- **Suggested Fix:**  
  Add rules in `xtask/policy/secret-rules.toml` for:
  1. `.netrc` credential lines: `(?i)(?:^|\s)machine\s+[^\s]+\s+login\s+[^\s]+\s+password\s+[^\s]{8,}`.
  2. `.pgpass` credential lines: `^[^\s:#]+:[0-9]{1,5}:[^\s:#]+:[^\s:#]+:[^\s:#]{8,}$`.
