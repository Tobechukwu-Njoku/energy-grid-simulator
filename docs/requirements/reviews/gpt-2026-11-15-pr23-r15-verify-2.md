## R15V2-01 — placeholder repair truncates real connection passwords

- Classification: **CORE**, regression in the requested ADV23R14-03 repair.
- Severity: **high**.
- Source: `xtask/src/secrets/credentials.rs:178`, especially line 205;
  literal classification starts at line 8 and consumes the truncated value
  at line 303.
- Introduced boundary: `assignment_value` now terminates an unquoted value at
  any whitespace or backtick. This is not a valid general boundary for
  semicolon-delimited ODBC connection-password values. If the first fragment
  equals a placeholder, the rest of a literal password is never classified.

### Minimal reproduction

In an otherwise passing minimal repository with an open-commercial baseline
manifest, build this synthetic ODBC string in a tracked `notes.txt`. Fragments
are kept separate here so the report does not itself publish a complete literal
credential fixture:

```bash
printf '%s%s%s\n' 'Server=database.internal;Uid=operator;Pwd' \
  '=' '<EXAMPLE_PASSWORD_WITH_SPACES>;' > notes.txt
git add notes.txt
"$CANDIDATE_XTASK" --repo "$PROBE_REPO" --policy "$CANDIDATE_POLICY" provenance
"$PREVIOUS_XTASK" --repo "$PROBE_REPO" --policy "$PREVIOUS_POLICY" provenance
```

The value consists of the placeholder word `secret`, an internal space, and
the additional literal fragment `<LITERAL_SUFFIX>`. It is a multiword password,
not the exact standalone placeholder. The earlier checker at
`60bef0d07bc41882d24be7de4c98e7d97deac302`, independently rebuilt with its own
unchanged policy, exits **1** with `local-connection-password`. The requested
candidate exits **0**, reporting `PASS: provenance/secrets/data (D-56)`.

Additional differential cases use the same connection-string prefix and these
separately described password fragments:

| Password construction | Previous checker | Requested candidate |
|---|---|---|
| Placeholder word, space, additional literal fragment | Reject, exit 1 | **Accept, exit 0** |
| Angle-bracket placeholder, space, additional literal fragment | Reject, exit 1 | **Accept, exit 0** |
| Ellipsis, space, additional literal fragment | Reject, exit 1 | **Accept, exit 0** |
| Ellipsis, literal backtick, additional literal fragment | Reject, exit 1 | **Accept, exit 0** |
| Angle-bracket placeholder, literal backtick, additional literal fragment | Reject, exit 1 | **Accept, exit 0** |

| Same multiword password explicitly braced | Reject, exit 1 | Reject, exit 1 |
| Same multiword password explicitly quoted | Reject, exit 1 | Reject, exit 1 |

The first reproduction uses only letters, digits and an internal space in the
password; it does not depend on special-character escaping or on whether a
driver tolerates a malformed string. Microsoft's ODBC connection-string grammar
defines an attribute value as a character string, including PWD; internal spaces
are not attribute terminators. Primary reference, accessed 2026-11-15:
`https://learn.microsoft.com/en-us/sql/odbc/reference/syntax/sqldriverconnect-function?view=sql-server-ver17`
(connection-string syntax section). No database connection or authentication
attempt is needed to demonstrate the scanner's truncation.

The same first fixture also passes in a full clone of the requested candidate:

- Staged tracked file: `provenance` exits 0.
- Staged tracked file: `all` exits 0, including provenance.
- Committed synthetic fixture: checkout `provenance` exits 0.
- Explicit range from the clean candidate to the fixture commit: `provenance`
  exits 0.

This is not a broad new review-round finding: it directly tests whether the
requested placeholder relaxation preserved ADV23R14-03's literal detection.
Fix value-boundary handling in the appropriate connection-string/Markdown
context; do not classify a truncated prefix as the entire password. Add these
negative cases alongside the passing exact-placeholder and Markdown controls.
No candidate fix is made in this verification PR.
