### ADV23R12-01: PuTTY Private Key Format (`PuTTY-User-Key-File`) Omitted from Private Key and Key File Scanning (D-56)

- **Classification:** CORE
- **Severity:** HIGH
- **Area:** Secrets & Private Key Scanning (D-56, ADR 0001)
- **File & Line Citation:** [xtask/src/repository.rs:654-666](../../../xtask/src/repository.rs#L654-L666), [xtask/src/repository.rs:704-715](../../../xtask/src/repository.rs#L704-L715)
- **Description:**  
  Decision D-56 and ADR 0001 prohibit committing credentials and private key material to the repository.  
  In `xtask/src/repository.rs`, private key detection in `scan_secrets` checks for PEM headers:
  ```rust
  const PEM_HEADER: &str = concat!("-----BEG", "IN");
  const PEM_KEY: &str = concat!("PRIVATE", " KEY");
  ...
  if line.contains(PEM_HEADER) && line.contains(PEM_KEY) {
      findings.push(Finding::at(path, Some(index + 1), "private key material must not be committed"));
  }
  ```
  PuTTY private keys (`.ppk`), generated by PuTTYgen and standard across Windows SSH tools, do not use the OpenSSL PEM armor headers. Instead, they begin with plaintext header lines:
  ```text
  PuTTY-User-Key-File-2: ssh-rsa
  ```
  or
  ```text
  PuTTY-User-Key-File-3: ssh-ed25519
  Encryption: none
  Comment: test-key
  Public-Lines: 2
  ...
  Private-Lines: 1
  ...
  ```
  Because `.ppk` is not in `KEY_EXTENSIONS` (`xtask/src/repository.rs:704`), and `PuTTY-User-Key-File` does not match `PEM_HEADER` or `PEM_KEY`, an unencrypted PuTTY private key placed in an allowed text file (such as `crates/key.txt` or `docs/key.txt`) completely bypasses secret scanning.
- **Minimal Test Inputs:**
  Tracked file `crates/putty_key.txt` containing:
  ```text
  PuTTY-User-Key-File-3: ssh-ed25519
  Encryption: none
  Comment: test-key
  Public-Lines: 2
  AAAAC3NzaC1lZDI1NTE5AAAAIGx5
  Private-Lines: 1
  AAAAYCe
  ```
- **Commands Run:**
  ```bash
  printf 'PuTTY-User-Key-File-3: ssh-ed25519\nEncryption: none\nComment: test-key\nPublic-Lines: 2\nAAAAC3NzaC1lZDI1NTE5AAAAIGx5\nPrivate-Lines: 1\nAAAAYCe\n' > crates/putty_key.txt
  git add -f crates/putty_key.txt
  cargo xtask provenance
  ```
- **Observed Output:**
  ```text
  PASS: provenance/secrets/data (D-56)
  ```
  Clean pass with exit code 0.
- **Suggested Fix:**  
  1. Add `.ppk` to `KEY_EXTENSIONS` in `xtask/src/repository.rs:704`.  
  2. In `scan_secrets`, check for `PuTTY-User-Key-File` header lines and report them as private key material.

### ADV23R12-02: GitLab Runner Authentication Tokens (`glrt-`) and Perplexity AI API Keys (`pplx-`) Omitted from `SECRET_RULES` (D-56)

- **Classification:** CORE
- **Severity:** HIGH
- **Area:** Secrets Detection (D-56, ADR 0001)
- **File & Line Citation:** [xtask/src/repository.rs:434-585](../../../xtask/src/repository.rs#L434-L585)
- **Description:**  
  `SECRET_RULES` defines recognized credential prefixes. While GitLab Personal Access Tokens (`glpat-`) are scanned, GitLab Runner Authentication Tokens (`glrt-`, standard 26+ character runner execution tokens introduced in GitLab 16.0) are omitted. In addition, Perplexity AI API keys (`pplx-`, standard 48-character API tokens) are omitted.  
  When committed in source code, configuration files, or documentation, both credentials pass completely undetected.
- **Minimal Test Inputs:**
  - Tracked file `crates/token.rs` containing a GitLab runner token: prefix `glrt-` followed by 26 alphanumeric characters.
  - Tracked file `crates/token.rs` containing a Perplexity API key: prefix `pplx-` followed by 48 hexadecimal characters.
- **Commands Run:**
  ```bash
  printf 'gitlab_runner_token="glrt-1234567890abcdef1234567890"\n' > crates/token.rs
  git add -f crates/token.rs
  cargo xtask provenance
  ```
  ```bash
  printf 'perplexity_key="pplx-abcdef1234567890abcdef1234567890abcdef1234567890"\n' > crates/token.rs
  git add -f crates/token.rs
  cargo xtask provenance
  ```
- **Observed Output:**
  ```text
  PASS: provenance/secrets/data (D-56)
  ```
  Both commands passed with exit code 0.
- **Suggested Fix:**  
  Add `SecretRule` entries for `glrt-` (GitLab runner token, min length 20) and `pplx-` (Perplexity API key, min length 40) in `SECRET_RULES`.

### ADV23R12-05: Gratitude Expressions `Thank you [to] <Model>`, `Kudos to <Model>`, and `Shoutout to <Model>` Evade Pattern 61 (D-52)

- **Classification:** PERIPHERAL
- **Severity:** HIGH
- **Area:** Attribution Policy (D-52) / Gratitude Phrase Coverage
- **File & Line Citation:** [.githooks/attribution-patterns.regex:61](../../../.githooks/attribution-patterns.regex#L61)
- **Description:**  
  In revision 12, Pattern 61 was introduced to catch gratitude clauses:

## 5. Conclusion & Recommendations

The revision 12 updates on PR #23 head `d996aac5b9d439d9f328d7f7b47a4c75ec540a91` successfully remediate all round 11 items (ADV23R11-01 through ADV23R11-06). Specifically, extensionless scripts starting with a UTF-8 BOM are now properly stripped and inspected; the data gate allowlist approach comprehensively gates non-allowlisted optimization and data formats; and bare Blackbox/Sweep footers, gratitude footers, credit trailers, and CodeGeeX/Granite are correctly detected.
