## Remaining findings

### 1. R8-01 — High — STRUCTURAL: the attribution gate cannot honor the D-61 bot-summary exception

**Locations at the reviewed head:** `xtask/src/attribution.rs:517` (event
conversion), `:650` (unconditional metadata scanning);
`.githooks/attribution-patterns.regex:49` and `:52` (summary-heading/comment
matching); `xtask/src/main.rs:116` (CLI/event entry point).
**Authority:** D-61 in the [decisions log](../03-decisions-log.md), and the
[ADR attribution section](../../architecture/adr/0001-repo-layout-and-ci-gates.md).

D-61 explicitly retains CodeRabbit's PR-description summaries and excludes bot
comments/summaries from attribution of authored work. ADR 0001 further requires
the exemption to apply only to the exact bot-managed block with verified edit
provenance, while continuing to reject spoofed markers and surrounding authored
credit. Revision 8 detects the bot's heading and markers, but implements no
provenance check or block exemption. `Range::from_event` discards the sender and
edit metadata, and `scan_range` scans every line of the complete body without
distinguishing its origin. There is no GitHub provenance lookup on this path.

**Concrete reproduction:** construct the following body at runtime, where `+`
means string concatenation and the lines are joined by newlines:

```text
"Implement M0 checks."
""
"<!-- This is an auto-generated comment: release notes by " + "coderabbit.ai -->"
"## Summary " + "by CodeRabbit"
""
"* Add checks."
"<!-- end of auto-generated comment: release notes by " + "coderabbit.ai -->"
```

Put that body in a `pull_request` event with `action = "edited"`,
`sender.login = "coderabbitai[bot]"`, `sender.type = "Bot"`, a clean title, and
both base/head SHAs equal to the reviewed head. Set `GITHUB_EVENT_NAME` and
`GITHUB_EVENT_PATH` to that event and run the reviewed binary's `attribution`
command. Observed: zero commits and added lines scanned, then **exit 1**, with
three body findings at lines 3, 4 and 7. Changing only the sender to an ordinary
user produces the identical result. The explicit `--body-file` path has the same
unconditional scanning behavior.

This is a synthetic event replay, not a claim that the reviewer caused a real bot
edit or authenticated the synthetic sender. It establishes that even the
bot-event path cannot preserve or verify provenance. A genuine bot-managed block
must reach the same unconditional rejection branch. The new shared attribution
test currently asserts rejection of these markers, without a positive
provenance-qualified PR-body test. The PR description also says the existing
automatic summary was removed, rather than demonstrating the required exception.

**Impact:** restoring the owner-approved integration makes routine bot summary
updates fail the attribution gate. Removing the integration changes D-61 rather
than implementing it. This is STRUCTURAL because the missing distinction is
between trusted bot-managed metadata and authored text, not another tool-name
spelling.

**Suggested change:** implement the ADR's provenance-qualified, precisely bounded
PR-body exception, retaining the integration. Keep the shared patterns for
authored footers, titles, commits and source lines. Add integration tests proving
that a verified bot-managed block passes, identical unverified/spoofed markers
fail, and authored credit before/after a valid block still fails. Document how
edit provenance is established; a supplied sender string or marker alone is not
proof. Amend the revision-8 addendum to describe the exception. No new owner
decision is needed to follow the existing D-61 rule.

## Enforcement and ADR limitation assessment

The structural fixes address the reported linker-name and feature-resolution
gaps. The linker guard now rejects an allowed name shadowed by an OUT_DIR file
and checks trusted system scripts recursively under a restricted grammar.
Production-only builds exercise configurations hidden by dev-dependencies;
member-only builds exercise defaults hidden by workspace feature unification.
The adapter package/directory list, compiler forbid, root checks, doctest
attributes and linker restrictions remain complementary controls around local
code. They do not establish that registry dependencies contain no unsafe Rust.

The `link_search_roots` setting contains fixed `/lib`, `/lib32`, `/lib64`,
`/libx32` and corresponding `/usr/lib*` paths, not an arbitrary wildcard. Trusting
these standard OS locations is appropriate for resolving the hosted image's C
runtime and its legitimate linker scripts at M0. Canonical, component-aware
directory checks avoid a sibling-prefix exemption, and build/temp directories
remain excluded. The allowlist still controls requested library names; trusting
a root does not directly authorize a request for a Python/Julia library name.

These paths are **location trust, not an isolation boundary**. GitHub documents
[passwordless sudo on Linux and macOS hosted VMs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#administrative-privileges).
Consequently, calling this an “unprivileged” job accurately describes its token
and lack of secrets, but does not mean its process cannot elevate within the
disposable VM. A malicious build script can alter system libraries, the Rust
sysroot or the guard itself; standard library ownership does not prevent that.
Risk 5 already acknowledges job tampering. Risk 11 should explicitly name the
configured OS roots as well as compiler/sysroot directories and clarify hosted
sudo. This is a documentation qualification of the existing risk, not a new
escape through ordinary OUT_DIR linking. Read-only tokens, separate trusted
jobs, protected workflows and exact-head code review remain essential.

With that qualification, risks 1–5, 7, 9–11 describe reasonable bounds for M0's
disposable hosted jobs. Corrected risk 6 accurately limits compiler evidence to
host configurations; corrected risk 8 accurately excludes some combinations of
multiple non-default features. The build gate is not a proof over every Cargo
configuration. Refusing response files and non-system scripts is a defensible
fail-closed M0 limit. M1's D-65 runner isolation evidence remains a separate
activation condition under NFR-12.

Workflow interpreter detection now covers the reported families and variants;
it remains a lexical shell lint, supplemented by protected workflow review.
Content signatures strengthen provenance enforcement but cannot determine the
licence or meaning of every arbitrary text/binary payload. The manifest,
declared-format checks and dataset review remain necessary. Attribution remains
a finite vocabulary with human/prose controls. Those ordinary bounds are
acceptable for M0; the missing explicit D-61 exception is a rule conflict and
cannot be accepted as another documented limitation.
