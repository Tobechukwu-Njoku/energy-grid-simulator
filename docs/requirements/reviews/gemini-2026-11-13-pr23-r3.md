## 2. Verification of Workflow Security & Trusted Gates Architecture

A comprehensive security audit of [.github/workflows/trusted-gates.yml](/home/njotob/.t3/projects/Dev%20-%20GitHub%20-%20Energy/t3-42e6e1ed-40c820d94ee3caea/.github/workflows/trusted-gates.yml) was performed to ensure that the `pull_request_target` trigger does not expose the execution environment to untrusted pull-request code:

1. **Checkout Scope:** Steps 1 and 2 check out `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1` without a `ref` parameter, defaulting to the target branch (`main`). Step 2 explicitly fetches `refs/remotes/origin/main` and runs `git checkout --quiet --detach refs/remotes/origin/main`.
2. **Data-Only Head Fetch:** The pull request head is fetched into a dedicated Git ref (`refs/remotes/pull/head`) strictly as Git object data. At no point is the pull request branch checked out into the working directory.
3. **Execution Tree:** `cargo run --locked --quiet -p xtask -- review` and `approval` are compiled and executed solely from the `main` checkout, using the toolchain pinned on `main`.
4. **Git Object Inspection:** `xtask review` and `xtask approval` read pull-request commit objects, diffs, and trees via plumbing commands (`git rev-list`, `git ls-tree`, `git diff`, `git cat-file`, `git show`), parsing output as plain text. No code, build scripts, proc macros, or binaries from the PR head are compiled or executed.
5. **Fail-Closed Guarantee:** If `xtask/Cargo.toml` is missing on `main`, `trusted-gates.yml` exits with code 1 immediately.

Conclusion: The `trusted-gates.yml` architecture is secure and does not execute untrusted pull-request code.

## 3. Detailed Findings (ADV23R3-01 .. ADV23R3-07)

### ADV23R3-01: Precomposed Latin Diacritics and Accents Evade Unicode Normalization and Confusable Folding

- **Severity:** HIGH
- **Area:** D-52 Attribution Policy / Unicode Normalization
- **File & Line Citation:** [xtask/src/attribution.rs:189-202](/home/njotob/.t3/projects/Dev%20-%20GitHub%20-%20Energy/t3-42e6e1ed-40c820d94ee3caea/xtask/src/attribution.rs#L189-L202)
- **Description:**  
  `attribution::normalise()` performs normalization as follows:
  ```rust
  for character in line
      .nfkc()
      .filter(|character| !is_invisible(*character) && !is_combining(*character))
  {
      fold_char(character, l_as, &mut out);
  }
  ```
  1. `line.nfkc()` is a *composition* normalization form (Compatibility Decomposition, followed by Canonical Composition). Standard precomposed Latin characters with accents—such as `á` (`U+00E1`), `é` (`U+00E9`), `í` (`U+00ED`), `ó` (`U+00F3`), `ú` (`U+00FA`), `ō` (`U+014D`), `ī` (`U+012B`)—are canonical in NFKC and remain composed.
  2. Because the accents remain precomposed into the base letter, `!is_combining(*character)` evaluates to `true` (combining mark characters `U+0300..=U+036F` are not present).
  3. `fold_char()` invokes Unicode UTS #39 skeletons (`unicode_security::confusable_detection::skeleton`). Under UTS #39, accented Latin letters are considered phonemically distinct graphemes, not visual confusables with ASCII letters (e.g. `skeleton("á")` produces `"á"`, not `"a"`).
  4. Consequently, `fold_char()` pushes `á` untouched. Pattern 4 in `.githooks/attribution-patterns.regex` requires ASCII `claude`. Any footer or trailer using accented vowels (e.g., `Generated with Cláude Code`, `Co-Authored-By: Cláude`, `Co-authored-by: Gémíní`, `Cōpīlōt`) completely evades attribution detection.
- **Minimal Test Input:**
  ```text
  Generated with Cláude Code
  ```
  *(where `á` is `\u{00e1}`)*
- **Command Run:**
  ```bash
  cargo run --locked --quiet -p xtask -- attribution --base HEAD~1 --head HEAD --title "Generated with Cláude Code"
  ```
- **Observed Output:**
  ```text
  scanned 1 commit(s), 121 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  ```
  The check passed without flagging any attribution violation.
- **Suggested Fix:**  
  Decompose characters using NFD (Canonical Decomposition) or NFKD prior to filtering out combining marks (`\p{M}` or `is_combining`), so accented Latin characters decompose into base letters plus combining marks, stripping the accent and leaving the unaccented ASCII prototype.

### ADV23R3-02: AI Vendor Prefixes on Model Names (`Google Gemini`, `OpenAI ChatGPT`, `Anthropic Claude`, `Meta Llama`) Evade Trailer and Footer Patterns

- **Severity:** HIGH
- **Area:** D-52 Attribution Policy / Trailer & Footer Syntax
- **File & Line Citation:** [.githooks/attribution-patterns.regex:2, 4](/home/njotob/.t3/projects/Dev%20-%20GitHub%20-%20Energy/t3-42e6e1ed-40c820d94ee3caea/.githooks/attribution-patterns.regex#L2-L4)
- **Description:**  
  In `.githooks/attribution-patterns.regex`:
  - Pattern 1 matches trailers of the form `Co-authored-by: <model>`. While `copilot` was given an optional vendor prefix `(?:github[\s_-]*)?copilot`, other models lack vendor prefixes. The model list requires `claude`, `gemini`, `gpt`, etc., directly following `by|with:`.
  - Pattern 4 matches footers of the form `Generated with <model>`. It requires `claude`, `gemini`, etc., directly following `using|with|by`.
  When a footer or trailer includes the vendor name (e.g. `Generated with Google Gemini`, `Generated with OpenAI ChatGPT`, `Co-Authored-By: Anthropic Claude`, `Co-Authored-By: Google Gemini`, `Generated with Meta Llama`), neither Pattern 1 nor Pattern 4 matches because the vendor word (`Google`, `Anthropic`, `OpenAI`, `Meta`) precedes the model name and is not an allowed keyword prefix.
- **Minimal Test Inputs:**
  - Input 1: `Generated with Google Gemini`
  - Input 2: `Co-Authored-By: Anthropic Claude`
- **Commands Run:**
  ```bash
  cargo run --locked --quiet -p xtask -- attribution --base HEAD~1 --head HEAD --title "Generated with Google Gemini"
  cargo run --locked --quiet -p xtask -- attribution --base HEAD~1 --head HEAD --title "Co-Authored-By: Anthropic Claude"
  ```
- **Observed Output:**
  ```text
  scanned 1 commit(s), 121 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  ```
  Both inputs were accepted without error.
- **Suggested Fix:**  
  In `.githooks/attribution-patterns.regex`, permit optional vendor prefixes across all model patterns:
  `(?:\b(?:google|openai|anthropic|meta|microsoft)[\s_-]+)?(?:claude|gemini|gpt|chatgpt|codex|llama|...)`.

### ADV23R3-03: Non-Rust Comment Syntaxes (PowerShell `<# ... #>`, Lua `--[[ ... ]]`, ARM Assembly `@ ...`) Evade Markup Stripping

- **Severity:** HIGH
- **Area:** D-52 Attribution Policy / Non-Rust File Markup Stripping
- **File & Line Citation:** [xtask/src/attribution.rs:209-239, 317-333](/home/njotob/.t3/projects/Dev%20-%20GitHub%20-%20Energy/t3-42e6e1ed-40c820d94ee3caea/xtask/src/attribution.rs#L209-L239)
- **Description:**  
  `strip_markup()` in `xtask/src/attribution.rs` strips standard comment markers (`//`, `/*`, `#`, `--`, `<!--`, etc.) to detect attribution in source comments. However, several comment formats common in scripting, tooling, and power grid simulation files are not handled:
  1. **PowerShell block comments (`<# ... #>`):** `PREFIXES` does not contain `<#` and `SUFFIXES` does not contain `#>`. Furthermore, `untag()` requires inner text to start with an ASCII alphabetic character or `!`, so `<#` is preserved.
  2. **Lua / SQL multiline comments (`--[[ ... ]]`):** `PREFIXES` strips `--`, leaving `[[ ... ]]`. `delink()` partially parses `[` but leaves `[ Generated with Claude Code ]`, which is rejected by Pattern 4's line anchors.
  3. **ARM / GNU Assembly line comments (`@`):** In ARM assembly files, `@` is the single-line comment marker. It is omitted from `PREFIXES` and `TRAILING_MARKERS`.
  In each case, added lines containing attribution prefixed with these comment markers evade detection.
- **Minimal Test Inputs:**
  - Input 1: `<# Generated with Claude Code #>`
  - Input 2: `--[[ Generated with Claude Code ]]`
  - Input 3: `@ Generated with Claude Code`
- **Commands Run:**
  ```bash
  cargo run --locked --quiet -p xtask -- attribution --base HEAD~1 --head HEAD --title "<# Generated with Claude Code #>"
  cargo run --locked --quiet -p xtask -- attribution --base HEAD~1 --head HEAD --title "--[[ Generated with Claude Code ]]"
  cargo run --locked --quiet -p xtask -- attribution --base HEAD~1 --head HEAD --title "@ Generated with Claude Code"
  ```
- **Observed Output:**
  ```text
  PASS: attribution policy (D-52)
  ```
  All three inputs passed inspection.
- **Suggested Fix:**  
  Add `<#`, `#>`, `--[[`, `]]`, and `@` to `PREFIXES`, `SUFFIXES`, and `TRAILING_MARKERS` in `xtask/src/attribution.rs`.

### ADV23R3-05: Inherited Workflow- and Job-Level `defaults.run.shell: python` Bypasses Python Shell Detection

- **Severity:** HIGH
- **Area:** CI Workflow Hardening / Python Ban (D-73)
- **File & Line Citation:** [xtask/src/workflows.rs:508-517](/home/njotob/.t3/projects/Dev%20-%20GitHub%20-%20Energy/t3-42e6e1ed-40c820d94ee3caea/xtask/src/workflows.rs#L508-L517)
- **Description:**  
  Decision D-73 forbids executing Python in CI runners outside dedicated offline tools.
  `xtask/src/workflows.rs:508-517` checks:
  ```rust
  if let Some(shell) = get(step, "shell")
      && invokes_python(&scalar(shell))
  {
      findings.push(Finding::at(path, None, format!("{step_scope}: Python shell is not allowed (D-73)")));
  }
  ```
  This check inspects only explicit `shell:` properties on individual steps. It does not inspect `defaults.run.shell` at either the workflow scope or the job scope.
  In GitHub Actions, setting:
  ```yaml
  defaults:
    run:
      shell: python
  ```
  at the job or workflow level configures all child `run:` steps to execute via `python`. Unless a step's script text contains the literal substrings `python`, `pip`, or `.py`, `invokes_python()` evaluates to `false`. The entire job executes via Python without triggering any finding.
- **Minimal Test Input:**
  A workflow with job configuration:
  ```yaml
  defaults:
    run:
      shell: python
  steps:
    - run: |
        import sys
        sys.exit(0)
  ```
- **Observed Result:**  
  `check_workflow()` reports 0 findings; the inherited Python shell is ignored.
- **Suggested Fix:**  
  In `xtask/src/workflows.rs`, inspect `defaults.run.shell` at both workflow and job scope, reject Python shells defined there, and treat steps in jobs with inherited shells accordingly.

### ADV23R3-06: Index File Keys (`sha256_index_file`) in Dataset Manifests Bypass Provenance File Registration

- **Severity:** HIGH
- **Area:** D-56 Provenance & Research-Only Data
- **File & Line Citation:** [xtask/src/repository.rs:111-135](/home/njotob/.t3/projects/Dev%20-%20GitHub%20-%20Energy/t3-42e6e1ed-40c820d94ee3caea/xtask/src/repository.rs#L111-L135)
- **Description:**  
  In `xtask/src/repository.rs`, `FILE_KEYS` defines the keys used to extract dataset filenames from manifest tables:
  ```rust
  const FILE_KEYS: &[&str] = &[
      "filename", "file", "files", "relative_path", "local_name", "path", "paths",
  ];
  ```
  However, in existing repository manifests (such as `spikes/data-gathering/elexon/manifest.toml`), datasets declare their files via `sha256_index_file = "..."` (e.g. `sha256_index_file = "system_prices_sha256.txt"`).
  Because `sha256_index_file` is not in `FILE_KEYS`, `manifest_datasets()` produces `files: []` for all 12 datasets in `elexon/manifest.toml`.
  If a dataset using index files has `licence_status = "research-only"`, zero files are registered into `restricted` or `registry`. Any committed research-only index file or data file declared in this manner passes without being flagged by `cargo xtask provenance`.
- **Minimal Test Input:**
  A dataset manifest declaring:
  ```toml
  [[datasets]]
  name = "elexon-index"
  licence_status = "research-only"
  sha256_index_file = "system_prices_sha256.txt"
  ```
- **Observed Result:**  
  `manifest_datasets()` returns `files: []`. `system_prices_sha256.txt` is omitted from `restricted`, and committing the file triggers no research-only finding.
- **Suggested Fix:**  
  Add `"sha256_index_file"`, `"index_file"`, and `"index"` to `FILE_KEYS` in `xtask/src/repository.rs`.

### ADV23R3-07: Provenance Manifest File Discovery is Hardcoded to `manifest.toml` Only

- **Severity:** MEDIUM
- **Area:** D-56 Provenance Manifest Detection
- **File & Line Citation:** [xtask/src/repository.rs:730](/home/njotob/.t3/projects/Dev%20-%20GitHub%20-%20Energy/t3-42e6e1ed-40c820d94ee3caea/xtask/src/repository.rs#L730)
- **Description:**  
  In `xtask/src/repository.rs:730`:
  ```rust
  if name == "manifest.toml" {
      manifests += 1;
      let (found, entries) = manifest_records(path, &text);
      findings.extend(found);
      records.extend(entries);
  }
  ```
  The provenance check exclusively parses files named exactly `manifest.toml` (and `sources.tsv`). If a dataset directory provides a manifest named `provenance.toml`, `data-manifest.toml`, `dataset.toml`, or `manifest.json`, the file is not parsed as a manifest. Any `research-only` dataset records declared within it are not registered, creating a false negative where restricted datasets declared under alternative standard manifest names are ignored.
- **Minimal Test Input:**
  A file `spikes/data/provenance.toml` declaring `licence_status = "research-only"` for `restricted_sample.csv`.
- **Observed Result:**  
  `repository::provenance()` skips `provenance.toml`; no records are registered in `registry`.
- **Suggested Fix:**  
  In `xtask/src/repository.rs:730`, match standard manifest patterns:
  `if name == "manifest.toml" || name.ends_with("-manifest.toml") || name == "provenance.toml" || name == "datasets.toml"`.
