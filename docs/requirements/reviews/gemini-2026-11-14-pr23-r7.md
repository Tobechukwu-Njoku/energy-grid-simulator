## 2. Verification of CI Quality Checks & Architecture Scope

A comprehensive adversarial robustness audit was conducted across PR #23 at revision 7 head `f986bbc48b23390ca50f4b22065313bcb08d94ea`:

1. **Compiler-Enforced Build Gate (`xtask/src/build_gate.rs`) & Unsafe Boundary (ADR 0001, NFR-10):**
   - Verified that `is_adapter()` now validates against the closed list of reviewed adapters declared in `xtask/policy/repository.toml` (`egs-solver-highs`, `egs-solver-gurobi`, `egs-solver-xpress`, `egs-solver-cuopt`).
   - Verified that build scripts (`build.rs`) are never exempt from compiler-enforced `-F unsafe_code`.
2. **Linker Guard Implementation (`xtask/src/build_gate.rs`) & Native Runtime Allowlist (NFR-10):**
   - Verified that the linker guard inspects `-framework`, `-weak_framework`, `-needed_framework`, `-reexport_framework`, `-lazy_framework`, `-upward_framework`, and `-Wl,-framework,` arguments against `link_frameworks` in `gates.toml`.
   - Verified that linker response files (`@file`), scripts, and driver redirection are refused.
3. **CI Workflow Checks, Environment Hardening & Script Interpreter Policy (NFR-12, D-73):**
   - Verified that file commands (`$GITHUB_ENV`, `$GITHUB_PATH`, `$GITHUB_OUTPUT`, `$GITHUB_STATE`, `$GITHUB_STEP_SUMMARY`) cannot be written outside allowlisted lines, and shell indirection is detected.
   - Verified that the `build-gate` step runs last in its job without `id` or `outputs`, and strips file command variables before launching `cargo`.
   - However, workflow script validation in `invokes_python()` strictly checks `python`, `pip`, and `.py`, omitting alternative runtimes such as Julia (`julia`), Python launcher (`pythonw`), and PyPy (`pypy`/`pypy3`).
4. **Trusted Gates Isolation (`.github/workflows/trusted-gates.yml`):**
   - Verified that `trusted-gates.yml` runs from `main` via `pull_request_target`, strictly checks out `refs/remotes/origin/main`, fetches the PR head only as Git data objects into `refs/remotes/pull/head`, and executes `xtask` compiled from `main`. Untrusted PR code is never checked out, compiled, or executed by trusted gates.
5. **Review and Approval Gates (`xtask/src/review_gates.rs`, D-74):**
   - Verified independent review pairing requirements against `xtask/policy/review.toml`, that Gemini cannot supply approval, and that protected path modifications require owner exact-head approval under D-74.
   - However, in `spoofed_gate_names()`, matching trusted gate IDs against PR workflow job IDs (`gate == id`) is case-sensitive, whereas GitHub check run names take the job ID when `name:` is absent. PR workflow jobs with IDs like `Policy-Approval` or `Independent-Review` bypass spoofed gate detection.
6. **Provenance and Dataset Gate (`xtask/src/repository.rs`, D-56):**
   - Verified that `has_component(path, "raw")` lowercases both directory components and `"raw"`, rejecting all casing variants.
   - However, `data_extensions` in `xtask/policy/repository.toml` includes traditional compression extensions (`.gz`, `.bz2`, `.xz`, `.7z`, `.tar`), but omits standard modern dataset compression formats `.zst` / `.zstandard` (Zstandard) and `.lz4`, allowing unvetted compressed datasets to be committed outside the sample allowlist without provenance records.
7. **Attribution Pattern Coverage (`.githooks/attribution-patterns.regex`, D-52):**
   - Verified pattern coverage for trailers and footers. Five false-negative gaps remain: omission of `prompted` from footer `ATTRIBUTE`, omission of `input` and `guidance` from `HELP` prepositions, missing vendor email domains for `continue.dev` and `supermaven.com`, missing dictionaries for `v0` and `Augment Code`, and lack of generic `coding assistant` coverage.

### ADV23R7-01: Case-Sensitive Job ID Matching in `spoofed_gate_names` Allows PR Workflows to Spoof Trusted Gates When `name:` Is Omitted

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** CI Review Gates / Spoofed Check Detection (F1, ADV23R-08, D-74)
- **File & Line Citation:** [xtask/src/review_gates.rs:633-635](../../../xtask/src/review_gates.rs#L633-L635)
- **Description:**  
  Decision D-74 and finding F1 prohibit pull-request workflows from defining jobs whose status checks spoof the trusted review and approval gates (`policy-approval`, `independent-review`).  
  In `xtask/src/review_gates.rs:604-645`, `spoofed_gate_names()` evaluates workflow jobs:
  ```rust
  for (id, job) in jobs {
      let id = id.as_str().unwrap_or_default();
      let name = job
          .as_hash()
          .and_then(|hash| hash.get(&Yaml::String("name".into())))
          .and_then(Yaml::as_str)
          .unwrap_or_default();
      if trusted_jobs
          .iter()
          .any(|gate| gate == id || name.eq_ignore_ascii_case(gate))
      {
          findings.push(Finding::at(
              path.as_str(),
              None,
              format!("job `{id}` reuses the name of trusted gate; rename it"),
          ));
      }
  }
  ```
  Notice that while `name` is compared with `name.eq_ignore_ascii_case(gate)`, the job key `id` is compared with exact case sensitivity: `gate == id`.  
  In GitHub Actions, when a job omits the `name:` property, GitHub uses the job's ID as the check run context name. Furthermore, branch protection check matching on GitHub evaluates context names.  
  If a PR workflow defines:
  ```yaml
  jobs:
    Policy-Approval:
      runs-on: ubuntu-24.04
      steps:
        - run: echo ok
  ```
  1. `trusted_jobs` contains `"policy-approval"` and `"independent-review"`.
  2. `gate == id` compares `"policy-approval"` to `"Policy-Approval"`, which evaluates to `false`.
  3. `name` is empty (`""`), so `name.eq_ignore_ascii_case(gate)` evaluates to `false`.
  4. `spoofed_gate_names()` reports 0 findings.
  
  The untrusted PR workflow creates a status check named `Policy-Approval`, bypassing spoofed gate detection entirely.
- **Minimal Test Input:**
  In `.github/workflows/spoof.yml`:
  ```yaml
  name: spoof
  on: [pull_request]
  permissions:
    contents: read
  jobs:
    Policy-Approval:
      runs-on: ubuntu-24.04
      steps:
        - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1
          with:
            persist-credentials: false
        - run: echo "bypass"
  ```
- **Command Run:**
  Evaluating `spoofed_gate_names(&workflows, &trusted_files, &trusted_jobs)` where `trusted_jobs` includes `"policy-approval"`.
- **Observed Output:**
  ```text
  findings: [] (0 findings reported; job `Policy-Approval` accepted without error)
  ```
  Contrast with `name: policy-approval` or `id: policy-approval`, which correctly generates:
  ```text
  job `policy-approval` reuses the name of trusted gate; rename it
  ```
- **Suggested Fix:**  
  In `xtask/src/review_gates.rs:634`, use case-insensitive comparison for both `id` and `name`:
  ```rust
  if trusted_jobs
      .iter()
      .any(|gate| gate.eq_ignore_ascii_case(id) || name.eq_ignore_ascii_case(gate))
  ```

### ADV23R7-02: Provenance Gate (D-56) Omits Standard Dataset Compression Extensions (`.zst`, `.lz4`), Permitting Unvetted Compressed Datasets

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** Provenance & Dataset Gate (D-56)
- **File & Line Citation:** [xtask/policy/repository.toml:35-41](../../../xtask/policy/repository.toml#L35-L41), [xtask/src/repository.rs:718-739](../../../xtask/src/repository.rs#L718-L739)
- **Description:**  
  Decision D-56 prohibits committing datasets outside allowlisted open-commercial sample paths (`open_commercial_data = ["spikes/data/samples/*"]`) or exact metadata files (`data_metadata_files`).  
  In `xtask/policy/repository.toml`, `data_extensions` enumerates recognized dataset extensions, including legacy compression formats:
  ```toml
  data_extensions = [
      ".csv", ".tsv", ".parquet", ".feather", ".arrow", ".xlsx", ".xls", ".ods", ".zip",
      ".gz", ".bz2", ".xz", ".7z", ".tar", ".nc", ".cdf", ".grib", ".grib2", ".grb", ".h5",
      ".hdf5", ".mat", ".m", ".npy", ".npz", ".pkl", ".pickle", ".json", ".jsonl",
      ".ndjson", ".xml", ".raw", ".rawx", ".sav", ".dyr", ".epc", ".sqlite", ".db",
      ".dbf", ".shp", ".gpkg", ".kml", ".kmz", ".pbf", ".osm", ".geojson", ".pdf",
  ]
  ```
  In modern data engineering and scientific computing, Zstandard (`.zst`, `.zstandard`) and LZ4 (`.lz4`) are two of the most widely adopted compression formats for tabular, timeseries, and network data (e.g. Parquet/CSV/JSON datasets compressed with Zstandard).  
  Because `.zst` and `.lz4` are omitted from `data_extensions`:
  1. A file committed as `spikes/grid_metrics.zst` or `spikes/transmission_data.lz4` does not match any entry in `data_extensions`.
  2. In `xtask/src/repository.rs:720`, `is_data` evaluates to `false`.
  3. `cargo xtask provenance` gives a clean pass with exit code 0.
  
  In contrast, committing the identical uncompressed or gzip-compressed file (`spikes/grid_metrics.parquet` or `spikes/grid_metrics.csv.gz`) is correctly rejected with exit code 1.
- **Minimal Test Input:**
  Tracked file `spikes/grid_metrics.zst`.
- **Command Run:**
  ```bash
  cargo xtask provenance
  ```
- **Observed Output:**
  ```text
  PASS: provenance/secrets/data (D-56)
  ```
  Exit code 0.  
  Contrast with `spikes/grid_metrics.parquet`:
  ```text
  FAIL: provenance/secrets/data (D-56)
    spikes/grid_metrics.parquet: data file outside the allow-listed open-commercial sample paths (D-56)
  ```
- **Suggested Fix:**  
  Add modern dataset compression extensions `.zst`, `.zstandard`, and `.lz4` to `data_extensions` in `xtask/policy/repository.toml`.

### ADV23R7-03: Workflow Policy Interpreter Validation in `invokes_python` Omits Julia (`julia`), Pythonw (`pythonw`), and PyPy (`pypy`/`pypy3`)

- **Classification:** STRUCTURAL
- **Severity:** HIGH
- **Area:** CI Workflow Hardening / Non-Rust Interpreter Enforcement (NFR-10, NFR-12, D-73)
- **File & Line Citation:** [xtask/src/workflows.rs:241-252, 611-616](../../../xtask/src/workflows.rs#L241-L252)
- **Description:**  
  Decision D-73 mandates: "Rust for product code, tooling, CI and tests. Python allowed only in spikes/ and offline reference validators." Decisions NFR-10 and ADR 0001 forbid Python and Julia runtimes.  
  In `xtask/src/workflows.rs:241-252`, `invokes_python()` inspects script words:
  ```rust
  fn invokes_python(script: &str) -> bool {
      script
          .split(|c: char| !(c.is_ascii_alphanumeric() || c == '.' || c == '_'))
          .any(|word| {
              word == "python"
                  || word.starts_with("python3")
                  || word.starts_with("python2")
                  || word == "pip"
                  || word == "pip3"
                  || word.ends_with(".py")
          })
  }
  ```
  This check contains several omissions:
  1. `word == "python"` uses exact equality. The standard Python windowed/headless executable `pythonw` fails `word == "python"` and does not start with `"python3"` or `"python2"`.
  2. Alternative Python implementations such as PyPy (`pypy`, `pypy3`), which are preinstalled on GitHub Actions runners, do not start with `"python3"`.
  3. Julia (`julia`), which is explicitly banned alongside Python in NFR-10, is entirely omitted from workflow script checking.
  
  When a workflow script executes `pypy3 -c "..."` or `julia -e "..."`, `invokes_python()` returns `false`, and `cargo xtask policy` gives a clean pass.
- **Minimal Test Inputs:**
  - Input 1: Workflow step `run: pypy3 -c "print(1)"`
  - Input 2: Workflow step `run: julia -e "println(1)"`
- **Commands Run:**
  ```bash
  cargo xtask policy
  ```
- **Observed Output:**
  ```text
  PASS: unsafe-scope
  PASS: manifests
  PASS: workflows
  PASS: python
  PASS: codeowners
  ```
  Both inputs pass with exit code 0.  
  Contrast with `python3 -c "print(1)"`:
  ```text
  FAIL: workflows
    .github/workflows/test.yml: job `test` step 2: CI must not run Python (D-73); use cargo xtask
  ```
- **Suggested Fix:**  
  Expand `invokes_python` in `xtask/src/workflows.rs` to detect `pythonw`, `pypy`, `pypy3`, and `julia`:
  ```rust
  fn invokes_untrusted_interpreter(script: &str) -> bool {
      script
          .split(|c: char| !(c.is_ascii_alphanumeric() || c == '.' || c == '_'))
          .any(|word| {
              word == "python"
                  || word.starts_with("python")
                  || word.starts_with("pypy")
                  || word == "pip"
                  || word.starts_with("pip")
                  || word == "julia"
                  || word.ends_with(".py")
                  || word.ends_with(".jl")
          })
  }
  ```

### ADV23R7-04: Attribution Footers Using `Prompted by <Model>` or `Prompted with <Model>` Evade Pattern 47

- **Classification:** ATTRIBUTION-SPELLING
- **Severity:** HIGH
- **Area:** D-52 Attribution Policy / Prompting Footers
- **File & Line Citation:** [.githooks/attribution-patterns.regex:36, 47](../../../.githooks/attribution-patterns.regex#L36-L47)
- **Description:**  
  In `.githooks/attribution-patterns.regex`, Pattern 45 recognizes `Prompted by:` and `Prompted with:` in git commit trailers:
  ```regex
  ^\s*{{DECOR}}(?:\p{L}+[\s{{DASH}}]+){1,4}(?:by|with|from)\s*:\s*...
  ```
  However, in attribution footer sentences matching Pattern 47:
  ```regex
  ^\s*{{DECOR}}(?:\*{1,2})?{{ATTRIBUTE}}\s+{{BY}}\s*:?\s*{{HELP}}?(?:{{NAME}}|\[{{NAME}}\]\(https?://[^\s)]+\))[.!]?(?:\*{1,2})?\s*$
  ```
  `ATTRIBUTE` (line 36) lists attribution verbs:
  ```regex
  define ATTRIBUTE = (?:generated|produced|written|wrote|authored|assisted|powered|created|made|drafted|built|crafted|developed|coded|implemented|prepared|composed|designed|engineered|edited|refactored|pair[{{DASH}}\s]*programm?(?:ed|ing)|co[{{DASH}}\s]*(?:written|authored|developed|created|programm?ed|wrote)|collaborated|collaboration|paired|partnered|teamed(?:[{{DASH}}\s]*up)?|helped|aided|supported)
  ```
  Notice that `prompted` is missing from `ATTRIBUTE`.  
  Developers commonly credit AI models using footer sentences such as `Prompted by Claude` or `Prompted with Claude`. Because `prompted` is omitted from `ATTRIBUTE`, these footers fail to match Pattern 47 and pass completely undetected.
- **Minimal Test Inputs:**

  ```text
  PASS: attribution policy (D-52)
  scanned 0 commit(s), 0 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  ```
  Both inputs passed with exit code 0.  
  Contrast with `Prompted-by: Claude`, which fails with exit code 1.
- **Suggested Fix:**  
  Add `prompted` to `ATTRIBUTE` in `.githooks/attribution-patterns.regex:36`.

### ADV23R7-05: Attribution Footers with Assistance Nouns `with input from <Model>` or `with guidance from <Model>` Evade Pattern 47

- **Classification:** ATTRIBUTION-SPELLING
- **Severity:** HIGH
- **Area:** D-52 Attribution Policy / Assistance Noun Variations
- **File & Line Citation:** [.githooks/attribution-patterns.regex:27, 38, 47](../../../.githooks/attribution-patterns.regex#L27-L47)
- **Description:**  
  In `.githooks/attribution-patterns.regex`, `QUALIFIER` (line 27) explicitly includes assistance nouns `input` and `guidance`.  
  However, in Pattern 47 footers:
  ```regex
  define HELP = (?:(?:the\s+|some\s+)?(?:help|assistance|aid|support)\s+(?:of|from)\s+)
  ```
  `HELP` strictly recognizes only `help`, `assistance`, `aid`, and `support`. It omits `input` and `guidance`.  
  When an author writes an attribution footer using standard professional phrasing:
  - `Written with input from Claude`
  - `Written with guidance from Claude`
  - `Developed with the guidance of Claude`
  
  `HELP` fails to match. Because `input` or `guidance` precedes `from`, `BY` (`with`) cannot consume `input from`. Pattern 47 fails to match, and the attribution passes undetected.
- **Minimal Test Inputs:**
  - Input 1: `Written with input from Claude`
  - Input 2: `Written with guidance from Claude`
- **Commands Run:**
  ```bash
  cargo xtask attribution --base HEAD --head HEAD --title "Written with input from Claude"
  cargo xtask attribution --base HEAD --head HEAD --title "Written with guidance from Claude"
  ```
- **Observed Output:**
  ```text
  scanned 0 commit(s), 0 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  scanned 0 commit(s), 0 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  ```
  Both inputs passed with exit code 0.  
  Contrast with `Written with help from Claude`, which correctly fails with exit code 1.
- **Suggested Fix:**  
  Add `input` and `guidance` to `HELP` in `.githooks/attribution-patterns.regex:38`:
  ```regex
  define HELP = (?:(?:the\s+|some\s+)?(?:help|assistance|aid|support|input|guidance)\s+(?:of|from)\s+)
  ```

### ADV23R7-07: Autonomous Developer Coding Assistants `v0` (Vercel) and `Augment` / `Augment Code` Omitted from Dictionaries

### ADV23R7-08: Generic Coding Assistant Attributions Without Model or Vendor Evade Trailer and Footer Patterns

- **Classification:** ATTRIBUTION-SPELLING
- **Severity:** HIGH
- **Area:** D-52 Attribution Policy / Generic Identity Tokens
- **File & Line Citation:** [.githooks/attribution-patterns.regex:21-25, 30, 41, 47](../../../.githooks/attribution-patterns.regex#L21-L47)
- **Description:**  
  In `.githooks/attribution-patterns.regex:30`, `GENERIC` matches assistants named without a model token:
  ```regex
  define GENERIC = (?:(?:{{VENDOR}}(?:['\x{2019}]s)?[\s_-]*(?:ai|intelligence|llms?|assistant|agent|models?)|(?:gen[\s_-]*)?ai|a\.i\.|llms?|chat[\s_-]*bots?|(?:large[\s_-]+)?language[\s_-]+models?)(?![\p{L}\p{N}]))
  ```
  Notice that `GENERIC` requires either a vendor prefix before `assistant|agent|models?`, or one of the explicit tokens `ai`, `llm`, `chatbot`, `language model`.  
  Developers commonly credit generic coding tools without a vendor prefix using terms like `coding assistant`, `code assistant`, or `programming assistant`:
  - `Co-Authored-By: Coding Assistant`
  - `Co-Authored-By: Code Assistant`
  - `Generated by a coding assistant`
  
  Because none of these contains the literal word `ai`, `llm`, `chatbot`, or a vendor name:
  1. `GENERIC` fails to match.
  2. `Co-Authored-By: Coding Assistant` passes Pattern 41 because it matches neither `NAME` nor `IDNAME` (it has no email).
  3. `Generated by a coding assistant` passes Pattern 47.
  
  Both inputs pass undetected.
- **Minimal Test Inputs:**
  - Input 1: `Co-Authored-By: Coding Assistant`
  - Input 2: `Generated by a coding assistant`
- **Commands Run:**
  ```bash
  cargo xtask attribution --base HEAD --head HEAD --title "Co-Authored-By: Coding Assistant"
  cargo xtask attribution --base HEAD --head HEAD --title "Generated by a coding assistant"
  ```
- **Observed Output:**
  ```text
  scanned 0 commit(s), 0 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  scanned 0 commit(s), 0 added line(s), title=yes, body=no
  PASS: attribution policy (D-52)
  ```
  Both inputs passed with exit code 0.  
  Contrast with `Generated by an AI assistant`, which correctly fails with exit code 1.
- **Suggested Fix:**  
  Include `(?:coding|code|programming)[\s_-]+(?:assistant|agent|bot)` in `GENERIC`.
