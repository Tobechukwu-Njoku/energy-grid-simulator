## R15V4-01 — BLOCKING: a backtick inside an earlier attribute still truncates the password

**Severity:** high. **Locations:** `xtask/src/secrets/credentials.rs:174`, `:177`,
`:183`, `:193`, `:325`. **Scope:** obvious bypass of R15V2-01/R15V3-02, not a new
credential family or an additional general review requirement.

The new opener regex binds a candidate delimiter to assignment-shaped text,
but that text can itself be part of an earlier connection attribute's literal
value. It still does not establish that the delimiter belongs to Markdown.

The scratch reproduction is an ordinary Rust string holding the same
semicolon-delimited connection attributes as the previous fixtures. The server
attribute is unchanged. The username value begins with a literal backtick and
then contains a short, non-secret key/value-shaped fragment. The password value
is the existing standalone placeholder word followed by a literal backtick,
an internal space and `<LITERAL_SUFFIX>`. The whole password is a literal, not
the standalone placeholder. No complete literal credential is printed here.

At the password assignment, the opener regex starts at the backtick inside the
username, accepts the following key/value-shaped fragment and semicolon as
connection syntax, and treats the password's backtick as the closing delimiter.
`markdown_value` consequently returns only the placeholder word. The literal
classifier never sees the password's suffix and the scanner exits 0.

Fresh controls isolate the cause:

- The complete Rust source passes candidate `provenance` in a minimal repository.
- The same complete connection string in ordinary tracked text also passes.
- Replacing only the username with the earlier ordinary username makes the
  candidate reject with `local-connection-password`; the password is unchanged.
- Bracing the complete password makes the candidate reject with that same
  diagnostic, because the quoted/braced path skips Markdown trimming.
- Both the accepting Rust source and the ordinary-username control independently
  compile with Rust 2024 and execute an assertion that the complete literal
  password suffix is still present. This is not Rust string truncation.
- In a full clone of the exact candidate, the accepting source passes staged
  `provenance`, staged `all`, committed-checkout `provenance`, and the explicit
  range after the source is committed and then deleted. All four exit 0; the
  clean full-clone `all` control also passes.

The baseline at `112de8d` accepts the same source; this is **not** claimed as an
old-reject/new-accept regression. It is BLOCKING under the requested D-75 rule
because it directly restores the already-fixed behavior: a non-Markdown
backtick outside the password hides the literal suffix of an otherwise
recognized connection-password assignment. Moving the earlier marker into a
preceding attribute does not introduce a new decoder, syntax family or policy
requirement. The standalone complete password still rejects without that prefix.

Suggested correction: do not let an inferred Markdown opener inside an earlier
attribute value shorten the password in source/plain connection text. Add the
accepting source/text forms, the ordinary-username control and existing Markdown
placeholder controls to regression coverage. This report makes no candidate fix
and records no bootstrap attestation.
