## Remaining defects

### 1. R10-01 — High — CORE: composed XML entity references bypass RDF data detection

**Locations at reviewed head:** `xtask/src/repository.rs:754` (`expand_references`),
`:791` (entity replacement is not decoded recursively), `:861` (`is_cim_rdf`).
**Authority:** D-56 and ADR 0001's revision-10 RDF/XML content guarantee.
**Disposition:** must fix before bootstrap attestation.

The sniffer expands original character references and original entity references
once, but does not expand references inside inserted entity values. XML resolves
those references when constructing namespace names. A node-element-root RDF
serialization can therefore be valid RDF/XML without the sniffer seeing either
an `RDF` root or its own already-recognized RDF namespace substring. This is not
an unknown file format, encryption, a large-file bound, or a policy modification.

**Concrete test:** track `spikes/network-notes.txt` containing these 265 bytes:

```xml
<!DOCTYPE r:Description [
<!ENTITY tail "rdf-&#x73;yntax-ns#">
<!ENTITY ns "http://www.w3.org/1999/02/22-&tail;">
]>
<r:Description xmlns:r="&ns;" r:about="urn:grid:bus:1">
  <bus:nominalVoltage xmlns:bus="urn:grid:terms:">400</bus:nominalVoltage>
</r:Description>
```

Use the compiled revision-10 xtask and an unchanged revision-10 trusted tree:

```bash
git add -f spikes/network-notes.txt
xtask --repo "$PROBE" --policy "$TRUSTED_R10" provenance
xtask --repo "$PROBE" --policy "$TRUSTED_R10" all
```

**Observed:** both commands exit **0**. Provenance reports PASS; all also passes
unsafe scope, manifests, workflows, Python, CODEOWNERS and every documentation
category. Python's independent `xml.etree.ElementTree.fromstring` parser accepts
the document and resolves its root to
`{http://www.w3.org/1999/02/22-rdf-syntax-ns#}Description`.
The graph's property is an ordinary namespace-qualified element.

**Control:** change only `xmlns:r="&ns;"` to the literal resolved RDF namespace,
leaving the doctype intact. Provenance exits **1**, identifying CIM/RDF XML content
outside allowlisted sample paths. The original file has no matching provenance
record. Actual restricted network data serialized under this same namespace can
therefore be committed outside the permitted sample paths without a policy change.
No real restricted data was used in this review.

**Suggested change and regression:** resolve the supported internal entities and
character references transitively with explicit depth/output-size/cycle bounds,
or fail closed on XML entity constructs the sniffer cannot safely interpret.
Do not enable external entity/network resolution. Add this exact node-root fixture
to the unit and full provenance-command tests; include direct/nested references,
cycles and exhaustion controls. Both fixtures above must be rejected, while the
existing Markdown/code/SVG controls stay valid. Correct the ADR if any supported
syntax is intentionally excluded rather than enforced.

### 2. R10-02 — Medium — PERIPHERAL: the LCS size fallback grants unproven bot authorship

**Locations at reviewed head:** `xtask/src/attribution.rs:853` (fail-closed comment),
`:877` (diff-cell cutoff), `:962` (unmatched lines receive the current editor),
`:967` (that block becomes historically verified).
**Authority:** D-52, D-61; ADR 0001 revision-10 provenance claim and refined risk 12.
**Disposition:** a tracked follow-up is safe for the requested CORE M0 boundary;
owner acceptance must acknowledge that the documented authorship guarantee is too strong.

Above `MAX_DIFF_CELLS = 4_000_000`, `kept_lines` returns no matches for the changed
middle. `Provenance::apply` treats every unmatched line as newly added by the
current editor. When that editor is the bot, the supposed fail-closed fallback
*grants* authorship to unchanged human credit and records the block as verified.
The final unknown-editor replay then preserves that false provenance.

**Concrete test:** replay the original R9-01 v0, v1 and v2, with these changes:

```text

v1 Bot/coderabbitai: original genuine bot block (R9-01)

                    then 2,100 separate lines: L0, L1, ..., L2099
v3 Bot/coderabbitai: "Added outside header." + newline + exact v2
                    + newline + "Added outside footer."
```

The credit line is `footer(Generated, with, Claude)`. Read the real start/end
markers from `xtask/policy/attribution-exemptions.toml`; use the original R9-01
block, not replacement policy. Each version has a complete body and a matching
actor in the same saved GraphQL shape used by R9-01, newest node first. Include
the owner's original version at `createdAt`. Scan v3 with equal base/head:

```bash

  --base 88148f01fe91dc6f3f62577d3130ca1e3261fab9 \
  --head 88148f01fe91dc6f3f62577d3130ca1e3261fab9 \
```

**Observed:** exit **0**, attribution PASS. The human credit never changes in v3;

naming the human credit at body line 7. The ordinary original R9-01 regression

This is a synthetic history replay, not evidence that the reviewer induced a
real bot to make these outer edits. Exploitation requires a genuine bot version

**Suggested change and regression:** distinguish "proven unmatched/new" from
"unknown because diff budget exhausted". Unknown lines must never acquire bot

retain genuine bot-edit and historical-restoration controls. Amend the ADR's

## Overall enforcement and M0 limitation assessment

The design is substantially stronger than revision 9: trusted-main policy,
protected workflow/action paths, exact-head owner approval, immutable aggregator
steps, reserved published check identities, full env-name allowlisting, compiler
unsafe enforcement and resolved-library checks form useful separate controls.
The submitted regressions and independent probes confirm the old reported paths
are rejected. No new bypass of trusted-main check execution, owner approval,
unsafe enforcement or Python/Julia linking was established in this review.
R10-01 does establish a remaining CORE data-policy bypass, so the blanket
proposition that this head reliably enforces all project rules is not supportable.

The ADR accurately distinguishes important deployment and trust limitations:

- Risks 1–4: bootstrap is manual exact-SHA trust until main has the trusted
  workflow; required-check/branch-protection configuration is external; check
  source identity matters; owner review requires a trusted-run rerun. These are
  activation prerequisites, not reasons to count current red jobs as successful.
- Risks 5, 9 and 11: build scripts/proc macros execute as the hosted job user;
  trusted filesystem locations, including system library roots, are not a
  sandbox. Hosted passwordless sudo is explicitly acknowledged in revision 9.
  Read-only tokens, no secrets, separate trusted jobs and exact-head review are
  sensible M0 controls, but not proof against deliberately malicious build code.
- Corrected risk 8: multi-nondefault-feature-only configurations remain outside
  the finite build matrix. Root compiler forbids remain relevant when those
  targets are compiled. This is an explicit coverage limit, not a claim of
  exhaustive configuration testing. Risk 10's response-file failure is closed.
- Refined risk 12: trusting genuine GitHub history and bot actor type, and not
  equating a bot summary with code authorship, is reasonable under D-61.
  However, its claim that kept/unknown lines never become exempt is false at
  the diff budget boundary (R10-02); no compromised account is needed there.
- Revision 10's RDF claim also overstates the implementation: supported-looking
  character plus internal-entity references are not transitively resolved
  (R10-01). The stated 64 KiB bound is not the cause of this tiny counterexample.

The explicit same-user, host/configuration and finite-feature limitations are
acceptable for a reviewed **M0 baseline**, not a hostile-code sandbox, provided
activation prerequisites remain mandatory and the owner accepts that threat
model. Heuristic secrets/data scans and finite attribution vocabulary still need
reviewer judgment; a clean scan is not licence clearance or proof of no secrets.
That general limitation does not excuse the concrete already-supported-format
false negative and inaccurate specific guarantees above.
