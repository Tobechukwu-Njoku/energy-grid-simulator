## What holds

- **Nested and double-encoded keys.** `credential_key` (`credentials.rs:276`)
  decodes only while the byte length strictly shrinks, so it always terminates;
  lossy decoding of invalid UTF-8 (one escape becomes three bytes for U+FFFD) stops
  the loop rather than growing it. Values are still percent-decoded exactly once,
  and `nested_keys_outside_jdbc_and_values_decode_once` checks that an encoded
  `<password>` value stays literal. The JDBC rule is keyed on the fully decoded
  name, and is covered three levels deep.
- **Malformed keys.** Incomplete, non-hex, NUL and decoded-delimiter escapes in
  JDBC query keys fail closed, and their placeholder values stay accepted. The
  controls (`sslmode`, `%2573slmode`, `compass`, `password_hint`) pass.
- **Record terminators.** The pgpass loop now splits on CR and LF, and its offsets
  still add up for CRLF because the lone `\n` piece trims to an empty, non-matching
  line. Netrc comments now end at CR. Tests cover LF, CR and CRLF for pgpass,
  netrc and connection strings.
- **Header names.** Backtick-quoted and quote-quoted names, and `Proxy-Authorization`,
  are matched by the `\b` anchor. Values are still truncated at the captured
  quote, so JSON and code-literal headers keep their placeholder handling.
  Unfolding keeps byte lengths unchanged, so finding ranges stay exact.
- **`all` history range.** `run_provenance` is now shared by `provenance` and `all`.
  Without a range, `provenance_range(ctx, None)` is exactly what
  `repository::provenance` did before, so a plain local `all` behaves as it used to.
- **Attribution parity.** The change edits only the shared pattern file, so the
  hook and CI stay in step. `lowercase_bare_names_have_hook_and_ci_parity` runs the
  real hook on all 72 combinations: body stripping, subject rejection with the
  file left unchanged, and a retained human `Reviewed by` line. The range test
  checks that the commit message, title, body and an added line each produce a
  finding (four in total). The fixture keys are built at runtime, and the new
  `source_fixtures_do_not_embed_credentials` self-scan stops the scanner's own
  tests from embedding credentials.
- No secret-exemption or history-exemption entries were added or widened.

## Findings

1. **Medium — header unfolding crosses indented line boundaries and creates false
   positives (`credentials.rs:339`, `credentials.rs:376-393`).** The new unfolding
   loop replaces *every* LF that is followed by a space or tab, anywhere in the text
   after the match. But leading whitespace is not an HTTP obs-fold when the header
   line itself is indented. Examples are a YAML `headers:` mapping, an indented
   Markdown code block, and a fenced `http` block nested in a list item. In each
   case every following line has the same indentation. A header line with a Bearer
   scheme and a `${API_TOKEN}` or `<token>` placeholder is then joined with the
   next indented line (for example an `Accept` header). `grammar_value` returns the
   joined text, `literal()` no longer sees a whole placeholder, and the line is
   reported as `local-http-authorization`. Before this PR the value stopped at the
   line end and was accepted. The new fold before the scheme in `AUTH` has the
   same problem with prose: a list item that ends with "Authorization" and a colon,
   followed by an indented continuation line starting "Bearer tokens are rotated…",
   now matches. The STATUS entry says unfolding works "without crossing ordinary
   header boundaries"; that is true only for header blocks that start at column 0.
   Every new test is a single unindented header, so none catches this.
   **Fix:** unfold (and allow the fold in `AUTH`) only when the continuation line
   is indented further than the line holding the header name. Equivalently, the
   header name must start at column 0 for a leading-whitespace continuation to count
   as a fold. Add accept controls for an indented YAML mapping, an indented code
   block and a list-nested fence, each with a placeholder value followed by
   another indented header.

2. **Low — the malformed-key rule covers every key that contains `%`, not just JDBC
   query keys, and it flags Windows batch variable references
   (`credentials.rs:291`, `credentials.rs:241`).** `ASSIGNMENT` now lets a key
   start with a bare `%`, and `malformed_password_key` applies to any matching key
   containing `%`, whatever its context. Take a batch idiom that compares the quoted
   `%PASSWORD%` (or `%DB_PASS%`) variable with an empty string using `==`. The key
   captured is `%password%`. Split on `%`, one segment is `password`, so the rule
   fires. The value is the rest of the line after the first `=`, which is a
   literal, so the line is reported as `local-connection-password`. Before this
   PR, `\b` keyed this as `PASS%` / `PASSWORD%`, which failed `password_key`, and
   the line passed. The STATUS entry describes the rule as covering "percent-bearing
   JDBC query keys", but the code does not limit it to that context.
   **Fix:** treat a `%NAME%` environment reference as a variable, not a key. That
   is the shape `literal()` already accepts as a placeholder. Alternatively, apply
   the split/skeleton rule only to query or connection contexts. Either way, add a
   batch-file accept control.

3. **Low — `macdef` skipping is still LF-only (`credentials.rs:134-145`).**
   `Tokens::next` now ends comments at CR, but `skip_macro` still uses
   `find('\n')`. In a CR-only netrc file, a `macdef` finds no LF and skips the rest
   of the file, so any later record with a literal password is never scanned. This
   is pre-existing, but it falls under the PR's "record terminators" item, and the
   new tests cover comments without covering macros.
   **Fix:** split on CR or LF in `skip_macro`, treating CRLF as one terminator.
   Add a CR-only regression with a `macdef` followed by a credential record.

4. **Low — reversed prose controls are not recorded in the ADR
   (`.githooks/tests/fixtures.json` r10-keep-2 / r12-keep-1;
   `attribution.rs:2689-2799`).** Removing `TOOLCAP` means the lowercase lines
   `Fixed by sweep` and `Tested by sweep` are now rejected. Those were accepted
   human/prose controls from R10 and R12-02 / ADV23R12-08. R13-04 asked that, if the
   rule were tightened, the `Fixed by sweep` control should be kept. The PR body
   says these controls were rewritten. In this repository "sweep" is ordinary
   domain language (parameter sweeps), so rejecting it is a real tradeoff, and
   that is acceptable only if it is decided on purpose. However, the ADR 0001
   revision-13 addendum (`0001-repo-layout-and-ci-gates.md:822`) still says the
   tradeoff "remains a follow-up" and "preserves existing ordinary-prose controls",
   which is now wrong.
   **Fix:** add an ADR 0001 addendum that records the new behaviour and the
   rejected spellings, and note that it supersedes the R13-04 retention guidance.
   That gives the owner one place to accept or reverse the change.

5. **Low — the `all` range test only checks the error path
   (`xtask/tests/policy.rs:1279-1301`).** `all_honors_provenance_history_range`
   shows that a bad `--head` is rejected. It does not show that a valid
   `--base/--head` range actually scans history, for example a credential added
   and then deleted inside the range. That positive case is the reason for the fix.
   The change also has a side effect: `all` now exits with an error inside GitHub
   Actions when there is no event range (R13-03 behaviour). No workflow calls
   `all` today. Even so, this should be mentioned next to `cargo xtask all` in
   `CONTRIBUTING.md`, or in the help text.
   **Fix:** add a temporary-repository test in which `all --base B --head H` fails
   on a secret that was added and then deleted within `B..H`, and passes without
   the range.

6. **Info — malformed JDBC keys are reported under the generic rule.** The `jdbc`
   flag (`credentials.rs:297`) depends on the decoded key being exactly `password`
   or `pwd`. A malformed key such as `password%GG` inside a JDBC query is therefore
   reported as `local-connection-password`, not `local-jdbc-password`. Detection
   still works. The tests check for the substring `password`, which hides the
   difference. This is cosmetic, but tests that assert the exact rule id would
   pin the behaviour down.

## Regression check on existing detection

None of the hunks loosens an existing rejection. `ASSIGNMENT` now matches a
superset of what it matched before (a bare leading `%`). `password_key` is the old
predicate, factored out. Placeholder handling (`literal`) and the URI and authority
rules are unchanged. In `AUTH` the `[ \t]+` path after the scheme is unchanged; the
fold alternatives only add matches. On the attribution side, `TOOLNAME` is a
case-insensitive superset of `TOOLCAP`, so every capitalised rejection still
applies. The only behaviour changes are the new rejections in findings 1, 2 and 4.
