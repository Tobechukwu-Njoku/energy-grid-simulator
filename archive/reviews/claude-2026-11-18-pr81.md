### Scenarios checked

- **Conflicts:** `git merge-tree` exits with status 1 on a conflict, and the `git` helper
  turns that into an error, so both gates fail. Test:
  `pr75_conflicting_merges_fail_both_gates_closed`. Unrelated histories also fail.
- **Reverts:** a revert of existing evidence shows up as a deletion in the merge result
  and is rejected at line 551. A revert of code goes to the ordinary gate.
- **No-op PRs:** a merge result equal to main passes both gates. The merge then changes
  nothing.
- **Merge methods:** rebase merges are enabled. GitHub refuses a rebase merge whose
  result would differ from a merge commit, and a squash commit has the merge-result
  tree, so the classification matches what lands.
- **`policy_approval` workflow scan:** it now reads workflows from the merge result
  instead of the head. That is the tree that `pull_request` events run.
  No workflow version in main's history has had a push trigger for any branch other
  than `main`, so a stale workflow that exists only in the head cannot publish checks.
- **Existing evidence:** all 71 Markdown files under `reviews/` on main still parse with no header errors
  under the stricter parser. I checked this with a line-by-line emulation of `field`
  and `parse_header` over the first 40 lines of each report.

I found no new way for a review-evidence PR to admit a non-review change, or to change
or remove existing evidence.

## Findings

1. **[P2] One malformed report anywhere on main blocks `independent-review` for every
   ordinary PR.**
   - **Cause.** `evaluate` now adds a finding for every report on main whose header has
     errors, before it checks whether the report cites the PR (lines 360-363, before
     `cites_pr` at line 368). `independent_review` passes every `.md` file under
     `docs/requirements/reviews/` to `evaluate`, nested directories included.
   - **How a malformed report reaches main.** The D-77 path validates headers only for
     single-component review files. An ordinary PR is not checked at all: it can add
     `docs/requirements/reviews/notes.md` or `reviews/sub/x.md` alongside code. Two
     `Verdict:` lines, a second `Reviewed head` line, or a sample header quoted in the
     first 40 lines are enough. Such a PR needs only one approving review of its own
     head.
   - **Effect.** After that PR merges, every later ordinary PR fails with
     "duplicate … header field", even though the report has nothing to do with it.
   - **No recovery through the gates.** Under D-77, a PR that deletes or edits the bad
     report is rejected (lines 551 and 570). Under the ordinary gate, the bad report is
     still on main, so that PR fails too. Only an owner bypass would get the repair
     merged. This is the kind of deadlock D-77 was written to remove. Before this PR,
     such a report was simply ignored.
   - **Fix.** Report header errors only for reports that cite a commit of this PR. The
     existing hex-word scan in `evaluate` would serve. Treat every other malformed
     report as non-evidence.
   - **Tests.** Add a regression test: a malformed report on main that does not cite
     the PR must not fail an otherwise approved PR. The existing duplicate-header test
     must still fail a malformed report that does cite the PR.

2. **[P3] STATUS keeps claims that are false at this head.** The paragraph "PR #75
   earlier review repairs (superseded above)" still says that "the
   Google-author/OpenAI-reviewer matrix alignment is included" and that "D-77's wording
   now spells out these validation rules" (`STATUS.md` lines 28-45). Neither is true:
   the matrix and D-77 are unchanged. AGENTS.md rule 7 makes STATUS the handoff record
   for future agents. Remove the paragraph, or reduce it to one line saying what was
   withdrawn.

## Other observations (no change requested)

- **D-77 provenance.** This PR is the first to put the D-77 row on main. Its only
  source in Git is the agent commit `c938d79`, and its "Owner" attribution is not
  backed by a recorded owner answer in the repository. The owner's approval of the
  exact head, which `policy-approval` needs anyway, should be read as confirming the
  row text. Q-K-5 already asks for confirmation of the implementation boundaries.
- **Results depend on the state of main.** Both gates now evaluate the merge with
  main as it is when the event fires. `trusted-gates.yml` does not re-run when main
  moves. A result computed against an older main can therefore differ from the merge
  that finally lands, especially when there are several merge bases. This was already
  true of the merge-base design. Requiring branches to be up to date, or a merge queue,
  would close it. I could not read the branch protection settings: the agent account
  gets 404 from that API.
- **Existing evidence cannot be corrected.** A review-documents-only PR that deletes
  or changes existing evidence returns findings and never reaches the ordinary gate.
  Correcting an old report therefore needs an owner bypass. This matches D-77's
  immutability wording.
- **New reports may be executable.** As noted in the earlier review, new reports may
  still have mode `100755`.
