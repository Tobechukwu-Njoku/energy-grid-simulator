## R15V5-01 — BLOCKING: valid encoded URI hosts suppress literal credentials

**Location:** `xtask/src/secrets/credentials.rs:400`, especially `:410`.
**Severity:** high. **Comparison:** both `112de8d` and `f666c59` reject; the
requested head accepts the identical fixture.

The replacement URI scanner discards the entire credential finding unless the
first host character is ASCII alphanumeric or an opening square bracket.
That is not the URI host grammar. Percent-encoded hostnames and PostgreSQL's
percent-encoded Unix-domain socket directories are valid supported inputs.

Reproduction without publishing a literal credential: construct a PostgreSQL
URI from an ordinary username, a fresh non-placeholder synthetic password, and
the host component `%2Fvar%2Frun%2Fpostgresql`; use `/db` as its database path.
The simpler host `%68ost` reproduces the same acceptance change. Do not use an
angle-bracket password placeholder as the negative fixture.

Independent `PQconninfoParse` parsing accepts the socket URI, returns the host
directory `/var/run/postgresql`, and preserves the complete supplied password.
No connection is attempted. A Rust source string holding that URI also compiles
and executes. This is neither malformed URI syntax nor a placeholder exemption.

Both earlier scanner binaries, with their respective unchanged policy trees,
exit 1 with `local-uri-credentials` in the same otherwise-passing minimal
repository. The requested head exits 0. Forty further encoded-scanner inputs
(two URI constructions, five UTF encodings and four byte alignments) preserve
this difference at all three heads: the candidate accepts every input and both
baselines detect every input.

In a full disposable clone at the exact candidate, the clean `all` control
passes. After staging the source, `provenance` and `all` still incorrectly pass.
Committed-checkout provenance and an explicit add-then-delete historical range
also incorrectly pass. This is therefore a working checkout/history bypass of
the requested CI gate, not merely an internal helper result.

Restore detection for URI-grammar host forms, including percent-encoded socket
paths. A restrictive host plausibility check must not silently erase an already
recognized literal password. Add controls at both checkout and range boundaries.

## R15V5-02 — BLOCKING: a leading encoded query-key character is no longer recognized

**Location:** `xtask/src/secrets/credentials.rs:269`, `:336`.
**Comparison:** `f666c59` rejects; candidate accepts. `112de8d` accepts too;
this is specifically a regression from the immediately preceding checker,
not a claimed regression from both baselines.

Use the original quoted JDBC fixture but percent-encode the first character of
the password parameter name: `%70assword`, `%70wd`, or an entirely encoded key.
Keep a complete non-placeholder literal as the value. The old dedicated JDBC
path decodes parameter names before recognizing them. Its replacement assignment
regex permits percent signs only after an initial ASCII letter or underscore.
It consequently never hands the complete encoded key to `percent_decode`.

The same minimal-repository CLI fixture exits 1 with `local-jdbc-password` at
`f666c59` and exits 0 at the requested head. An ordinary key and an interior-only
encoding remain recognized. This is an old-reject/new-accept change in an
already supported query-key decoder, not a request to introduce another format.

## R15V5-03 — BLOCKING: adjacent matching runs do not establish a CommonMark span

**Location:** `xtask/src/secrets/credentials.rs:174`, `:200`.
**Comparison:** `f666c59` rejects; candidate accepts. `112de8d` accepts too.

Enclose an environment-assignment example in a two-backtick code span. Inside
that span put a single backtick immediately before the assignment key, then an
angle-bracket placeholder, a single backtick and an additional literal suffix.
Under CommonMark the inner single runs are literal content: code spans do not
nest. The complete value is not merely the placeholder.

The candidate nevertheless takes the inner run as an opener and its matching
run as a closer, hiding the suffix from classification. The minimal CLI case
exits 0; `f666c59` exits 1 with `local-connection-password`. Fenced-code-context
controls show the same absence of Markdown-context validation. By contrast,
genuine direct-key placeholder spans pass, and unequal-only runs and a run not
directly before the key reject as designed.

The helper validates local run adjacency and length, not membership in an actual
CommonMark inline span. Restrict the exception to real eligible spans or preserve
the format-derived value where that cannot be established. Merely adding another
local backtick heuristic does not meet the claimed exception.

Additional differential strings with malformed quoted keys or braced HTTP
values also lose earlier findings. They are not used here to claim usable
credential syntax: particularly, braces are not valid Basic/Bearer token68
characters. Any broader support for such syntaxes is **FOLLOW-UP**. The valid
URI regression alone is sufficient to block this head under either baseline.

## Changed Markdown controls: complete inventory and writability

1. For each one-, two- and three-backtick delimiter, the controls opening before
   `&password`, `?password`, and `Server=...;Pwd` now expect findings rather than
   acceptance: three shapes, nine assertions. In each, the run is not directly
   before the credential key and the value otherwise absorbs trailing markup.
2. The five JDBC placeholder controls move the opener from before the whole URL
   to directly before the password key. Their five placeholder values are
   unchanged: `<password>`, `<EXAMPLE_PASSWORD>`, `%3Cpassword%3E`, `...`, and
   `%2E%2E%2E`. This now exercises the specifically permitted exception.
3. The single driver/host/port/database JDBC template makes the same opener move
   to its password key; no detection expectation is weakened.
4. In the round-14 report, line 111 adds a following query parameter to terminate
   the password placeholder. Line 113 quotes its ellipsis value. Both repaired
   lines pass the scanner and retain their original explanatory meaning.

Two adjacent, non-Markdown changes are also accounted for: the no-value
Authorization description keeps its acceptance expectation but constructs its
source text from fragments; the URI negative test appends a literal suffix to a
variable placeholder, because a whole variable reference is now an intended
positive control. Neither is evidence that a literal credential became safe.

The documentation restrictions are noticeable, but do not make ordinary docs
unwritable: full connection examples with a terminating semicolon, query examples
with a following parameter, quoted whole-placeholder attributes and genuine
direct-key spans all pass. These alternatives were tested, rather than merely
suggested. All 53 controls match their intended results: 37 positive controls
and 16 negatives, including the nine changed assertions and seven unambiguous
placeholder-plus-literal-suffix controls. More permissive safe presentation
normalization is **FOLLOW-UP**, not a reason to restore suffix truncation.
